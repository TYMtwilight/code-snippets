Optional.orElseThrow と Supplier<T>

  • 📅 作成日: 2026-09-20
  • 🔄 更新日: 2026-10-01

🎯概要

Optional.orElseThrow(Supplier) は、値が空のときだけ例外を「作って」投げる仕組み。Supplier<T> は「引数なしで値を返す処理」を表す関数型インターフェースで、ラムダ式 () -> new XxxException() はコンパイラの型推論によって自動的にこのインターフェースの実装として扱われる。

📌使用場面

  • DBやリポジトリ検索の結果が「見つからないかもしれない」ときに、Optional<T>で受け取り、空ならドメイン固有の例外を投げたい場合
  • 例外オブジェクトの生成コストを、実際に必要になったとき(=値が空のとき)だけ発生させたい場合(遅延評価)
  • Spring MVCの @ExceptionHandler / @RestControllerAdvice と組み合わせて、Service層は例外を投げるだけにし、HTTPレスポンスへの変換を一元化する設計。Service層がHTTPステータスやレスポンス形式を意識せずに済み、変換ルールをコントローラーごとに散らばらせず1箇所にまとめられる

💻コード

1. UserController

@RestController
public class UserController {

    @GetMapping("/users/{id}")
    public User getUser(@PathVariable Long id) {
        return userService.findById(id)
                .orElseThrow(() -> new UserNotFoundException(id));
    }
}

そもそも何を解決したいのか

  • 「IDでユーザーを検索したら、いないかもしれない」という状況を安全に扱いたい、というのが出発点
  • nullを直接返す設計はNullPointerExceptionの温床になるため、「中にUserが入っているかもしれないし、空かもしれない箱」としてOptional<User>を使う

箱が空だったときの処理をどう渡すか

  • orElseThrow(() -> new UserNotFoundException(id))のようにラムダ式(=まだ実行されていない「レシピ」)を渡すと、箱が空のときだけレシピが実行され、例外が作られる。これが「遅延評価」
  • Java では、メソッドを呼ぶ前に引数の式が必ず先に計算される。値そのものを渡す書き方だと、箱の中身がある/ないに関わらず毎回計算されてしまう。この違いは、orElse と orElseGet を比べると分かりやすい
// orElse: 引数が先に計算されるので、値があっても createGuest() が毎回呼ばれる
User user = opt.orElse(createGuest());

// orElseGet: Supplier(レシピ)を渡すので、空のときだけ createGuest() が呼ばれる
User user = opt.orElseGet(() -> createGuest());
  • orElseThrow の引数も Supplier なので、orElseGet と同じく必要なときだけ例外が作られる。例外のインスタンスを直接渡す orElseThrow(new UserNotFoundException(id)) は、そもそもコンパイルエラーになる

2. UserNotFoundException(自作のカスタム例外)

// 非検査例外
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(Long id) {
        super("User not found: id=" + id);
    }
}

super(...) の意味

  • super(...)は「親クラス(RuntimeException)のコンストラクタを呼び出す」という意味
  • 例外の「何が起きたか」というメッセージは、getMessage()で取り出せる仕組みになっているが、その中身は親クラス(RuntimeException、さらに遡るとThrowable)が管理している
  • super("User not found: id=" + id)でメッセージを親に渡しておくことで、catchした側がex.getMessage()で"User not found: id=5"のような文字列を取得できるようになる
  • これを省略するとgetMessage()がnullを返し、ログを見てもエラーの詳細が分からなくなる

3. Supplier(標準ライブラリ: java.util.function)

public interface Supplier<T> {
    T get(); // 抽象メソッドはこれ1つだけ
}

ラムダ式(レシピ)の「型」が Supplier<T>

  • java.util.function.Supplier<T>は「引数なしで、何かを作って返す処理」を表す標準の関数型インターフェース。抽象メソッドはT get()ただ1つ
  • () -> new UserNotFoundException(id)というラムダ式は、実質「Supplier<UserNotFoundException>型のインスタンスであり、get()の中身がreturn new UserNotFoundException(id);である」という意味

4. Optional.orElseThrow のシグネチャ(標準ライブラリ: Optional<T> クラス内)

public <X extends Throwable> T orElseThrow(Supplier<? extends X> exceptionSupplier) throws X

シグネチャの読み方

部分意味
<X extends Throwable>「Throwable(例外の親玉)を継承した、何らかの型X」を扱えるようにする宣言
T orElseThrow(...)Optional<T>の中身(T型)を返すメソッド
Supplier<? extends X> exceptionSupplier引数として「X型(かその子クラス)を作るSupplier」を受け取る
throws XこのメソッドはX型の例外を投げる可能性がある、という宣言
  • 今回の例ではT=User、X=UserNotFoundExceptionが当てはまる

なぜコードに Supplier という文字が出てこないのか

  • 呼び出す側(自分が書くコード)はSupplierという文字を書かない。orElseThrowの引数の型がSupplier<? extends X>だとメソッド定義側にすでに書いてあるので、コンパイラがラムダ式をそこに自動で当てはめる(型推論)
  • Supplierには抽象メソッドがget()ただ1つしかないため、「このラムダ式はどのメソッドの実装か」で迷う余地がない

5. ラムダ式を匿名クラスで書いた場合

// ラムダ式 () -> new UserNotFoundException(id) は、次の匿名クラスの省略記法にすぎない
Supplier<UserNotFoundException> supplier = new Supplier<UserNotFoundException>() {
    @Override
    public UserNotFoundException get() {
        return new UserNotFoundException(id);
    }
};
User user = opt.orElseThrow(supplier);   // opt は Optional<User>

ラムダ式との関係

  • 型推論の結果をラムダ式を使わずに全部書き出すと、このコードと完全に等価になる
  • ラムダ式は、これを毎回書くのが面倒なので生まれた省略記法にすぎない

6. 全体の流れ

  • findByIdが空のOptionalを返す(該当データなし)
  • orElseThrowが内部でexceptionSupplier.get()を呼び出し、UserNotFoundExceptionを生成してスロー
  • 例外はコントローラーメソッドの外に飛び出し、@ExceptionHandlerや@RestControllerAdvice側でキャッチされ、HTTPレスポンスに変換される
