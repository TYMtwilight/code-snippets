関数型インターフェースとは

  • 📅 作成日: 2026-09-20
  • 🔄 更新日: 2026-09-26

🎯概要

関数型インターフェースとは、「穴(未実装のメソッド)が1つだけ空いている型はめパズル」のこと。穴が1つしかないから、ラムダ式というピースをはめても「どの穴用か」で迷わない。これにより、普通の変数には「計算の結果」が入るのに対し、関数型インターフェースの変数には「計算の手順」を入れられるようになる。入れた手順は、あとで好きなタイミングで実行したり、他のメソッドに渡して実行を任せたりできる。

📌使用場面

  • ある処理(足し算、判定、変換など)を変数や引数として渡したいとき
  • new Xxx() { ... }という匿名クラスの記述を、ラムダ式で簡潔に書き換えたいとき
  • Supplier, Function, Predicate, Consumer, Comparator など、java.util.functionパッケージの標準インターフェースを使うとき

💻コード

// 抽象メソッドが1つだけ → 関数型インターフェース
@FunctionalInterface
interface Adder {
    int add(int a, int b);
}

// ラムダ式登場前(匿名クラス)
Adder adder1 = new Adder() {
    @Override
    public int add(int a, int b) {
        return a + b;
    }
};

// ラムダ式で簡潔に書ける(add()の実装だと一意に決まる)
Adder adder2 = (a, b) -> a + b;
System.out.println(adder2.add(2, 3)); // 5

// 抽象メソッドが2つあると、ラムダ式は渡せない(コンパイルエラー)
interface BadAdder {
    int add(int a, int b);
    int subtract(int a, int b); // どちらの実装か決められないため NG
}

💡説明

0. たとえ話: 「穴が1つだけの型はめパズル」

  • インターフェースは「型はめパズルの外枠」。抽象メソッドは、そこに空いている「穴」だと考える
  • interface Adder { int add(int a, int b); } には穴が1つだけある。「引数を2つ受け取って数字を返す」形の穴
  • ラムダ式 (a, b) -> a + b は、その穴にぴったりはまる「ピース」。ピース側には「どの穴用か」なんて書いていないし、書く必要もない
  • 穴が1つしかないパズルなら、ピースを持ってきたらそこにはめるしかないので迷いようがない。これが関数型インターフェースの正体
  • もし穴が2つあったら(addとsubtractの両方がある等)、1つのピースをどちらの穴にはめればいいか分からなくなる。だからJavaは「抽象メソッドは1つだけ」というルールを設けている

0.5 「計算の結果」を入れる変数と「計算の手順」を入れる変数

  • 普通の変数: int x = 3 + 5; は、この行で 3 + 5 がその場で計算され、x には結果の 8 だけが入る
  • 関数型インターフェースの変数: Supplier<Integer> s = () -> 3 + 5; は、この時点では何も計算されない。s に入るのは「3 + 5 を計算する」という手順そのもの
  • int result = s.get(); のように呼び出した瞬間に、初めて計算が実行されて 8 が得られる
  • たとえるなら、普通の変数は「できあがった料理」を冷蔵庫にしまうこと。関数型インターフェースの変数は「レシピ」をしまっておき、食べたいときに作ること

0.6 手順を他のメソッドに渡して、実行を任せる

  • 手順を変数に入れられるということは、他のメソッドの引数として渡すこともできる。レシピを渡して「必要になったら、これで作って」と頼むイメージ
  • 身近な例: userRepository.findById(id).orElseThrow(() -> new UserNotFoundException(id))。ここで渡しているのは例外オブジェクトそのものではなく、「例外を作る手順」
  • ユーザーが見つかった場合: 渡した手順は一度も実行されない(例外は作られない)
  • 見つからなかった場合: orElseThrow の中で初めて手順が実行され、例外が作られて投げられる
  • つまり、いつ実行するか(そもそも実行するか)を、受け取った側が決められる。これが「処理を値のように扱える」ことの利点

1. 出発点: 「処理」を変数に入れたい

  • Javaで扱えるのは基本的に「値」(int, String, オブジェクトなど)
  • 「2つの数を足す処理」のような処理そのものを変数として持ち運びたい場合、静的型付け言語であるJavaでは何らかの「型」が必要になる
  • この「型」の役割を、これまで通りインターフェースに担わせる(実装クラスや匿名クラスを使う)

2. ラムダ式による簡略化と、その代償

  • new Adder() { ... }という匿名クラスの記法は冗長。ラムダ式 (a, b) -> a + b を使えば短く書ける
  • ただしラムダ式の文法には「どのメソッドの実装か」という名前を書く場所が存在しない。インターフェースに抽象メソッドが複数あると、コンパイラはどれを実装したいのか判断できない

3. 解決策: 抽象メソッドを1つに制限する

  • 「抽象メソッドをちょうど1つだけ持つインターフェース」に限ってラムダ式の代入を許す、というルールがこれを解決する
  • メソッドが1つしかなければ、コンパイラは「渡されたラムダ式は、この唯一のメソッドの実装に決まっている」と迷わず判断できる
  • この条件を満たすインターフェースが「関数型インターフェース」

4. @FunctionalInterface アノテーションの役割

  • 「このインターフェースは関数型インターフェースとして使うつもりです」という意図を明示する
  • 付けなくても、抽象メソッドが1つだけなら関数型インターフェースとして機能する。ただし付けておくと、誤って抽象メソッドを2つ以上追加してしまった場合にコンパイルエラーで検知できる
  • defaultメソッドやstaticメソッド、Object由来のメソッド(equals, hashCode, toString)は抽象メソッドの数にカウントされない

5. 標準ライブラリの既製品

  • Javaは頻出パターンをあらかじめ関数型インターフェースとしてjava.util.functionパッケージに用意している
  • 例: Supplier<T>(T get())、Function<T,R>(R apply(T t))、Predicate<T>(boolean test(T t))、Consumer<T>(void accept(T t))
  • これらのおかげで、毎回自分でインターフェースを定義しなくても、標準の型にラムダ式やメソッド参照をそのまま渡せる
