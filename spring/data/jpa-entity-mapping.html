JPA エンティティのマッピング

  • 📅 作成日: 2026-10-07
  • 🔄 更新日: 2026-10-07

🎯概要

エンティティとは、DB のテーブルに対応する Java のクラスのこと。アノテーションで「このクラスはどのテーブルに、どのフィールドはどのカラムに対応するか」を JPA に伝える。この対応づけをマッピングと呼ぶ。

Java 側class Product
⇄
DB 側products テーブル
Java 側String name
⇄
DB 側name カラム
Java 側Long id
⇄
DB 側主キー
Java 側インスタンス 1 個
⇄
DB 側レコード 1 行

マッピングができていれば、SQL を書かなくても、Java のオブジェクトを保存したり取り出したりできるようになる。

💻コード

1. 基本の形

import jakarta.persistence.*;

@Entity
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String name;

    @Column(nullable = false)
    private BigDecimal price;

    @Enumerated(EnumType.STRING)
    private ProductStatus status;

    private LocalDateTime createdAt;

    // JPA が使う引数なしコンストラクタ
    protected Product() {
    }

    public Product(String name, BigDecimal price) {
        this.name = name;
        this.price = price;
        this.status = ProductStatus.ON_SALE;
        this.createdAt = LocalDateTime.now();
    }

    // getter は省略
}

必ず要る 3 つ

1@Entity

「このクラスはテーブルに対応する」という目印。これがないと、リポジトリで扱えない（アプリの起動時にエラーになる）。

  • リポジトリで保存・取得できるようになる
  • JPQL でクラス名を使って書ける（SELECT p FROM Product p）
  • 代わりに制約も付く：@Id が必須、引数なしコンストラクタが必要、final にできない

2@Id

主キーにあたるフィールドに付ける。エンティティには必ず 1 つ必要。JPA はこの値で「どのデータか」を判断する。

3@GeneratedValue

主キーを誰が採番するかの指定。IDENTITY なら DB の自動採番に任せるので、id に値を入れずに保存できる。

省略できる 2 つ

@Table(name = "products")

テーブル名の指定。省略するとクラス名から自動で決まる（次の「2.」で詳しく）。

@Column(nullable = false, length = 100)

カラムの制約や名前の指定。何も指定しないならフィールドだけ書けばよく、@Column 自体が不要。上のコードで createdAt に付けていないのはそのため。

属性意味
nameカラム名を変える
nullable = falseNOT NULL 制約を付ける
length文字列の長さ（VARCHAR(100) など）
unique = true一意制約を付ける

2. 名前の対応ルール

@Table や @Column で名前を指定しなかった場合、Spring Boot はキャメルケースをスネークケースに変換して対応づける。

Java 側省略したときの DB 側の名前
class Productproduct（単数形のまま）
String namename
LocalDateTime createdAtcreated_at

つまり、テーブル名を 複数形の products にしたい場合は @Table が必要になる。逆に createdAt → created_at は自動で変換されるので、@Column(name = "created_at") は書かなくてよい。

📌 明示しておくと安全な場面

既存の DB に合わせる場合や、チームでテーブル名の規約が決まっている場合は、省略せずに書いておくほうが事故が少ない。自動変換のルールは設定で変えられるため、「書いていないが、たまたま一致していた」状態は壊れやすい。

3. 主キーの採番（@GeneratedValue）

よく使う戦略は 2 つ。使う DB によって選べるものが変わる。

IDENTITY

DB の自動採番に任せる（MySQL の AUTO_INCREMENT など）。INSERT して初めて ID が決まる。

MySQL / PostgreSQL どちらでも使える
SEQUENCE

DB のシーケンスから採番する。INSERT する前に ID を取得できる。

PostgreSQL / Oracle 向け（MySQL は非対応）
// IDENTITY：DB の自動採番に任せる
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

// SEQUENCE：シーケンス名を指定して使う
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE,
                generator = "product_seq")
@SequenceGenerator(name = "product_seq",
                   sequenceName = "product_seq",
                   allocationSize = 50)
private Long id;

💬 補足: IDENTITY は 1 件ごとに INSERT して採番するため、複数件をまとめて INSERT する最適化が効かない。大量登録の性能が問題になる場面では SEQUENCE が有利（allocationSize の分だけ ID をまとめて確保できる）。

4. 引数なしコンストラクタが必要な理由

JPA は DB からデータを取り出すとき、まず空のインスタンスを作り、そこにフィールドの値を入れていく。このとき引数なしのコンストラクタが使われる。

✗ 引数ありのコンストラクタだけを定義する 
public class Product {

    public Product(String name, BigDecimal price) {
        this.name = name;
        this.price = price;
    }
}

Java には「コンストラクタを 1 つも書かなければ、引数なしのものが自動で用意される」というルールがある。これまで JPA は、この暗黙のコンストラクタを借りて空のインスタンスを作っていた。

ところが自分でコンストラクタを書くと、この自動生成は止まる。すると JPA が使えるコンストラクタが 1 つも無くなり、DB から取り出すときにインスタンスを作れずエラーになる。

✓ 引数なしコンストラクタを添える 
// JPA が使う。アプリのコードからは呼ばせたくないので protected
protected Product() {
}

public Product(String name, BigDecimal price) {
    this.name = name;
    this.price = price;
}

public である必要はなく、protected で十分。こうしておくと「中身が空の Product」をアプリのコードから誤って作ってしまうことを防げる。

⚠️ private にはできない

JPA には、関連するデータを実際に使うときまで読み込まない仕組み（遅延ロード）がある。このとき Hibernate は、本物の代わりに Product を継承した「身代わり」のクラスを実行時に作る。

継承したクラスは親のコンストラクタを呼ぶが、private は継承先から呼べない。そのため JPA の仕様でも、public か protected にすることと決められている。

つまり protected は、仕様を満たせる範囲でいちばん狭い可視性ということ。

5. フィールドの型の選び方

用途使う型避ける型理由
主キーLonglongnull で「まだ保存していない」を表せる
金額BigDecimaldoubledouble は誤差が出る
日時LocalDateTimeDatejava.time のほうが扱いやすい
区分値enumString / int取りうる値がコード上で決まる

enum は必ず EnumType.STRING で保存する

@Enumerated(EnumType.STRING)
private ProductStatus status;

この指定がないと、enum は宣言した順番の番号で保存される。ProductStatus.SOLD_OUT を保存したときに、DB に何が入るかが変わる。

指定なし（ORDINAL）

並び順の番号が入る

status 列 → 1
EnumType.STRING

enum の名前が入る

status 列 → 'SOLD_OUT'

番号で保存していると、あとから enum に値を足したときに意味がずれる。たとえば「準備中」を先頭に足すと、こうなる。

public enum ProductStatus {
    PREPARING,   // ← 先頭に追加した（0 番目）
    ON_SALE,     // 0 番目 → 1 番目にずれた
    SOLD_OUT     // 1 番目 → 2 番目にずれた
}

⚠️ データは変わっていないのに、意味だけが変わる

DB に入っている 1 は、もともと「売り切れ（SOLD_OUT）」のつもりだった。しかし追加後は 1 が「販売中（ON_SALE）」として読まれる。

status = 1 → 追加前: SOLD_OUT（売り切れ）／追加後: ON_SALE（販売中）

売り切れの商品が販売中として扱われてしまうが、エラーは出ないので気づきにくい。STRING なら 'SOLD_OUT' という名前で入っているので、並び順を変えても影響がない。

6. やりがちな失敗

Lombok の @Data を付ける

@Data は getter / setter / toString / equals / hashCode を全フィールドからまとめて自動生成する。便利だが、エンティティに付けると 3 つの問題が起きる。

例として、Product（商品）と Category（カテゴリ）が互いを参照している状態で見ていく。

@Entity
@Data
public class Product {

    @Id
    private Long id;

    private String name;

    @ManyToOne
    private Category category;       // Product → Category
}

@Entity
@Data
public class Category {

    @Id
    private Long id;

    @OneToMany(mappedBy = "category")
    private List<Product> products;  // Category → Product
}

このようにどちらからでも相手を辿れる状態を、双方向の関連と呼ぶ。

1toString() が無限ループする

toString は全フィールドを文字列にしようとするため、関連先も文字列にしようとする。

product.toString()フィールドの category も文字列にする
↓
category.toString()フィールドの products も文字列にする
↓
product.toString()最初に戻ってしまう
↓
💥 StackOverflowError

2equals / hashCode が全フィールドで作られる

関連フィールドまで比較の対象になるため、次の問題が起きる。

  • 比較しただけで DB アクセスが起きる：まだ読み込んでいない関連先を、比較のために読みにいってしまう
  • 同じ商品でも「別物」と判定される：id が同じでも、name を 1 つ変えれば等しくないことになる

3id にも setter ができる

主キーは DB が採番するもので、アプリのコードから書き換えるものではない。setId() があると、誤って別のデータを上書きする事故につながる。

✓ 必要なものだけを付ける 
@Entity
@Getter                      // setter は必要なフィールドにだけ個別に付ける
public class Product {

    @ToString.Exclude        // toString が必要な場合は、関連フィールドを除外する
    @ManyToOne
    private Category category;
}

エンティティでは @Data をひとまとめに付けず、必要なものを 1 つずつ選んで付ける。

equals / hashCode を id だけで実装する

@Override
public boolean equals(Object o) {
    if (!(o instanceof Product other)) return false;
    return Objects.equals(id, other.id);   // 保存前は id が null
}

一見よさそうだが、保存する前のエンティティは id が null。未保存のオブジェクトどうしが「等しい」と判定されたり、Set に入れた後で保存すると hashCode が変わって取り出せなくなる、といった問題が起きる。

対策としては、業務上の一意なキー（商品コードなど）で実装するか、そもそも equals / hashCode を定義しないという選択もある。
