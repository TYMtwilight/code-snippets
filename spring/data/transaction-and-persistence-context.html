トランザクションと永続化コンテキスト

  • 📅 作成日: 2026-10-10
  • 🔄 更新日: 2026-10-10

🎯概要

永続化コンテキストとは、JPA が「いま扱っているエンティティ」を覚えておく作業場のこと。DB から取り出したエンティティは、まずここに置かれる。

この作業場が存在するのは、トランザクションの開始から終了までの間だけ。そして、その範囲を決めているのが @Transactional。

1
トランザクション開始空の作業場が用意される
2
取得DB から読んだエンティティが作業場に置かれる（SELECT）
3
変更setter で値を書き換える。この時点ではまだ SQL は走らない
4
コミット変更された分の SQL（UPDATE など）がまとめて発行される
5
トランザクション終了作業場は破棄される。以降、中のエンティティは管理されない

この仕組みを知らないと、「save() を呼んでいないのに更新された」「例外が出たのにロールバックされない」といった挙動に戸惑うことになる。

💻コード

1. 同じデータを 2 回取得しても SQL は 1 回

永続化コンテキストは一次キャッシュとしても働く。同じトランザクションの中で同じデータを取得すると、2 回目は DB ではなく作業場から返る。

@Transactional
public void example() {
    Product a = productRepository.findById(1L).orElseThrow();  // SELECT が走る
    Product b = productRepository.findById(1L).orElseThrow();  // SQL は走らない

    System.out.println(a == b);   // true（同じインスタンス）
}

== は「メモリ上で同じオブジェクトか」を調べる比較（equals の「中身が同じ値か」とは別物）。これが true ということは、a と b は中身が同じコピーではなく、まったく同一のオブジェクトだという意味になる。

作業場の中では「1 件のデータにつき、インスタンスは 1 つ」と決まっているため。これにより、片方を書き換えるともう片方にも反映される。

a.setName("シャープペン");

System.out.println(b.getName());   // "シャープペン"（b も変わっている）

この仕組みによって、DB 上の同じ 1 行（この例では id = 1 の商品）が Java 側で 2 つのインスタンスに分裂し、内容が食い違う、ということが起きないようになっている。

2. ダーティチェッキング（save を呼ばなくても更新される）

@Transactional
public void renameProduct(Long id, String newName) {
    Product product = productRepository.findById(id).orElseThrow();
    product.setName(newName);

    // save() を呼んでいないのに、コミット時に UPDATE が発行される
}

JPA は取得した時点の値をコピーして持っている。コミットのタイミングで現在の値と見比べ、違っていれば自動で UPDATE を発行する。これをダーティチェッキング（変更の自動検知）と呼ぶ。

コミット時、作業場の中で起きていること

取得したときのコピー name = "ボールペン"
≠
いまのエンティティ name = "シャープペン"
↓ 違いを検知したので
UPDATE products SET name = 'シャープペン' WHERE id = 1

変更していないフィールドは比較しても同じなので、実際に書き換えた分だけが UPDATE の対象になる。

⚠️ 意図しない更新に注意

「画面表示用にちょっと値を書き換えただけ」のつもりでも、管理されているエンティティなら DB に反映される。参照だけの処理では readOnly = true を付けて防ぐ（「4.」で後述）。

逆に、トランザクションの外で setter を呼んでも何も起きない。作業場が存在せず、誰も変更を見ていないため。

3. save() が実際にやっていること

Spring Data の save() は、中で 2 つの処理を使い分けている。

// SimpleJpaRepository の中身（簡略版）
if (entityInformation.isNew(entity)) {
    em.persist(entity);        // 新規 → INSERT
    return entity;
} else {
    return em.merge(entity);   // 既存 → SELECT してから UPDATE
}
persist

新規エンティティを作業場に登録する。コミット時に INSERT。

判定：id が null → 新規
merge

DB から現在の状態を読み込んでから、渡された値を上書きする。

判定：id が入っている → 既存

merge は内部で SELECT が 1 回増える。すでに作業場で管理されているエンティティに対しては、ダーティチェッキングだけで更新されるため、save() を呼ぶ必要はない。

⚠️ id を自分で採番する場合は要注意

新規でも id に値が入っているため、「既存」と誤判定されて merge が走る。存在しない行を SELECT しにいく無駄が発生する。

対策として、エンティティに Persistable を実装し、isNew() の判定を自分で書く方法がある。

4. @Transactional の役割と、付ける場所

何をしてくれるのか

メソッドに @Transactional を付けると、そのメソッドの開始から終了までが 1 つのトランザクションになる。開始・コミット・ロールバックを、Spring が代わりに行ってくれる。

タイミングSpring がやること
メソッドに入るときトランザクションを開始する（永続化コンテキストも用意される）
正常に終わったときコミットする（変更が DB に反映される）
例外が出たときロールバックする（変更がなかったことになる）

この仕組みがなければ、同じことを手書きすることになる。

✗ @Transactional がない場合 
tx.begin();
try {
    // やりたい処理
    tx.commit();
} catch (RuntimeException e) {
    tx.rollback();
    throw e;
}
✓ @Transactional を付ける 
@Transactional
public void renameProduct(Long id, String newName) {
    // やりたい処理だけを書けばよい
}

開始とコミット、例外時のロールバックという決まりきった処理が消え、業務の処理だけが残る。

どこに付けるか

トランザクションの範囲は「ここからここまでを、全部成功か全部失敗にしたい」という業務処理の単位。その単位を表すサービス層のメソッドに付ける。

@Service
public class ProductService {

    // 更新あり
    @Transactional
    public void renameProduct(Long id, String newName) { ... }

    // 参照のみ
    @Transactional(readOnly = true)
    public List<Product> findAll() { ... }
}

readOnly = true を付ける効果

  • ダーティチェッキング用のコピーを作らない：取得時の値を控えておく必要がなくなるので、何百件も読むような処理ではメモリと CPU の節約になる
  • 意図しない更新を防げる：うっかり setter を呼んでも UPDATE が飛ばないので、「2.」で見たような事故を防げる
  • DB やドライバによっては、読み取り専用の最適化が効くこともある（参照専用サーバーへの振り分けなど）

💬 補足: readOnly = true を付けたうえで setter を呼んでも、例外にはならない。UPDATE が飛ばないだけで、Java 側のインスタンスは書き換わっている。「エラーで気づける仕組み」ではない点に注意。

📌 参照だけのメソッドにも付ける意味はあるのか

実は SimpleJpaRepository には、最初から @Transactional(readOnly = true) が付いている。そのため、リポジトリを 1 回呼ぶだけのメソッドなら、サービス側に書かなくても読み取り専用トランザクションで動く。

// これだけなら、付けても付けなくてもほぼ同じ
public List<Product> findAll() {
    return productRepository.findAll();
}

意味が出てくるのは、リポジトリを複数回呼ぶ場合。サービス側に付けないと、呼び出しごとに別のトランザクションになってしまう。

別々だと困るのは次の 2 点。

  • 読む時点がずれる：1 回目と 2 回目のあいだに他の処理がコミットすると、商品一覧は更新前・件数は更新後、という食い違った画面になりうる
  • 永続化コンテキストも分かれる：同じデータを 2 回取得すると、SQL も 2 回発行される（「1.」のキャッシュが効かない）

サービスのメソッドに付ければ、その中の取得すべてが 1 つのトランザクションにまとまるので、どちらも同じ時点のデータとして扱える。

// 2 回の取得が同じトランザクションになる
@Transactional(readOnly = true)
public DashboardView load() {
    List<Product> products = productRepository.findAll();
    long orderCount = orderRepository.count();
    ...
}

「1 回しか呼んでいないから要らない、2 回呼ぶから必要」とメソッドごとに見極めるのは手間がかかるうえ、あとからリポジトリの呼び出しが増えたときに付け忘れる。そのため実務では、参照系のメソッドには一律で付けるというルールにしておくことが多い。

5. @Transactional が効かないケース

@Transactional は、Spring が作るプロキシによって実現されている。メソッドの呼び出しがプロキシを通らないと、トランザクションは始まらない。

✗ 自己呼び出し：トランザクションが始まらない 
@Service
public class ProductService {

    public void outer() {
        inner();   // ← 自分のメソッドを直接呼んでいる
    }

    @Transactional
    public void inner() {
        // トランザクションは始まらない
    }
}
◯
外部から呼ぶ場合呼び出し元 → プロキシ（ここでトランザクション開始）→ 実体のメソッド
✗
自己呼び出しの場合実体のメソッド → 実体のメソッド（プロキシを通らない）

同じクラスの中から呼ぶと、プロキシを経由せず素のメソッドがそのまま実行される。アノテーションは無視され、エラーにもならないため気づきにくい。

💬 同じ理由で、private メソッドや final メソッドに付けても効かない。プロキシが上書きできないため。

✓ クラスを分けて、外部から呼ぶ形にする 
@Service
public class ProductService {

    private final ProductUpdater updater;   // 別クラスとして注入する

    public void outer() {
        updater.inner();   // プロキシを経由するので有効になる
    }
}

6. ロールバックされる条件

「例外が出れば必ずロールバックされる」と思いがちだが、既定では非検査例外のときだけ。

例外の種類例既定の挙動
非検査例外（RuntimeException / Error）IllegalArgumentExceptionロールバックされる
検査例外（Exception）IOExceptionコミットされる
✗ 検査例外は、投げてもロールバックされない 
@Transactional
public void register(Product product) throws IOException {
    productRepository.save(product);

    throw new IOException();   // 保存はコミットされてしまう
}
✓ rollbackFor で対象を広げる 
@Transactional(rollbackFor = Exception.class)
public void register(Product product) throws IOException { ... }

💬 そもそも検査例外を投げず、非検査例外に包み直してから投げる設計にしておけば、この問題は起きにくい。検査例外はその場で catch し、自作の非検査例外にして投げ直す。

@Transactional   // rollbackFor は不要
public void register(Product product) {
    productRepository.save(product);

    try {
        fileStorage.write(product);          // IOException（検査例外）を投げる
    } catch (IOException e) {
        throw new FileStorageException(e);   // 非検査例外に包み直す
    }
}

包み直す先は、RuntimeException を継承した例外として用意しておく。元の例外を cause として渡すと、スタックトレースに原因が残る。

public class FileStorageException extends RuntimeException {

    public FileStorageException(Throwable cause) {
        super(cause);
    }
}

7. propagation（トランザクションの伝播）

トランザクションの中から、別のトランザクション付きメソッドを呼んだときの振る舞い。

REQUIRED

既定値。すでにトランザクションがあれば参加し、なければ新しく開始する。

外側がロールバックすれば、内側も巻き込まれる
REQUIRES_NEW

既存のものを中断し、必ず新しいトランザクションを開始する。

外側がロールバックしても、内側は残る

REQUIRES_NEW の使いどころは、本処理が失敗しても記録を残したい場合。監査ログがその代表例で、「登録しようとして失敗した」という事実自体を残したい。

ログを書き込む側に REQUIRES_NEW を付ける。

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAuditLog(String message) {
    auditLogRepository.save(new AuditLog(message));
}

呼び出す側は、ふつうに @Transactional を付けたメソッド。ここで例外が出たとする。

@Transactional
public void register(Product product) {
    productRepository.save(product);
    auditService.writeAuditLog("登録: " + product.getName());

    throw new IllegalStateException();   // 後続の処理で失敗
}

トランザクション A ── register()

save(product)取り消される

トランザクション B ── writeAuditLog()／REQUIRES_NEW

save(auditLog)そのまま残る

✗ 例外 → A をロールバック（B には影響しない）

A と B は別のトランザクションなので、A のロールバックは B に届かない。結果として、商品は登録されていないが、ログだけは残る。

💬 REQUIRES_NEW を付けずに既定の REQUIRED のままにすると、ログの保存もトランザクション A に参加する。つまり商品と一緒に取り消され、何も残らない。
