Spring Data ページングとソート

  • 📅 作成日: 2026-10-06
  • 🔄 更新日: 2026-10-06

🎯概要

一覧を全件まとめて取得するのではなく、「何ページ目を・何件ずつ・どの順で」取得する仕組み。登場人物は 3 つで、要求と結果に分かれている。

名前種類役割
Pageableインターフェース要求：何ページ目を・何件ずつ・どの順で取得するか
PageRequest実装クラスPageable を実際に作るためのクラス
Page<T>インターフェース結果：取得したデータ本体 + 総件数などのメタ情報
① 要求を作る PageRequest.of(0, 20)
→
② リポジトリに渡す findAll(pageable)
→
③ 結果を受け取る Page<Product>

💻コード

1. なぜページングするのか

✗ 全件まとめて取得する 
List<Product> all = productRepository.findAll();

商品が 10 万件あれば、10 万件すべてをメモリに読み込む。メモリを圧迫し、レスポンスも遅くなる。データが増えるほど悪化し、ある日突然落ちる。

✓ ページ単位で取得する 
Pageable pageable = PageRequest.of(0, 20);
Page<Product> page = productRepository.findAll(pageable);

発行される SQL に LIMIT / OFFSET が付き、20 件だけを取得する。件数が増えても、1 回に読み込む量は変わらない。

SELECT * FROM products LIMIT 20 OFFSET 0

2. Pageable を作る（PageRequest.of）

// 基本形：1 ページ目を 20 件
Pageable pageable = PageRequest.of(0, 20);

// ソート付き（price の昇順）
Pageable sorted = PageRequest.of(0, 20, Sort.by("price").ascending());

// 複数条件でソート（price の降順 → 同額なら id の昇順）
Pageable multi = PageRequest.of(0, 20,
        Sort.by("price").descending()
            .and(Sort.by("id").ascending()));

// 短縮形（Direction とフィールド名を直接渡す）
Pageable shorthand = PageRequest.of(0, 20, Sort.Direction.DESC, "price");

引数の意味

1第 1 引数：ページ番号

0 始まり。0 が 1 ページ目にあたる。

2第 2 引数：1 ページあたりの件数

SQL の LIMIT にあたる。この値がそのまま 1 回に読み込む件数になる。

3第 3 引数：Sort（省略可）

並び順。Sort.by("フィールド名") に .ascending()（昇順）か .descending()（降順）を付ける。.and(...) でつなぐと、複数条件の並び替えになる。

📌 ページ番号は 0 始まり

100 件のデータを 1 ページ 20 件で表示する場合、ページ番号と取得範囲は次のように対応する。

ページ番号取得される範囲
page = 01 〜 20 件目（画面上の 1 ページ目）
page = 121 〜 40 件目
page = 481 〜 100 件目（最後のページ）

このとき getTotalPages() は 5 を返す。画面に「1 ページ目」と表示したい場合は、page + 1 する必要がある。

🔍 補足: なぜ変数の型を Pageable にするのか

PageRequest.of(...) が返すのは PageRequest だが、PageRequest は Pageable を実装しているので Pageable 型の変数で受け取れる。リポジトリ側も Pageable 型で受け取るため、渡す側も Pageable 型で扱うのが自然。

3. リポジトリに渡す

全件検索（findAll）は、宣言しなくても使える

public interface ProductRepository extends JpaRepository<Product, Long> {
}

この空のリポジトリでも、findAll(Pageable) は呼べる。JpaRepository が最初から持っているメソッドだから。

productRepository.findAll(PageRequest.of(0, 20));

💬 補足: このメソッドの出どころは PagingAndSortingRepository。JpaRepository がこれを継承しているので使える。CrudRepository だけを継承している場合は使えない。

自分で定義した検索メソッドに足す

「販売中の商品だけを 20 件ずつ」のように、条件を付けた検索でもページングできる。既存のメソッドに手を加える箇所は 2 つだけ。

✗ ページングなし：条件に合う商品が全件返る
List<Product> findByStatus(ProductStatus status);
✓ ページングあり：色を付けた 2 か所を変えるだけ
Page<Product> findByStatus(ProductStatus status, Pageable pageable);

1戻り値を Page<Product> に変える

データ本体に加えて、総件数などのメタ情報も受け取れるようになる。

2引数の最後に Pageable を足す

検索条件の引数（status）の後ろに置く。Pageable は「何ページ目を・何件ずつ」という指示であって検索条件ではないため、必ず最後の引数にする決まりになっている。

呼び出し側は、検索条件と Pageable を並べて渡す。

Page<Product> page = productRepository.findByStatus(
        ProductStatus.ON_SALE,          // 検索条件
        PageRequest.of(0, 20));         // 1 ページ目を 20 件

@Query で書いたクエリに足す

自分でクエリを書いた場合も、同じように Pageable を足せる。

@Query("SELECT p FROM Product p WHERE p.price <= :maxPrice")
Page<Product> findCheaperThan(@Param("maxPrice") Integer maxPrice,
                              Pageable pageable);

JPQL で書いていれば、総件数を数える COUNT のクエリは Spring Data が自動で組み立てるので、何も書かなくてよい。

⚠️ ネイティブクエリでは countQuery も自分で書く

nativeQuery = true で素の SQL を書いた場合、Spring Data はその SQL を解析できないため、COUNT のクエリを自動では作れない。countQuery に自分で書く。

@Query(
    value = "SELECT * FROM products WHERE price <= :maxPrice",
    countQuery = "SELECT count(*) FROM products WHERE price <= :maxPrice",
    nativeQuery = true)
Page<Product> findCheaperThanNative(
        @Param("maxPrice") Integer maxPrice,
        Pageable pageable);

JOIN を含むクエリでは、件数を数えるだけなら JOIN が要らないこともある。その場合も countQuery を自分で書くと、COUNT を軽くできる。

💬 補足: ページングは要らず並び替えだけしたい場合は、Pageable ではなく Sort をそのまま渡せる。戻り値は List になる。
productRepository.findAll(Sort.by("price").descending());

4. Page から取り出せる情報

Page はデータ本体とメタ情報をまとめて持っているので、ページ送りの UI に必要な値がここからすべて取れる。

📋 ここからの例の前提

商品が全部で 100 件。1 ページ 20 件で、1 ページ目（page = 0）を取得したとする。

Page<Product> page = productRepository.findAll(PageRequest.of(0, 20));

取り出せる値と、この例での結果

// データ本体
page.getContent();           // 20 件の Product が入った List

// 全体の情報
page.getTotalElements();     // 100
page.getTotalPages();        // 5

// このページの情報
page.getNumber();            // 0
page.getSize();              // 20
page.getNumberOfElements();  // 20

// 前後のページの判定
page.hasPrevious();          // false
page.hasNext();              // true
page.isFirst();              // true
page.isLast();               // false
メソッド戻り値意味
getContent()List<T>このページのデータ本体
getTotalElements()long全体の件数
getTotalPages()int全体のページ数
getNumber()int現在のページ番号（0 始まり）
getSize()int1 ページあたりの上限件数
getNumberOfElements()intこのページに実際に入っている件数
hasNext() / hasPrevious()boolean次 / 前のページがあるか
isFirst() / isLast()boolean最初 / 最後のページか

まぎらわしい 2 つの「件数」

上の例ではどちらも 20 で同じ値になるが、端数が出るページでは食い違う。商品が 95 件だった場合の最後のページ（page = 4）で比べる。

getSize()

1 ページに入る上限。どのページでも変わらない。

→ 20
getNumberOfElements()

そのページに実際に入っている件数。

→ 15（81 〜 95 件目）

ページによって変わる判定メソッド

4 つの boolean は、今いるページによって値が変わる。100 件を 20 件ずつ（全 5 ページ）表示した場合は次のとおり。

今いるページhasPrevious()hasNext()isFirst()isLast()
page = 0（最初）falsetruetruefalse
page = 2（途中）truetruefalsefalse
page = 4（最後）truefalsefalsetrue

この値をそのまま使えば、ページ送りボタンの出し分けができる。

if (page.hasNext()) {
    // 「次へ」ボタンを表示する
}

そのまま JSON で返したときの形

{
  "content": [
    { "id": 99, "name": "ボールペン", "price": 120 },
    { "id": 100, "name": "ノート", "price": 250 }
  ],
  "totalElements": 100,
  "totalPages": 5,
  "number": 0,
  "size": 20,
  "first": true,
  "last": false
}

content の中に実データが入り、その外側にページの情報が並ぶ。クライアントは totalPages や last を見て、ページ送りのボタンを作れる。

5. Controller では自動で作られる

@RestController
@RequestMapping("/products")
public class ProductController {

    private final ProductRepository productRepository;

    public ProductController(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    // GET /products?page=0&size=20&sort=price,desc
    @GetMapping
    public Page<Product> findAll(Pageable pageable) {
        return productRepository.findAll(pageable);
    }
}

メソッドの引数に Pageable を置くだけで、Spring がクエリパラメータから PageRequest を組み立てて渡してくれる。@RequestParam は書かなくてよい。

受け取れるクエリパラメータ

パラメータ意味例
pageページ番号（0 始まり）page=1
size1 ページあたりの件数size=20
sort並び順（フィールド名,方向）sort=price,desc
sort（複数）sort を 2 つ以上書くと、その順で並び替えるsort=price,desc&sort=id,asc

指定がなかったときの既定値

@GetMapping
public Page<Product> findAll(
        @PageableDefault(size = 20,
                         sort = "createdAt",
                         direction = Sort.Direction.DESC)
        Pageable pageable) {
    return productRepository.findAll(pageable);
}

@PageableDefault を付けると、クエリパラメータが省略されたときの値を決められる。この例では「新しい順に 20 件」が既定になる。

アプリ全体の既定値（application.properties）

spring.data.web.pageable.default-page-size=20
spring.data.web.pageable.max-page-size=100

max-page-size は特に重要。これがないと ?size=1000000 のような指定を受け付けてしまい、ページングしている意味がなくなる。

⚠️ sort はユーザーが自由に指定できる

sort の値はそのままフィールド名として扱われる。存在しないフィールド名を渡されると PropertyReferenceException が発生し、500 エラーになる。

GET /products?sort=notExists,desc → 500 エラー

公開 API では、並び替えに使ってよい項目を決めておき、それ以外は弾く（ホワイトリスト方式）。

6. 総件数が要らないなら Slice

Page は総件数を知るために、データ取得とは別に COUNT のクエリをもう 1 回発行している。総件数が必要ない画面では、この 1 回が無駄になる。

Page<T>

総件数・総ページ数がわかる。
SQL は 2 回（データ取得 + COUNT）。

「1 2 3 … 5」とページ番号を並べる UI 向き
Slice<T>

次のページがあるかだけわかる。
SQL は 1 回（データ取得のみ）。

「もっと見る」式の無限スクロール向き
// 戻り値を Slice にするだけで、COUNT クエリが発行されなくなる
Slice<Product> findByStatus(ProductStatus status, Pageable pageable);

使えるのは getContent() や hasNext() などで、getTotalElements() / getTotalPages() は使えない。
