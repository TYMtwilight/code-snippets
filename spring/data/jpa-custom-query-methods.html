Spring Data JPA カスタムクエリの作り方

  • 📅 作成日: 2026-10-05
  • 🔄 更新日: 2026-10-06

🎯概要

JpaRepository の標準メソッド（findById / findAll など）だけでは足りない検索は、リポジトリに自分でメソッドを追加して作る。作り方は主に 4 つあり、検索の複雑さに応じて使い分ける。クエリを自分で書く場合は、SQL ではなく JPQL という JPA 用のクエリ言語で書くのが基本。

作り方向いている場面
1. クエリメソッド条件が 2〜3 個までの単純な検索
2. @Query条件が多い・JOIN や集計を使うなど、複雑な検索
3. @Modifying + @Query条件に合うデータの一括更新・一括削除
4. Specification など検索画面のように、入力によって条件が変わる検索

🔍 用語ノート: JPQL

JPA で使うクエリ言語。SQL とよく似ているが、テーブル名・カラム名ではなく、エンティティ名・フィールド名で書く。JPA が実行時に SQL へ変換してくれるので、DB の種類（MySQL、PostgreSQL など）に依存しない。 

-- SQL：テーブル名 products、カラム名 created_at
SELECT * FROM products p WHERE p.price > 1000 ORDER BY p.created_at;

-- JPQL：エンティティ名 Product、フィールド名 createdAt
SELECT p FROM Product p WHERE p.price > 1000 ORDER BY p.createdAt

💻コード

以下の例では、次の Product エンティティを使う。

@Entity
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private Integer price;

    @Enumerated(EnumType.STRING)
    private ProductStatus status;  // ON_SALE / SOLD_OUT など

    private LocalDateTime createdAt;

    // getter / setter は省略
}

🔍 用語ノート: @Enumerated(EnumType.STRING)

enum 型のフィールドを DB に保存するとき、enum の名前（文字列）で保存するための指定。

保存される値の違い

public enum ProductStatus {
    ON_SALE,   // 販売中
    SOLD_OUT   // 売り切れ
}

status に ProductStatus.SOLD_OUT を入れて保存すると、DB の status カラムには次の値が入る。

指定DB に入る値中身
EnumType.STRING'SOLD_OUT'enum の名前（文字列）
EnumType.ORDINAL
（指定しない場合のデフォルト）		1enum の並び順（0 始まりの番号）

なぜ STRING を指定するのか

デフォルトの ORDINAL には、enum の並び順を変えるとデータが壊れるという問題がある。

public enum ProductStatus {
    PREPARING, // 準備中 ← 先頭に追加した
    ON_SALE,
    SOLD_OUT
}

DB に保存されている値が 1 の商品は、次のように読まれ方が変わる。

追加する前

0ON_SALE
1SOLD_OUT（売り切れ）
→

追加した後

0PREPARING
1ON_SALE（販売中）
2SOLD_OUT

💥 DB の値は 1 のままなのに、意味が「売り切れ」から「販売中」に変わる

売り切れの商品が、すべて販売中として扱われてしまう。しかもエラーは出ないので気づきにくい。

STRING なら DB には 'SOLD_OUT' という名前が入っているので、並び順を変えても影響を受けない。DB を直接見たときに値の意味がわかるのもメリット。実務では、ほぼ必ず EnumType.STRING を指定する。

⚠️ STRING でも注意すること

enum の名前を変えると（SOLD_OUT → OUT_OF_STOCK など）、DB に入っている既存のデータと一致しなくなる。名前を変えるときは、DB のデータも合わせて更新する必要がある。

1. クエリメソッド（メソッド名から自動生成）

public interface ProductRepository extends JpaRepository<Product, Long> {

    // name と status が両方一致する商品
    List<Product> findByNameAndStatus(String name, ProductStatus status);

    // price が指定した金額より高い商品
    List<Product> findByPriceGreaterThan(Integer price);

    // 登録日時が新しい順に先頭 10 件
    List<Product> findTop10ByOrderByCreatedAtDesc();
}

決められたルールでメソッド名を付けるだけで、Spring Data がメソッド名を解析してクエリを自動生成する。実装もクエリも書かなくてよい。

メソッド名の読み方

findByNameAndStatus は、次のように分解して読まれる。

  • findBy検索する
  • Namename が
  • Andかつ
  • Statusstatus が一致

生成されるクエリ（JPQL）のイメージ：

SELECT p FROM Product p WHERE p.name = ?1 AND p.status = ?2

メソッド名に書くのはエンティティのフィールド名。存在しないフィールド名を書くと、アプリの起動時にエラーになるので、間違いにすぐ気づける。

よく使うキーワード

メソッド名の中にキーワードを入れると、条件の種類が変わる（色付きの部分がキーワード）。

Containing
findByNameContaining(name)

name に指定した文字を含む

p.name LIKE %値%
StartingWith
findByNameStartingWith(name)

name が指定した文字で始まる

p.name LIKE 値%
IgnoreCase
findByNameIgnoreCase(name)

大文字・小文字を区別せずに一致

UPPER(p.name) = UPPER(値)
In
findByStatusIn(statusList)

status がリストのどれかに一致

p.status IN (値1, 値2, ...)
Between
findByPriceBetween(min, max)

price が min 以上 max 以下

p.price BETWEEN min AND max
IsNull
findByCreatedAtIsNull()

createdAt が null

p.createdAt IS NULL
OrderBy
findByStatusOrderByPriceAsc(status)

結果を price の昇順に並べる（降順は Desc）

ORDER BY p.price ASC

条件が多いときは @Query に切り替える

✗ 条件を全部メソッド名に詰め込む 
List<Product> findByNameContainingAndStatusAndPriceBetweenOrderByCreatedAtDesc(
        String name, ProductStatus status, Integer min, Integer max);

動きはするが、メソッド名が長すぎて何を検索しているのか読み取りにくい。目安として条件が 2〜3 個を超えたら、次の @Query で書く。

2. @Query（クエリを自分で書く）

public interface ProductRepository extends JpaRepository<Product, Long> {

    @Query("""
            SELECT p FROM Product p
            WHERE p.name LIKE %:keyword%
              AND p.status = :status
              AND p.price BETWEEN :minPrice AND :maxPrice
            ORDER BY p.createdAt DESC
            """)
    List<Product> search(@Param("keyword") String keyword,
                         @Param("status") ProductStatus status,
                         @Param("minPrice") Integer minPrice,
                         @Param("maxPrice") Integer maxPrice);
}

メソッド名は自由に付けられるので、search のように目的が伝わる短い名前にできる。クエリはテキストブロック（"""）で書くと、改行を入れて読みやすく書ける。

各要素の意味

1@Query で実行するクエリを指定する

@Query("SELECT p FROM Product p WHERE ...")
List<Product> search(...);

リポジトリのメソッドに @Query を付けると、メソッド名からの自動生成ではなく、書いたクエリがそのまま実行される。クエリメソッドと同じく、実装クラスは書かなくてよい。

  • メソッド名は自由に付けられる（命名ルールに縛られない）
  • クエリの書き間違い（存在しないフィールド名など）は、アプリの起動時にエラーになるので気づける

戻り値の型で、結果の受け取り方が決まる

戻り値の型結果
List<Product>複数件。0 件なら空のリスト
Optional<Product>1 件。0 件なら空の Optional
Page<Product>ページ単位（引数に Pageable を追加する）

2クエリ本体は JPQL で書く

SELECT p FROM Product p ... ORDER BY p.createdAt DESC
  • Product → エンティティ名（テーブル名 products ではない）
  • createdAt → フィールド名（カラム名 created_at ではない）

3名前付きパラメータで値を渡す

クエリの中
p.status = :status
↕同じ名前で対応
メソッドの引数
@Param("status") ProductStatus status

クエリ中の :status に、@Param("status") を付けた引数の値が入る。名前で対応づけるので、どの値がどこに入るかが一目でわかる。

✗ 番号で書く方法もあるが…
WHERE p.name = ?1 AND p.status = ?2
  • 引数の順番を入れ替えると壊れる
  • ?3 と書かれても、何の値か読み取りにくい

4LIKE %:keyword% で部分一致検索

p.name LIKE %:keyword%

Spring Data JPA 独自の書き方で、keyword の前後に % を付けた部分一致検索になる。

  • keyword に「ペン」を渡す → p.name LIKE '%ペン%' として実行
  • 「ボールペン」「ペンケース」など、「ペン」を含む商品がヒットする

SQL を直接書く（nativeQuery）

@Query(value = "SELECT * FROM products WHERE price > :price",
       nativeQuery = true)
List<Product> findExpensive(@Param("price") Integer price);

nativeQuery = true を付けると、JPQL ではなく SQL をそのまま DB に送って実行する。JPA による変換が入らないので、書いた SQL がそのまま動く。

1使うのは JPQL で書けないときだけ

基本は JPQL で書き、DB 固有の関数や構文を使いたいときだけ nativeQuery にする。たとえば PostgreSQL の ILIKE（大文字・小文字を区別しない LIKE）は JPQL にはないので、SQL で書く。

// PostgreSQL 専用：名前に keyword を含む（大文字・小文字を区別しない）
@Query(value = """
        SELECT * FROM products
        WHERE name ILIKE '%' || :keyword || '%'
        """,
       nativeQuery = true)
List<Product> searchByName(@Param("keyword") String keyword);

このほか、MySQL の全文検索（MATCH ... AGAINST）や、DBA がチューニングした SQL をそのまま使いたい場合などが該当する。

2注意点

  • 書き間違いが実行するまでわからない：テーブル名やカラム名のミスは、起動時ではなく、そのメソッドを呼んだときに初めてエラーになる。テストで必ず実行しておく
  • エンティティで受け取るなら全カラムを返す：戻り値を List<Product> にする場合、SELECT * のようにエンティティのフィールドに対応するカラムをすべて返す必要がある
  • DB の種類に依存する：開発は H2、本番は PostgreSQL のように DB が違うと、片方でしか動かないことがある

「全カラムを返す」の失敗例

✗ 一部のカラムだけ取得して、エンティティで受け取る 
@Query(value = "SELECT name, price FROM products",
       nativeQuery = true)
List<Product> findNameAndPrice();

// 実行するとエラー：
// 結果に id や status などのカラムがないため、Product を組み立てられない

エンティティは「全フィールドがそろった 1 行」として作られるので、カラムが 1 つでも足りないと実行時にエラーになる。

✓ 一部のカラムだけ欲しいなら、専用のインターフェースで受け取る 
// 欲しいカラムの getter だけを持つインターフェース
public interface ProductSummary {
    String getName();
    Integer getPrice();
}

@Query(value = "SELECT name, price FROM products",
       nativeQuery = true)
List<ProductSummary> findNameAndPrice();

カラム名と getter 名（name → getName()）が対応づけられ、取得した値だけを受け取れる。全部の項目が必要なら、SELECT * にしてエンティティで受け取る。

3. 更新・削除のクエリ（@Modifying）

条件に合うデータをまとめて更新・削除する。次の 2 つの手順で使う。

手順 1：リポジトリにクエリを定義する

public interface ProductRepository extends JpaRepository<Product, Long> {

    @Modifying(clearAutomatically = true)
    @Query("UPDATE Product p SET p.status = :status WHERE p.price < :price")
    int updateStatusByPriceLessThan(@Param("status") ProductStatus status,
                                    @Param("price") Integer price);
}

条件に合うデータを、1 回の UPDATE / DELETE 文でまとめて更新・削除できる。戻り値の int には、更新・削除された件数が入る。

手順 2：サービス層で、@Transactional を付けたメソッドから呼ぶ

@Service
public class ProductService {

    @Transactional  // ← このメソッド全体が 1 つのトランザクション
    public void closeCheapProducts() {
        // ① 安い商品を売り切れにする
        productRepository.updateStatusByPriceLessThan(
                ProductStatus.SOLD_OUT, 1000);

        // ② 操作の履歴を残す（ここで失敗すると①も取り消される）
        historyRepository.save(new History("安い商品を売り切れに変更"));
    }
}

各要素の意味

1@Modifying：データを書き換えるクエリだと伝える

@Modifying(clearAutomatically = true)

Spring Data は、@Query に書いたクエリを基本的に SELECT（取得）として実行する。@Modifying を付けると、UPDATE / DELETE として実行するように切り替わる。

  • 戻り値には、取得結果ではなく更新・削除された件数（int）が返る
  • 付け忘れると、SELECT として実行しようとして実行時にエラーになる

2clearAutomatically = true：実行後にキャッシュを空にする

@Modifying(clearAutomatically = true)

クエリの実行後に永続化コンテキストを空にする設定。永続化コンテキストとは、JPA が一度取得したエンティティを覚えておく一時的な置き場（キャッシュ）のこと。同じトランザクションの中で同じデータを取得すると、DB ではなくここから返される。

✗ 付けないと：置き場と DB の内容がずれる

@Query の UPDATE / DELETE は置き場を経由せず、DB を直接書き換える。そのため、すでに置き場にあるエンティティは古い値のまま残る。

次のように、ID を指定してステータスを更新するメソッドで確認する。

// リポジトリ：clearAutomatically を付けていない
@Modifying
@Query("UPDATE Product p SET p.status = :status WHERE p.id = :id")
int updateStatusById(@Param("id") Long id,
                     @Param("status") ProductStatus status);
@Transactional
public void example() {
    // ① 取得：status = ON_SALE が置き場に残る
    Product before = productRepository.findById(1L).orElseThrow();

    // ② DB を直接更新：DB 上は SOLD_OUT になる
    productRepository.updateStatusById(1L, ProductStatus.SOLD_OUT);

    // ③ 再取得：置き場から返るので、ON_SALE のまま！
    Product after = productRepository.findById(1L).orElseThrow();
}
✓ 付けると：DB から読み直す 
@Modifying(clearAutomatically = true)
@Query("UPDATE Product p SET p.status = :status WHERE p.id = :id")
int updateStatusById(@Param("id") Long id,
                     @Param("status") ProductStatus status);

②の実行後に置き場が空になるので、③では DB から取り直し、正しく SOLD_OUT が返る。

  • 同じトランザクションの中で、更新後にもう一度データを取得する処理があるときに付ける

3@Transactional：サービス層のメソッドに付ける

@Transactional
public void closeCheapProducts() { ... }

データの書き換えは、トランザクションの中で実行する必要がある。リポジトリには付けず、呼び出し元のサービス層のメソッドに付ける。

なぜサービス層に付けるのか

トランザクションは「ここからここまでを、全部成功か全部失敗にしたい」という範囲を決めるもの。その範囲は 1 つの業務処理と一致するので、業務処理を表すサービス層で決める。

  • 手順 2 のコードでは、商品の更新（①）と履歴の保存（②）がまとめて成功するか、まとめて取り消される。「商品は売り切れになったのに履歴がない」という中途半端な状態にならない
  • サービス層に付け忘れたまま呼ぶと、トランザクションがないため実行時にエラー（TransactionRequiredException）になる。付け忘れにすぐ気づける

4. 動的な検索条件（Specification）

なぜ必要か

検索画面のように「入力された条件だけで絞り込みたい」場合、ここまでの方法では対応しにくい。

✗ クエリメソッドで対応しようとする 
// 名前・ステータス・価格の 3 条件だと、入力の組み合わせは 8 通り
List<Product> findByName(String name);
List<Product> findByStatus(ProductStatus status);
List<Product> findByNameAndStatus(String name, ProductStatus status);
List<Product> findByNameAndPriceLessThanEqual(String name, Integer price);
// ... 組み合わせの数だけメソッドが必要になる

条件が増えるたびにメソッドが倍々で増え、Service 側にも「どれを呼ぶか」の分岐が必要になる。これを解決するのが Specification。条件を 1 つずつ部品にしておき、必要な部品だけをその場で組み合わせて検索できる。

下準備：JpaSpecificationExecutor を追加する

Specification を使って検索するには、リポジトリに JpaSpecificationExecutor を追加しておく必要がある。

public interface ProductRepository
        extends JpaRepository<Product, Long>,
                JpaSpecificationExecutor<Product> {
}

JpaSpecificationExecutor を継承すると、そこで定義されている findAll(Specification) などのメソッドが使えるようになる。

🔍 補足: <Product> という型パラメータ

<Product> は「どのエンティティを検索するか」を指定する型パラメータ。JpaRepository<Product, Long> と違って型パラメータが <T> の 1 つだけなのは、Specification を使った検索では ID を指定するメソッドがなく、ID の型を指定する必要がないから。

Specification とは

Specification は、検索条件を 1 つ表すインターフェース。@Query のようにクエリ全体を文字列で書くのではなく、条件を 1 つだけ Java のコードとして書く。

✗ @Query：クエリ全体を 1 つの文字列で書く 
@Query("SELECT p FROM Product p WHERE p.status = :status")
List<Product> findByStatus(@Param("status") ProductStatus status);

findByStatus は status が一致する商品を検索するメソッド。条件は @Query の文字列の中に直接書かれているので、「名前だけで検索したい」「価格だけで検索したい」のような別の条件を増やしたいときは、似たような検索メソッドをもう 1 つ作る必要がある。

✓ Specification：条件の部分だけを Java のメソッドにする 
// 定義：ProductSpecs クラスに条件を 1 つ生やす
public class ProductSpecs {
    public static Specification<Product> statusEquals(ProductStatus status) {
        return (root, query, cb) -> cb.equal(root.get("status"), status);
    }
}

// 呼び出し：クラス名 + メソッド名で、定義した条件を取り出して使う
Specification<Product> spec = ProductSpecs.statusEquals(ProductStatus.ON_SALE);
List<Product> products = productRepository.findAll(spec);

さっき追加した JpaSpecificationExecutor のおかげで、findAll(Specification) が使える。渡した条件に一致する商品だけが返ってくる。

ProductSpecs クラスの statusEquals を 3 つの部分に分けて見ると、それぞれの役割がわかる。

1戻り値の型：Specification<Product>

Product を検索するための条件を表す型。呼び出す側は、この戻り値をそのまま findAll に渡せば検索できる。

2引数：ProductStatus status

検索したい値を、ただのメソッド引数として受け取る。@Query（上の例）はクエリが文字列なので、:status と @Param("status") を名前で対応づける必要があった。Specification は条件も Java のコードなので、status をそのまま変数として使える。

3戻り値の中身：(root, query, cb) -> ...

これは、Specification が持つ toPredicate というメソッドを実装した部分。条件そのものを組み立てている部分で、ラムダ式だけを取り出すと次のようになる。

(root, query, cb) -> cb.equal(root.get("status"), status)

これは JPQL でいうと、次の色付きの部分に対応する。

SELECT p FROM Product p WHERE p.status = 'ON_SALE'

3 つの部分がそろうと、これは「status を受け取って、一致する条件を返すメソッド」になる。

toPredicate をもう少し詳しく

③ で出てきた toPredicate について。

  • 🧩
    Specification が持つ、唯一の抽象メソッド 下の「Specification が持つもの」も参照
  • 🔤
    英単語 predicate の意味 （真か偽かを判定する）命題・断定
  • 🔧
    やること root / query / cb を受け取り、Predicate（条件）に変換する
  • 📞
    呼び出されるタイミング 自分で直接呼び出すことはなく、findAll(spec) の実行時に JPA が裏側で呼び出す
SIGNATURE
Predicate toPredicate(Root<T> root, CriteriaQuery<?> query, CriteriaBuilder cb)

返ってきた Predicate を使って、SQL の WHERE 句が組み立てられる。

💡 なぜ @Override が付いていないのか

// 匿名クラスで書くと、こうなる
Specification<Product> spec = new Specification<Product>() {
    @Override
    public Predicate toPredicate(Root<Product> root, CriteriaQuery<?> query, CriteriaBuilder cb) {
        return cb.equal(root.get("status"), status);
    }
};
public static Specification<Product> statusEquals(ProductStatus status) {
    return (root, query, cb) -> cb.equal(root.get("status"), status);
}

Specification は、抽象メソッドが toPredicate だけの関数型インターフェース。候補が 1 つしかないので、Java は「このラムダ式 = toPredicate の実装」と迷わず判断できる。だから、メソッド名や型を書かなくても伝わり、@Override を付ける場所もなくなる。

もし抽象メソッドが 2 つあったら、どちらを実装したいのか Java には決められず、コンパイルエラーになる。

root, query, cb が何なのか

📌 root / query / cb は自分で用意しなくてよい

findAll(spec) を実行すると、Spring Data（JPA）がこの 3 つを自動的に用意して、ラムダ式に渡してくれる。new したり、自分で組み立てたりする必要は一切ない。

それぞれ、JPQL の次の部分に対応する。

root：検索対象を指す「変数」

JPQL で FROM Product p と書いたときの p にあたる。これから検索する Product そのものを指している。

root.get("status") // JPQL でいう p.status

root.get("フィールド名") で、そのフィールドを指定できる。

cb（CriteriaBuilder）：条件を作る道具箱

💬 英単語の criteria は「判断や評価の基準」という意味（単数形は criterion）。CriteriaBuilder は、その基準＝条件を組み立てるための道具箱、という名前。

equal（一致）、like（部分一致）、greaterThan（より大きい）など、条件の種類ごとにメソッドが用意されている。

cb.equal(root.get("status"), ProductStatus.ON_SALE) // JPQL でいう p.status = 'ON_SALE'
  • 1 つ目の引数（root.get("status")）＝ 比べる対象
  • 2 つ目の引数（ProductStatus.ON_SALE）＝ 比べる値

この 2 つを cb.equal に渡すと、「status が ON_SALE かどうかを判定する条件」が 1 つできあがる。この条件のことを Predicate と呼ぶ。

具体的には…

  • 商品の status が ON_SALE → この Predicate は true
  • 商品の status が SOLD_OUT → この Predicate は false

この Predicate が、そのまま toPredicate の戻り値になる。

query（CriteriaQuery）：クエリ全体の設定

WHERE 以外の部分、たとえば重複を除く DISTINCT や、並び替えの ORDER BY を設定したいときに使う。単純な条件だけなら、ほとんど使わない。

query.distinct(true) // JPQL でいう SELECT DISTINCT p ...

💬 補足: ORDER BY は query ではなく Sort / Pageable で渡すのが一般的。並び替えは条件（WHERE）とは別の関心ごとなので、query.orderBy() で Specification の中に書き込むことは実務ではあまりしない。代わりに、findAll の Sort / Pageable 引数で渡す。

Sort sort = Sort.by(Sort.Direction.DESC, "createdAt"); productRepository.findAll(spec, sort);

つまり、root でどのフィールドを見るかを指定し、cb でどう判定するかを組み立てる、という役割分担になっている。query は特別な設定をしたいときだけ使う。

Specification が持つもの

Specification はインターフェースなので、フィールドは持たない。自分で実装するのは toPredicate だけだが、条件どうしを組み合わせるためのメソッドが、あらかじめ用意されている。

toPredicate(...)抽象メソッド

自分で実装する唯一のメソッド。条件の中身を書く

(root, query, cb) -> cb.equal(root.get("status"), status)
and(other)default

この条件と other を AND でつなぐ

Specification.where(nameContains) .and(statusEquals)
or(other)default

この条件と other を OR でつなぐ

Specification.where(nameContains) .or(statusEquals)
not(spec)static

条件を否定する

Specification.not(statusEquals) // status が一致 "しない" 商品
where(spec)static

1 つの条件から書き始めるときの入口

Specification.where(nameContains) // ここから and / or でつなげていく
allOf(spec, ...)static

複数の条件をまとめて AND でつなぐ

Specification.allOf( nameContains, statusEquals)
anyOf(spec, ...)static

複数の条件をまとめて OR でつなぐ

Specification.anyOf( nameContains, statusEquals)

条件を 1 つずつつなぐ and と、まとめてつなぐ allOf は、どちらも同じ結果になる。条件の数が決まっていない動的な検索では、allOf の方がすっきり書ける。

複数の条件を組み合わせて検索する

ここまでを踏まえて、「入力された条件だけで絞り込む」検索を実際に作ってみる。

① 条件を 1 つずつ部品として定義する

public class ProductSpecs {

    // 名前に keyword を含む（未入力なら条件なし）
    public static Specification<Product> nameContains(String keyword) {
        return (root, query, cb) -> keyword == null
                ? null
                : cb.like(root.get("name"), "%" + keyword + "%");
    }

    // ステータスが一致する（未入力なら条件なし）
    public static Specification<Product> statusEquals(ProductStatus status) {
        return (root, query, cb) -> status == null
                ? null
                : cb.equal(root.get("status"), status);
    }

    // 価格が maxPrice 以下（未入力なら条件なし）
    public static Specification<Product> priceAtMost(Integer maxPrice) {
        return (root, query, cb) -> maxPrice == null
                ? null
                : cb.lessThanOrEqualTo(root.get("price"), maxPrice);
    }
}

statusEquals を例に、中身を詳しく見る。

return (root, query, cb) -> status == null
        ? null                                    // 未入力 → 条件を作らず null を返す
        : cb.equal(root.get("status"), status);   // 入力あり → 条件を作る
status == null

条件を作らず、null をそのまま返す

→ 絞り込みなし（この条件は無視される）
status != null

cb.equal(...) で実際の条件（Predicate）を作る

→ status = 入力値 で絞り込む

🔍 具体例で確認する

「ステータスだけ選んで検索した」場合（name と maxPrice は未入力）で見てみる。

⊘ nameContains(null) → null 条件なし
✅ statusEquals(ON_SALE) → status = 'ON_SALE' 条件あり
⊘ priceAtMost(null) → null 条件なし

Specification.allOf(...) は、null になった条件を無視して組み立てる。そのため、実際に実行される WHERE 句は次のようになる。

WHERE status = 'ON_SALE'

name と maxPrice の条件は、最初から無かったものとして扱われる。これが「入力された条件だけで絞り込む」の実現方法。

② Service で、さっきの allOf を使って組み合わせる

public List<Product> search(ProductSearchForm form) {
    Specification<Product> spec = Specification.allOf(
            ProductSpecs.nameContains(form.keyword()),
            ProductSpecs.statusEquals(form.status()),
            ProductSpecs.priceAtMost(form.maxPrice()));

    return productRepository.findAll(spec);
}

Specification.allOf で、すべての条件を AND でつなぐ。条件が増えても、部品を 1 つ追加して allOf に足すだけで済む。
