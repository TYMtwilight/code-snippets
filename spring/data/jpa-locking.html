排他制御（楽観ロックと悲観ロック）

  • 📅 作成日: 2026-10-10
  • 🔄 更新日: 2026-10-10

🎯概要

排他制御とは、同じデータを 2 人が同時に更新したときに、片方の更新が消えてしまうのを防ぐ仕組み。

JPA には 2 つのやり方がある。

楽観ロック

ロックを掛けずに更新し、衝突したら失敗させる。エンティティに @Version を付けるだけ。

悲観ロック

先に DB の行をロックして、他のトランザクションを待たせる。リポジトリに @Lock を付ける。

ふだん使うのは楽観ロック。悲観ロックは、在庫の引き当てのようにどうしても待たせたい場面に限って使う。

🔍 用語ノート: 在庫の引き当て

注文が入ったときに、「この在庫はこの注文のぶん」と確保しておく処理のこと。出荷するより前に押さえておかないと、同じ商品を他の注文にも売ってしまう。

そのため在庫は、ふつう 3 つの数で管理する。

呼び方意味
実在庫倉庫に物理的にある数
引当済数すでに注文に割り当てた数
引当可能数実在庫 − 引当済数（これから売れる数）

排他制御の例としてよく挙がるのは、「引当可能数を読む → 足りるか判断する → 引き当てる」が一続きでないと破綻するから。残り 1 個を 2 人が同時に読むと、どちらも「買える」と判断してしまう。

💻コード

1. 何も対策しないと起きること

在庫 10 個の商品に対して、2 人が同時に注文処理をしたとする。

時刻ユーザー Aユーザー BDB の在庫
①在庫を読む → 1010
②在庫を読む → 1010
③2 個減らして保存 → 88
④3 個減らして保存 → 77

合計 5 個売れたのに、在庫は 7 になっている。B が保存したのは「10 から 3 引いた 7」であって、A が減らした 2 個は上書きされて消えてしまっている。

🔍 用語ノート: ロストアップデート

このように、後から保存したほうが先の更新を上書きしてしまう現象を「ロストアップデート（更新の喪失）」と呼ぶ。排他制御は、まずこれを防ぐための仕組み。

2. 楽観ロック（@Version）

エンティティに @Version を付けたフィールドを 1 つ用意する。これだけで有効になる。

@Entity
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private int stock;

    @Version
    private Long version;   // アプリからは触らない
}

何が起きるのか

更新時の SQL に、where 句でバージョンの一致チェックが付く。そして新しいバージョンに +1 される。

update products set stock = 7, version = 2 where id = 1 and version = 1

先に A が保存すると、DB のバージョンは 2 に上がる。あとから B が保存しようとしても、B が持っているのは古い 1 なので、where 句に一致する行が無い。

時刻ユーザー Aユーザー BDB の version
①読む（version 1）1
②読む（version 1）1
③保存 → 成功2
④保存 → 更新 0 件 → 例外2

JPA は更新件数が 0 件だったことを検知して、ObjectOptimisticLockingFailureException を投げる。トランザクションはロールバックされるので、B の更新はなかったことになる。

📌 「楽観」の意味

衝突はめったに起きないと楽観して、ロックを掛けずに進む。そのかわり、保存の瞬間に衝突が判明したら失敗させる、という考え方。待ちが発生しないので、ふつうの更新処理はこれで足りる。

ObjectOptimisticLockingFailureException とは

Spring が用意している非検査例外。名前のとおり「楽観ロックに失敗した」ことを表す。次の階層に属する。

RuntimeException
  └ DataAccessException                           … データアクセス全般の失敗
      └ ConcurrencyFailureException               … 同時実行による失敗
          └ OptimisticLockingFailureException     … 楽観ロックの失敗
              └ ObjectOptimisticLockingFailureException

📌 catch するなら親の型で

Spring のドキュメントやサンプルでは、1 つ上の OptimisticLockingFailureException で受けることが多い。JPA 以外の実装に替わっても同じ catch で拾えるため。

どちらで受けても動作は変わらないので、迷ったら親のほうで受けておく。

⚠️ 投げられるのは、メソッドを抜けたあと

バージョンの照合が走るのは、永続化コンテキストの内容が DB に書き出されるとき。つまり多くの場合はトランザクションのコミット時、メソッドを抜けた直後になる。

そのため、更新処理の内側で try-catch しても捕まらない。

✗ 中で捕まえようとする：ここは通らない 
@Transactional
public void updateStock(Long id, int stock) {
    try {
        Product product = productRepository.findById(id).orElseThrow();
        product.setStock(stock);
    } catch (OptimisticLockingFailureException e) {
        // UPDATE はまだ発行されていないので、ここには来ない
    }
}   // ← トランザクションのコミットはここ。例外が出るのもここ
✓ 呼び出し側で捕まえる 
try {
    productService.updateStock(id, stock);        // この中でコミットされる
} catch (OptimisticLockingFailureException e) {
    // 衝突したときの処理
}

version フィールドの扱い

  • アプリからは一切触らない：値を入れるのも増やすのも JPA の仕事。setter で書き換えてはいけない
  • 型は Long / Integer など：日時型（Instant など）も使えるが、整数が無難
  • 新規登録時は 0 から始まる：null のまま save() すれば JPA が設定する

3. 衝突したときにどうするか

例外を捕まえたあとの扱いは、処理の性質で変わる。

✓ 画面操作なら、やり直してもらう 
try {
    productService.updateStock(id, newStock);
} catch (OptimisticLockingFailureException e) {
    return "他のユーザーが更新しました。最新の内容を確認してください。";
}
✓ バッチや内部処理なら、取り直して再実行 
@Retryable(
        retryFor = OptimisticLockingFailureException.class,
        maxAttempts = 3)
@Transactional
public void decreaseStock(Long id, int count) {
    Product product = productRepository.findById(id).orElseThrow();
    product.setStock(product.getStock() - count);
}
✗ 自前のループをトランザクションの中に書く 
@Transactional
public void decreaseStock(Long id, int count) {
    for (int i = 0; i < 3; i++) {
        try {
            Product product = productRepository.findById(id).orElseThrow();
            product.setStock(product.getStock() - count);
            return;
        } catch (OptimisticLockingFailureException e) {
            // 同じトランザクション・同じ永続化コンテキストのままなので、
            // 何度繰り返しても結果は変わらない
        }
    }
}

やり直しは、新しいトランザクションで始める

リトライで重要なのは、1 回ごとに別のトランザクションになっていること。失敗したトランザクションの中でそのまま繰り返しても、次の 2 つの理由で必ず失敗する。

  • ロールバックが確定している：一度例外が出たトランザクションは「ロールバックするしかない」状態になる。中で何をしてもコミットできない
  • 古いエンティティが残っている：永続化コンテキストは version = 1 のエンティティを覚えたまま。もう一度 findById() しても、SQL は発行されず同じ古いインスタンスが返る

つまり、リトライがトランザクションの外側にある必要がある。

リトライ（@Retryable）

1 回目のトランザクション

読む（version 1）→ 保存例外 → ロールバック

2 回目のトランザクション（新しい永続化コンテキスト）

読み直す（version 2）→ 保存成功

2 回目は永続化コンテキストが作り直されるので、findById() で最新のバージョンを読み直せる。だからやり直しが意味を持つ。

💬 @Retryable と @Transactional を同じメソッドに付けた場合、Spring Retry は既定でトランザクションより外側に入るため、この形で問題ない。

4. 悲観ロック（@Lock）

読むときに、DB の行そのものをロックしてしまう方法。リポジトリのメソッドに @Lock を付ける。

public interface ProductRepository extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select p from Product p where p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);
}

発行される SQL に for update が付き、他のトランザクションはこの行を読めずに待たされる。

select p.id, p.stock, ... from products p where p.id = 1 for update
時刻ユーザー Aユーザー B
①ロックして読む
②読もうとする → 待たされる
③更新してコミット
④待ち解除 → 更新後の値を読む

B は A の結果を見てから処理を始めるので、そもそも衝突しない。

⚠️ トランザクションの中でしか意味がない

ロックが解放されるのはトランザクションの終了時。つまり @Transactional の付いたメソッドの中で、ロックして読む → 更新するまで済ませる必要がある。

また、待っている間はスレッドが止まる。ロックしている区間はできるだけ短く保つ。

ロックモードの種類

PESSIMISTIC_WRITE

読み書きとも他を待たせる。ふつうはこちら。

select ... for update
PESSIMISTIC_READ

他の読み取りは許すが、更新は待たせる。

select ... for share

待ち時間の上限を決める

相手の処理が長いと、延々と待ち続けてしまう。@QueryHints でタイムアウト（ミリ秒）を指定できる。

@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints({
        @QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000")
})
Optional<Product> findByIdForUpdate(@Param("id") Long id);

時間内にロックを取れなければ PessimisticLockingFailureException になる。

5. どちらを使うか

楽観ロック悲観ロック
仕組み保存時にバージョンを照合読む時点で行をロック
待ち発生しない発生する
衝突したら例外 → やり直しそもそも衝突しない
向く場面衝突がまれな通常の更新在庫引き当て、座席予約
注意点やり直しの導線が必要デッドロック、性能低下

まず楽観ロックを既定にする。@Version を付けておくだけで、気づかないうちに更新が消える事故は防げる。

悲観ロックを選ぶのは、衝突が頻繁で、やり直しが現実的でない場面。残り 1 個の在庫を奪い合うような処理では、毎回リトライさせるより待たせたほうが素直になる。

6. 落とし穴

1一括更新クエリはバージョンを上げない

@Modifying の UPDATE は SQL を直接発行するので、version 列は変わらない。他の人が持っている古いエンティティが、そのまま保存できてしまう。

update Product p set p.stock = 0  →  version はそのまま

バージョンも一緒に上げるなら、クエリに明示的に書く。

update Product p set p.stock = 0, p.version = p.version + 1

2画面をまたぐ編集では version を持ち回る

編集画面を開いてから保存するまでの間は、トランザクションが切れている。表示時のバージョンを画面に埋め込んで、保存時に送り返す必要がある。

<input type="hidden" name="version" value="1">

送られてきたバージョンをエンティティに載せて保存すれば、画面を開いている間に他の人が更新していた場合に検知できる。

3読むだけの処理にはロックは要らない

排他制御が要るのは読んだ値をもとに更新する処理。一覧表示や検索に @Lock を付けると、待ちが増えるだけで得るものがない。
