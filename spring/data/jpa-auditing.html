監査（Auditing）

  • 📅 作成日: 2026-10-10
  • 🔄 更新日: 2026-10-10

🎯概要

監査（Auditing）とは、「いつ・誰が作ったか／更新したか」を自動で記録する仕組み。

エンティティにアノテーションを付けておくと、保存のたびに Spring Data が値を埋めてくれる。アプリ側で setUpdatedAt(...) を書く必要がなくなる。

付けるアノテーションは、役割の違う 2 種類に分かれる。

① クラスに @EntityListeners(AuditingEntityListener.class)「保存のときに値を埋める処理を呼んでほしい」というスイッチ。エンティティ 1 つにつき 1 回
② フィールドに下の 4 つ「このフィールドに何を入れるか」の指定。必要なものだけ選んで付ける 
@Entity
@EntityListeners(AuditingEntityListener.class)   // ① スイッチ
public class Product {

    @LastModifiedDate                            // ② 入れる値の指定
    private LocalDateTime updatedAt;
}

②だけ付けても値は入らない。①と②がそろって初めて動くという関係になっている。

@CreatedDate

作成日時

@LastModifiedDate

最終更新日時

@CreatedBy

作成者

@LastModifiedBy

最終更新者

💻コード

1. 手で書くと何が困るのか

日時の記録は、自分で書こうとすると更新処理のすべてに同じ 1 行が必要になる。

✗ 更新するたびに書く 
@Transactional
public void rename(Long id, String newName) {
    Product product = productRepository.findById(id).orElseThrow();
    product.setName(newName);
    product.setUpdatedAt(LocalDateTime.now());   // 毎回これを書く
}

書き忘れてもコンパイルは通るし、テストも落ちない。気づくのは、あとから更新日時を見たときになる。監査の機能を使えば、この 1 行自体が不要になる。

2. 有効にする 2 ステップ

1 設定クラスに @EnableJpaAuditing を付けるアプリ全体で 1 回だけ
2 エンティティに @EntityListeners を付ける値を埋める処理を呼んでもらうため 
@Configuration
@EnableJpaAuditing   // 1. アプリ全体で 1 回だけ
public class JpaConfig {
}
@Entity
@EntityListeners(AuditingEntityListener.class)   // 2. 値を埋める処理を呼んでもらう
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}

⚠️ @EntityListeners を書き忘れると、黙って null になる

@EntityListeners(AuditingEntityListener.class) は、保存の前後に処理を差し込むための宣言。これが無いと値を埋める処理そのものが呼ばれないので、@CreatedDate を付けていても列は空のままになる。

insert into product (name, created_at, updated_at) values ('ノート', null, null)

例外も警告も出ないため、気づくのは後から DB を見たときになる。

3. いつ値が入るのか

値が設定されるのは、DB に書き出される直前。save() を呼んだ瞬間ではなく、INSERT / UPDATE の発行前になる。

新 新規登録のときcreatedAt と updatedAt の両方に、同じ時刻が入る
更 更新のときupdatedAt だけが書き換わる。createdAt はそのまま

ダーティチェッキングによる更新（save() を呼ばないケース）でも、同じように updatedAt は更新される。DB に UPDATE が飛ぶなら必ず働く、と考えてよい。

📌 @Column(updatable = false) も付けておく

@CreatedDate が付いていれば Spring Data は作成日時を書き換えないが、アプリの他の場所から setter で上書きされることは防げない。updatable = false を付けておくと、UPDATE 文の対象から外れるので安全になる。

@CreatedDate
@Column(updatable = false)   // UPDATE 文に含めない
private LocalDateTime createdAt;

@LastModifiedDate            // 更新のたびに書き換わるので不要
private LocalDateTime updatedAt;

4. 複数のエンティティで使い回す

同じ 4 つのフィールドを全エンティティに書くのは無駄なので、親クラスにまとめて継承する。

親クラス 
@MappedSuperclass                              // 表にはならず、列の定義だけ子に配る
@EntityListeners(AuditingEntityListener.class)   // ここに書けば子クラスでは不要
public abstract class BaseEntity {

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    // getter
}
子クラス 
@Entity
public class Product extends BaseEntity {// 監査用の記述は一切なし

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
}

@MappedSuperclass とは

「テーブルにはならないが、フィールドの定義を子クラスに配る」ためのアノテーション。親クラスは設計図の共通部分でしかなく、実体を持つのは子クラスだけになる。

ピンクの列が、親クラスから配られたもの

押さえておくのは次の 3 点。

✓ @Entity は付けない親クラス自身はテーブルにならないので、base_entity という表は存在しない
✓ 列は子クラスごとに作られるproduct にも orders にも、同じ created_at 列ができる
✗ 親クラスの型では検索できないBaseEntity を指す表が無いため、JpaRepository<BaseEntity, Long> や JPQL の from BaseEntity は使えない

💬 共通の親テーブルを作って親の型でまとめて検索したい場合は、@MappedSuperclass ではなく @Entity + @Inheritance を使う。監査用の共通フィールドを配るだけなら @MappedSuperclass で十分。

5. 「誰が」を記録する（AuditorAware）

日時と違って、作成者はアプリにしか分からない。そのため、現在のユーザーを返す実装を 1 つ用意する。

💬 auditor は「監査する人」という意味の英単語。ただしここでは検査する側ではなく、監査ログに名前が載る側を指すので、「操作している本人」と読むと実態に合う。AuditorAware は「その人を知っているもの」。

AuditorAware の実装 
@Component
public class SpringSecurityAuditorAware implements AuditorAware<String> {

    @Override
    public Optional<String> getCurrentAuditor() {
        Authentication auth = SecurityContextHolder.getContext()
                .getAuthentication();

        if (auth == null || !auth.isAuthenticated()) {
            return Optional.empty();   // 未ログインなら記録しない
        }
        return Optional.of(auth.getName());
    }
}

このクラスは誰が呼ぶのか

自分のコードからは一度も呼ばない。保存のたびにフレームワーク側から呼ばれる。「誰が」だけはアプリ固有の事情なので、そこを埋める穴として開けられている。

1 save() で監査処理が走るSpring Data が AuditorAware 型の Bean を探して呼ぶ
2 getCurrentAuditor() が値を返す今ログインしているユーザーの ID
3 @CreatedBy のフィールドに入る戻り値がそのまま created_by 列に書かれる

見つけてもらうために必要なのは、次の 2 つだけ。クラス名は自由に付けてよい。

@Component

Bean として登録する。これが無いと探されない。

AuditorAware<String>

この型が目印になる。<String> は記録する値の型。

💬 SecurityContextHolder は、Spring Security が現在のリクエストのログイン情報を置いている場所。auth.getName() がログイン ID にあたる。

📌 なぜ getCurrentAuditor() の戻り値が Optional なのか

Optional<String> getCurrentAuditor()

バッチ処理や起動時のデータ投入など、ログインしていない状態で保存が走ることがある。そのため「記録する人がいない」を表せるようになっている。

  • Optional.empty() を返す → その列は null のまま。エラーにはならない
  • チェックを省いて auth.getName() を呼ぶ → auth が null で NullPointerException

Spring Security を使っていないなら、Optional.of("system") と固定値を返すだけの実装でも成立する。

あとはエンティティ側に @CreatedBy / @LastModifiedBy を足せば、保存のたびにこのメソッドが呼ばれて値が入る。

親クラス（4 項目そろった形） 
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    @CreatedBy                      // ここから追加
    @Column(updatable = false)
    private String createdBy;

    @LastModifiedBy
    private String updatedBy;

    // getter
}

型は何にするか

String

ログイン ID をそのまま持つ。単純で、ユーザーが削除されても残る。

User エンティティ

リレーションとして持つ。氏名などを辿れるが、結合が増える。

Bean が複数あるとき

AuditorAware の実装が 1 つなら、Spring Data が型で自動的に見つけるので何も要らない。複数あるときだけ、どれを使うかを Bean 名で指定する。

@EnableJpaAuditing(auditorAwareRef = "springSecurityAuditorAware")

ここに入るのはクラスのパスではなく Bean 名。名前は定義のしかたで決まる。

定義のしかたBean 名
@Component を付けたクラスクラス名の先頭を小文字にしたもの（springSecurityAuditorAware）
@Component("auditor")auditor
@Bean メソッドメソッド名

💬 存在しない名前を書くと起動時に落ちるので、タイプミスには気づける。

6. 落とし穴

1一括更新クエリでは働かない

@Modifying を付けた UPDATE は SQL を直接発行するため、エンティティを経由しない。監査の処理も呼ばれないので、更新日時は古いままになる。

update Product p set p.status = 'SOLD_OUT'  →  updated_at は変わらない

必要なら、クエリの中に明示的に書く。

update Product p set p.status = 'SOLD_OUT', p.updatedAt = :now

2時刻はアプリのサーバーで決まる

値を決めるのはアプリが動いているマシンの時計。DB 側のタイムゾーン設定は関係ない。

アプリの時計 → created_at ／ DB の CURRENT_TIMESTAMP は使われない
LocalDateTime か Instant か

問題が起きるのは、時計の基準が複数あるとき。台数そのものではない。

LocalDateTime

地域の情報を持たない。「サーバーの TZ = 見たい地域」という前提で成り立つ。

Instant

UTC の一点を指す。前提が要らないので、環境が変わってもずれない。

次のどれかに当てはまるなら Instant にしておく。型を差し替えるだけで、他の記述は変わらない。

  • アプリサーバーが複数台あり、時計やタイムゾーンがそろっていない
  • 環境で TZ が変わる（ローカルは JST、本番コンテナは UTC）
  • DB や他システムが入れた値と比較する
private Instant createdAt;

🔍 Instant にすると、日本語表記にする手間が増えないか

Instant は地域の情報を持たないので、「どの地域で見るか」を渡す必要がある。増えるのは withZone の 1 行。

private static final DateTimeFormatter JP =
        DateTimeFormatter.ofPattern("yyyy年M月d日 H:mm")
                         .withZone(ZoneId.of("Asia/Tokyo"));   // 増えるのはここだけ

JP.format(product.getCreatedAt());   // 2026年10月10日 14:30

フォーマッタは定数にして使い回すので、書く場所は 1 箇所で済む。

LocalDateTime にこの行が要らないのは、変換が不要だからではない。サーバーの TZ をそのまま使っているだけなので、前提が崩れてもずれに気づけない。

そもそもこの変換が必要なのは、サーバー側で表示まで作るとき（画面の HTML 生成、CSV や PDF の出力）だけ。REST API なら Instant をそのまま返せばよい。

// Jackson が ISO-8601 に変換してくれる
public record ProductResponse(Long id, String name, Instant createdAt) {}

// {"id":1,"name":"ノート","createdAt":"2026-10-10T05:30:00Z"}

どの地域の時刻で見せるかは見る人によって変わるので、サーバーで決め打ちせず、UTC で返してクライアント側で表示を変換するのが素直な設計になる。

3テストで時刻を固定したい

「作成日時が期待どおりか」を検証したい場合は、時刻を供給する担当である DateTimeProvider を差し替えて固定できる。

public interface DateTimeProvider {
    Optional<TemporalAccessor> getNow();   // 監査処理はここから現在時刻を受け取る
}

テスト用に、固定値を返す実装を Bean として登録する。

@TestConfiguration
@EnableJpaAuditing(dateTimeProviderRef = "fixedDateTimeProvider")
public class FixedDateTimeConfig {

    @Bean
    public DateTimeProvider fixedDateTimeProvider() {   // メソッド名が Bean 名になる
        LocalDateTime fixed = LocalDateTime.of(2026, 1, 1, 0, 0);
        return () -> Optional.of(fixed);
    }
}
  • dateTimeProviderRef に渡すのはBean 名。@Bean メソッドの名前がそのまま一致する
  • 返す型はエンティティのフィールドと合わせる。Instant のフィールドに LocalDateTime を返すと実行時に失敗する
  • 本番の設定にある @EnableJpaAuditing を、テスト側のこの設定で上書きする形になる

あとはテスト側でこの設定を読み込めば、固定した時刻がそのまま検証できる。

@DataJpaTest
@Import(FixedDateTimeConfig.class)   // 時刻を固定した設定を読み込む
class ProductAuditingTest {

    @Autowired
    private ProductRepository productRepository;

    @Test
    void 作成日時に固定した時刻が入る() {
        Product saved = productRepository.saveAndFlush(new Product("ノート"));

        assertThat(saved.getCreatedAt())
                .isEqualTo(LocalDateTime.of(2026, 1, 1, 0, 0));
    }
}

💬 @DataJpaTest は設定クラスを読み込まないので、@Import が必要。これが無いと監査そのものが働かず、createdAt は null になる。

💬 DateTimeProvider はメソッドが 1 つだけのインターフェースなので、implements したクラスを作らずラムダで書ける。処理が数行以上になるならクラスにした方が読みやすい。AuditorAware も単一メソッドなので同じく、固定値を返すだけならラムダで足りる。

@Bean AuditorAware<String> auditorAware() { return () -> Optional.of("system"); }

4変更履歴は残らない

記録されるのは最後に更新した日時と人だけ。「いつ何がどう変わったか」をすべて残したい場合は、Hibernate Envers のような履歴テーブルを作る仕組みが必要になる。
