🎯概要

「商品はカテゴリに属する」といったエンティティどうしの関係をアノテーションで表したものが、リレーション。リレーションを定義しておくと、product.getCategory() のようにメソッドを呼ぶだけで、リレーションの先にあるデータを取り出せる。

ただし、この便利さには見えない SQL が裏で走るという代償がある。product.getCategory() は、カテゴリをまだ読み込んでいなければその場で SELECT を 1 回発行して取りに行く。ただのメソッド呼び出しに見えて、中では DB アクセスが起きている。

商品 1 件を表示するだけなら、増えるのは 1 回だけなので問題にならない。困るのは、この呼び出しがループの中に入ったとき。

// 商品を 20 件取得する
List<Product> products = productRepository.findAll();

for (Product p : products) {
    // この 1 行が、商品 1 件につき 1 回ずつ SELECT を発行する
    System.out.println(p.getCategory().getName());
}

getCategory() は呼ばれるたびに SELECT を 1 回出すので、ループが 20 周すれば 20 回になる。最初の findAll() と合わせて 1 + 20 = 21 回。商品が 1000 件なら 1001 回になる。これが N+1 問題（→「4. N+1 問題」）。

Java のコードは「取得 1 回」と「ループ 1 つ」にしか見えず、SQL はどこにも書かれていない。そのぶん回数が増えたことに気づけないのが、この問題の厄介なところ。だからリレーションは、書き方とパフォーマンスをセットで覚える必要がある。

いちばんよく使うのは @ManyToOne と @OneToMany の組み合わせ。

@Entity
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // 多くの商品が、1 つのカテゴリに属する
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "category_id")
    private Category category;
}

@Entity
@Table(name = "categories")
public class Category {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // 1 つのカテゴリが、多くの商品を持つ
    @OneToMany(mappedBy = "category")
    private List<Product> products = new ArrayList<>();
}

リレーションのアノテーションはフィールドに付ける

リレーションは「どのフィールドが、どの相手と繋がっているか」という情報なので、相手のエンティティを持つフィールドの上に付ける。クラスの上には付けない。

public class Product {

    // カテゴリとのリレーション
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "category_id")
    private Category category;

    // メーカーとのリレーションは、別のフィールドに付ける
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "maker_id")
    private Maker maker;
}

1 つのクラスが category と maker のように複数のリレーションを持つこともあるため、クラス単位では表現できない。フィールドごとに付けるからこそ、リレーションを何本でも持てる。

アノテーション付けるフィールド意味
@ManyToOne相手を 1 つ持つフィールド（Category category）この商品は、このカテゴリに属する
@OneToMany相手の一覧を持つフィールド（List<Product> products）このカテゴリは、これらの商品を持つ
@JoinColumn@ManyToOne と同じフィールド外部キーのカラム名を指定する

💬 補足: mappedBy や cascade、fetch は独立したアノテーションではなく、@OneToMany などの属性。属性が多いときは改行して書くこともあるが、1 行で書いた場合と意味は同じ。

@JoinColumn：リレーションを持つカラムを指定する

Java と DB では、リレーションの持ち方が違う。同じ「ボールペンは文房具カテゴリ」という事実が、両者ではこう分かれる。

JAVA 側

Product インスタンス name = "ボールペン" category → Category インスタンス

カテゴリそのものを持っている

DB 側

products の 1 行 name = 'ボールペン' category_id = 3

カテゴリの id という数字だけを持っている

この違いは、カテゴリ名を取り出すコードにそのまま表れる。

Java 
// オブジェクトをたどるだけでよい
product.getCategory().getName();
SQL 
-- id を手がかりに、自分で JOIN する
SELECT c.name
FROM products p
JOIN categories c ON c.id = p.category_id
WHERE p.id = 1;

Java のコードに JOIN は 1 文字も出てこないが、裏では JPA が上の SQL を組み立てて実行している。

このとき JPA が知らないといけないのは、「products テーブルのどのカラムが外部キーか」の 1 点だけ。@JoinColumn は、この外部キーのカラム名を伝えている。

Java 
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "category_id")
private Category category;

ここで name に書いたカラム名が、JPA が組み立てる SQL の ON c.id = p.category_id の部分になる。

書く場所は外部キーを持つ側、つまり @ManyToOne が付いたフィールド。Category 側に書くものではない。

📌 省略できるが、書いておくほうがよい

省略すると「フィールド名 + _ + 参照先の主キー名」になる。この例では category_id なので、書かなくても結果は同じ。

  • 書いておけば、コードだけでカラム名がわかる
  • 命名の規則は設定で変えられるので、省略に頼ると壊れやすい
  • nullable = false など、他の指定もここでできる

中間テーブルに「数量」「登録日」などの属性を持たせる必要が出てくることが多いが、@ManyToMany では中間テーブルに追加のカラムを持たせられないため。

2. 双方向のリレーションと mappedBy

片方向と双方向

リレーションは片側だけでも成立する。外部キーを持つ Product に @ManyToOne と @JoinColumn を書けば、それだけで product.getCategory() からカテゴリを辿れる。これが片方向。

@Entity
public class Product {

    @ManyToOne
    @JoinColumn(name = "category_id")   // リレーションを保持する外部キーカラム
    private Category category;
}

さらに Category 側にも、@OneToMany(mappedBy = "category") を付けた products フィールドを持たせると、category.getProducts() で逆方向にも辿れるようになる。このように両方のエンティティから相手を辿れる状態を、双方向のリレーションと呼ぶ。

@Entity
public class Category {

    @OneToMany(mappedBy = "category")   // Product 側の category フィールドと対応
    private List<Product> products = new ArrayList<>();
}

💬 補足: 双方向は便利に見えるが、両側を管理する手間が増える。「カテゴリから商品一覧を取りたい」という要件がなければ、片方向のままで十分。

どちらの変更を DB に反映するのか

双方向にすると、Java と DB で「リレーションの数」が合わなくなる。

JAVA 側

Product category → Category
Category products → List<Product>

お互いが相手を知っている（参照は 2 つ）

DB 側

products テーブル category_id = 3
categories テーブル 商品を指すカラムは無い

片方しか相手を知らない（リレーションは 1 つ）

ポイントは Category 側。Java では category.getProducts() で商品の一覧を持っているのに、categories テーブルには商品を指すカラムが 1 つも無い。DB でリレーションを保持しているのは、products テーブルの category_id だけ。

この違いは、商品の所属カテゴリを変えるときに問題になる。いま「雑貨」カテゴリ（misc）に入っているボールペンを、「文房具」カテゴリ（stationery）に移すとしよう。この1 つの処理が、参照が 2 つあるせいで2 通りに書けてしまう。

// ボールペン
Product product = productRepository.findById(1L).orElseThrow();

// 移動元の「雑貨」と、移動先の「文房具」
Category misc = categoryRepository.findByName("雑貨").orElseThrow();
Category stationery = categoryRepository.findByName("文房具").orElseThrow();

// ① Product 側の参照を差し替える
product.setCategory(stationery);

// ② Category 側のリストを入れ替える
misc.getProducts().remove(product);
stationery.getProducts().add(product);

どちらも Java 上は「カテゴリを変更した」ように見える。しかし DB で書き換えるのは products.category_id というたった 1 つのカラム。

もし ① と ② に違う内容を書いたら、JPA は category_id をどちらに合わせればいいか決められない。

そこで JPA は、外部キーを持つ側（所有者）の参照だけを見て DB を更新する仕組みになっている。ここでは category_id を持つ Product が所有者。

所有者 = 外部キー（category_id）を持つクラス = Product
Product（所有者）Category（所有者ではない側）
書き方@ManyToOne@OneToMany(mappedBy = "category")
外部キー持っている（category_id）持っていない
DB への反映この側の変更だけが反映される反映されない（読み取り用）

mappedBy は「所有者のどのフィールドでマッピングされているか」を示す

mappedBy は「〜によってマッピングされている」という意味。@OneToMany(mappedBy = "category") は、Category 側の「このリレーションをマッピングしているのは Product の category フィールドであって、私ではない」という申告。

// ── 所有者：外部キーを持つ ──
@Entity
public class Product {

    @ManyToOne
    @JoinColumn(name = "category_id")
    private Category category;          // ← mappedBy が指しているフィールド
}

// ── 所有者ではない側：外部キーを持たない ──
@Entity
public class Category {

    @OneToMany(mappedBy = "category")   // ← Product.category の "category"
    private List<Product> products = new ArrayList<>();
}

所有者そのものは、外部キーを持つかどうかですでに決まっている（→ 前の項目）。mappedBy はそれを決めるのではなく、その所有者がどのフィールドかを指し示すだけ。

なぜフィールド名だけで特定できるのか

mappedBy に書いたのは "category" というフィールド名だけで、クラス名はどこにもない。JPA は2 つの情報を組み合わせて特定している。

① どのクラスか

ジェネリクスの型から決まる

List<Product> products
② どのフィールドか

mappedBy の文字列から決まる

mappedBy = "category"

この 2 つから、Product クラスの category フィールドだと決まる。

💬 補足: 書くのはカラム名（category_id）ではなくフィールド名（category）。文字列なのでフィールド名を変えてもコンパイルエラーにならず、起動時に初めて失敗する。

書き忘れると保存場所が 2 つできる

mappedBy が無いと、JPA は Product.category と Category.products を別々の 2 つのリレーションと解釈し、それぞれに保存場所を用意してしまう。

✓ mappedBy あり：保存場所は 1 つ 
products テーブル
  id | name | price | category_id    ← リレーションはここだけ
✗ mappedBy なし：保存場所が 2 つに分かれる 
products テーブル
  id | name | price | category_id    ← Product 側のリレーション

category_products テーブル           ← JPA が勝手に作る「中間テーブル」
  category_id | products_id          ← Category 側のリレーション

「どの商品がどのカテゴリに属するか」という同じ情報が 2 か所に保存されることになる。しかも更新されるタイミングが別々で、product.setCategory(...) は products.category_id を、category.getProducts().add(...) は中間テーブルを書き換える。

⚠️ 片方しか書かなければ 2 つの内容が食い違い、どちらが正しいのか分からなくなる。

やりがちな失敗：所有者ではない側を更新する

双方向にすると、同じリレーションを表すフィールドが 2 つできる（product.category と category.products）。このうち DB に反映されるのは所有者の product.category だけ。

✗ 所有者ではない側に追加する 
category.getProducts().add(product);
// product.getCategory() は null のまま
// → DB の category_id も更新されない

メモリ上のリストは更新されるが、DB は更新されない。所有者の product.category が null のままだからで、この追加はトランザクションが終わるとなかったことになる。

しかも例外は 1 つも出ない。category.getProducts() に商品は入っているので、その場では成功したように見える。

リレーションを変えるときは、必ず所有者のフィールド（product.setCategory(...)）を更新する。

所有者だけ更新すればよいわけではない

DB に保存するだけなら、所有者を更新すれば足りる。

// 「文房具」カテゴリを DB から読み込む
Category stationery = categoryRepository.findById(3L).orElseThrow();

// ボールペンのカテゴリを差し替える
product.setCategory(stationery);

ただしこれを呼んでも、すでに読み込まれている stationery.getProducts() の中身は古いままになる。この 2 つは別々のフィールドなので、片方を書き換えても、もう片方が連動して変わることはない。

やりたいこと：ボールペンを「雑貨」から「文房具」に移す

product.setCategory(stationery)
↓ 更新されるのは片方だけ ↓
所有者

カテゴリを取り直せば DB の内容が反映されるものの、同じトランザクションの中で stationery.getProducts() を使うと、移したはずのボールペンが入っていない。この食い違いでも例外は出ないため、気づきにくい。

リレーションを変えるときは、両方のフィールドを更新する必要がある。

所有者
product.category DB を更新するため
所有者ではない側
category.products 手元のオブジェクトを更新するため

両方のフィールドをまとめて更新するメソッドを用意する

呼び出す場所で 2 行書いてもよい。

// カテゴリを設定するたびに、この 2 行をセットで書く
product.setCategory(stationery);
stationery.getProducts().add(product);

ただし、カテゴリを設定する処理はアプリの中に何か所も現れる（商品の新規登録、カテゴリの変更、CSV の取り込みなど）。そのすべてで 2 行をセットで書く必要がある。1 か所でも片方を忘れれば、ここまで見てきた食い違いが起きる。setCategory() を忘れれば DB に保存されず、getProducts().add() を忘れれば手元のリストが古いままになる。

そこで、この 2 行をエンティティのメソッドにまとめる。呼ぶ側は 1 行だけになり、書き忘れようがなくなる。

両側に書くと無限ループになる

このメソッドは、どちらか一方のクラスにだけ置く。Category と Product の両方に書くと、こうなる。

✗ 2 つのメソッドが互いを呼び合う 
public class Category {

    public void addProduct(Product product) {
        products.add(product);
        product.setCategory(this);      // ← Product 側を呼ぶ
    }
}

public class Product {

    public void setCategory(Category category) {
        this.category = category;
        category.addProduct(this);      // ← また Category 側を呼ぶ
    }
}

category.addProduct(product) を呼ぶと、2 つのメソッドが延々と呼び合う。

category.addProduct(product)
  → product.setCategory(category)
      → category.addProduct(product)
          → product.setCategory(category)
              → ...  （終わらない）

呼び出しが積み上がりすぎて StackOverflowError で落ちる。

Category.addProduct に任せるなら、Product.setCategory はフィールドに代入するだけにしておく。

メソッドを置くのは、所有者ではない側（Category）

理由：リストは Category の持ち物だから

products リストは Category の private フィールド。つまりCategory クラスの中からしか直接触れない。同じ処理でも、どちらのクラスに書くかで中身がこう変わる。

✓ Category に置く 
public void addProduct(Product product) {

    // 自分のリストなので、そのまま操作できる
    products.add(product);

    // 相手には、公開されたメソッドで頼む
    product.setCategory(this);
}

💬 product.setCategory(this) の this は、いま addProduct() が呼ばれている Category インスタンス自身。stationery.addProduct(ボールペン) と呼べば this は stationery なので、「このボールペンのカテゴリは文房具です」とセットしていることになる。

✗ Product に置く 
public void setCategory(Category category) {

    // 自分のフィールドなので、そのまま代入できる
    this.category = category;

    // 相手のリストを取り出して、中身を書き換える
    category.getProducts().add(this);
}

どちらが「カプセル化」を守れているか

カプセル化とは、オブジェクトの中身を外から直接いじらせず、公開されたメソッド経由でだけ操作させるという考え方。

  • Category に置く場合：自分のリストは直接操作し、Product には setCategory() という公開された入口から頼む。どちらも正式な手段で操作している
  • Product に置く場合：getProducts() でリストそのものを外に持ち出して、その中身を書き換える。Category から見れば、知らないうちに自分のリストが変えられている

後者は壊れやすい。getProducts() が変更できないリストを返すように直されただけで、Product 側の add() は例外になる。

リストの管理は、持ち主の Category に任せる。

更新メソッドの書き方

追加用と削除用を対で用意する。どちらも中身は 2 行で、「自分のリストを操作する」＋「相手のフィールドを更新する」をセットで行う。

category.addProduct(product)

1
products.add(product) 自分のリストに相手を入れる
2
product.setCategory(this) 相手のフィールドに自分をセットする

category.removeProduct(product)

1
products.remove(product) 自分のリストから相手を外す
2
product.setCategory(null) 相手のフィールドを null に戻す

「自分」は category、「相手」は引数の product

名前は addProduct / removeProduct のように、リストに何が入るのかが分かる形にしておく。

@Entity
public class Category {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @OneToMany(mappedBy = "category")
    private List<Product> products = new ArrayList<>();

    // 両側の参照をまとめて更新するメソッド
    public void addProduct(Product product) {
        products.add(product);          // 自分のリストに追加
        product.setCategory(this);      // 相手にも自分をセットする
    }

    public void removeProduct(Product product) {
        products.remove(product);       // 自分のリストから外す
        product.setCategory(null);      // 相手の参照も外す
    }
}

カテゴリに商品を追加する

addProduct を呼ぶだけ。

@Transactional
public void addToCategory(Long productId, Long categoryId) {

    Product product = productRepository.findById(productId).orElseThrow();
    Category category = categoryRepository.findById(categoryId).orElseThrow();

    category.addProduct(product);
}

カテゴリから商品を外す

removeProduct を呼ぶ。商品の category は null になる。

@Transactional
public void removeFromCategory(Long productId, Long categoryId) {

    Product product = productRepository.findById(productId).orElseThrow();
    Category category = categoryRepository.findById(categoryId).orElseThrow();

    category.removeProduct(product);
}

💬 補足: category_id が NOT NULL のカラムなら、外した時点で保存に失敗する。どのカテゴリにも属さない商品を許すのかを決めたうえで使う。

商品を別のカテゴリに移す

外してから入れる。removeProduct と addProduct を組み合わせる。

@Transactional
public void moveToCategory(Long productId, Long newCategoryId) {

    Product product = productRepository.findById(productId).orElseThrow();
    Category newCategory = categoryRepository.findById(newCategoryId).orElseThrow();

    // 今のカテゴリから外す
    Category current = product.getCategory();
    if (current != null) {
        current.removeProduct(product);
    }

    // 新しいカテゴリに入れる
    newCategory.addProduct(product);
}

リレーションでつながった相手を、いつ取りに行くかの設定。

EAGER

使わなくても取得してしまう
LAZY

必要なときだけ SQL が走る

EAGER：商品を取る時点でカテゴリも取る Java

@ManyToOne(fetch = FetchType.LAZY)

実行される SQL 
Product product = productRepository.findById(1L).get();

@ManyToManyLAZY

4. N+1 問題

リレーションを扱ううえでパフォーマンス面でいちばん重要な問題。「商品を 20 件取得して、それぞれのカテゴリ名を表示する」という処理で見ていく。

List<Product> products = productRepository.findAll();   // 商品 20 件

for (Product p : products) {
    System.out.println(p.getCategory().getName());      // カテゴリ名を使う
}

一見 1 回の取得に見えるが、実際に発行される SQL はこうなる。

SELECT * FROM products;                     -- ① 商品の取得（1 回）

SELECT * FROM categories WHERE id = 1;      -- ② 1 件目のカテゴリ
SELECT * FROM categories WHERE id = 2;      -- ② 2 件目のカテゴリ
SELECT * FROM categories WHERE id = 3;      -- ② 3 件目のカテゴリ
-- ... 商品の数だけ繰り返される
合計 1 + 20 = 21 回（商品が 1000 件なら 1001 回）

N+1 問題の名前の由来は、このクエリの内訳。

  • 1 … 商品を N 件まとめて取る、最初の SELECT
  • N … リレーション先のカテゴリを取りに行く SELECT。商品 1 件ごとに category_id をもとに categories テーブルへ問い合わせるため、商品の件数だけ繰り返される

つまり、本体を取る 1 回とリレーション先を取る N 回で N+1 回。件数が増えるほど悪化するため、テストデータが少ないうちは気づきにくい。

対策

やり方は 3 つある。いずれも「カテゴリをまとめて取ってくる」ことで追加クエリを減らす。

JOIN FETCH

JPQL を自分で書く。細かく制御できる

@EntityGraph

アノテーションを付けるだけ。いちばん手軽

batch_fetch_size

設定 1 行でアプリ全体に効く。個別の対策が漏れたときの保険になる

対策① JOIN FETCH：JPQL に書く

JOIN FETCH は「JOIN した先のエンティティも一緒に読み込む」という JPQL の書き方。@Query で指定する。

public interface ProductRepository extends JpaRepository<Product, Long> {

    @Query("SELECT p FROM Product p JOIN FETCH p.category")
    List<Product> findAllWithCategory();
}

呼び出し側のコードは変わらない。

List<Product> products = productRepository.findAllWithCategory();

for (Product p : products) {
    System.out.println(p.getCategory().getName());   // 追加の SQL は走らない
}

発行される SQL は 1 回だけ。カテゴリのカラムも同じ結果セットに含まれる。

SELECT p.*, c.*
FROM products p
JOIN categories c ON c.id = p.category_id;

💬 補足: 上の書き方ではカテゴリ未設定（category_id が NULL）の商品が結果から落ちる。全件ほしいなら LEFT JOIN FETCH を使う。

対策② @EntityGraph：アノテーションで指定する

Repository のメソッドに @EntityGraph を付け、一緒に取りたいリレーションを attributePaths に並べる。JPQL を書かなくても、リレーション先のエンティティまで取得できる。

findByPriceLessThan のようにメソッド名から自動でクエリが作られるもの（メソッド名クエリ）にも付けられる。

💬 用語: グラフとは、Product → Category、Product → Maker のようにエンティティが参照でつながった構造のこと。@EntityGraph は、そのどこまでを一緒に読み込むかを指定する。

public interface ProductRepository extends JpaRepository<Product, Long> {

    @EntityGraph(attributePaths = "category")
    List<Product> findAll();                       // 継承した findAll を上書き

    @EntityGraph(attributePaths = "category")
    List<Product> findByPriceLessThan(int price);  // メソッド名クエリにも付けられる
}

発行される SQL は LEFT JOIN になる（デフォルトで NULL も残る）。

SELECT p.*, c.*
FROM products p
LEFT JOIN categories c ON c.id = p.category_id;

リレーションが複数あるときは配列で並べ、ネストした先は . でつなぐ。

@EntityGraph(attributePaths = {"category", "maker", "category.parent"})
List<Product> findAll();

category.parent は、カテゴリがさらに親カテゴリを持っている場合（Category に @ManyToOne Category parent がある構成）に、そこまで一緒に読み込むという指定。商品 → カテゴリ → 親カテゴリ と 2 段たどることになる。

対策③ batch_fetch_size：設定でまとめ取りする

個別の対策ではなく、アプリ全体の既定の振る舞いを変える方法。LAZY のリレーションを取りに行くとき、1 件ずつではなく IN 句でまとめて取るようになる。

# application.properties
spring.jpa.properties.hibernate.default_batch_fetch_size=100

💬 用語: hibernate.default_batch_fetch_size は、LAZY のリレーションを取りに行くとき、何件ぶんまとめて取るかの既定値。default は「エンティティごとに @BatchSize で個別指定しなければ、これを使う」という意味。

コードは元のまま何も変えない。

List<Product> products = productRepository.findAll();

for (Product p : products) {
    System.out.println(p.getCategory().getName());
}

1 件目のカテゴリに触れた時点で、残りの商品の分もまとめて取りに行く。

SELECT * FROM products;                              -- ① 商品の取得

SELECT * FROM categories WHERE id IN (1, 2, 3, 4);   -- ② まとめて 1 回
-- 20 回が 1 回に減る（100 件ずつまとめるので、未取得が 100 件を超えたら複数回）

💬 補足: JOIN FETCH や @EntityGraph と違い、SQL は 2 回に分かれる（本体＋リレーション）。ただし件数に比例して増えないので N+1 は解消される。

5. コレクションの JOIN FETCH とページングは併用しない

ここまでの例は「商品 → カテゴリ」（@ManyToOne）だった。これを逆向きにして、「カテゴリ → 商品」（@OneToMany のコレクション）を JOIN FETCH しながらページングすると、落とし穴がある。一見きちんと動くのに、裏側では全件がメモリに読み込まれてしまう。

原因は「件」と「行」の数え方の違い。ここだけ押さえれば理解できるので、順を追って見ていく。

前提：ページングは SQL の LIMIT でやっている

PageRequest.of(0, 10) と書くと、Spring Data JPA は DB にこう投げる。

SELECT * FROM categories LIMIT 10 OFFSET 0;

LIMIT 10 の意味は「結果の先頭 10 行をください」。ここが重要で、LIMIT が数えているのはエンティティの件数ではなく、結果の行数。

JOIN しなければ、この 2 つは一致する。

categories テーブル
idname
1文房具1 行 = カテゴリ 1 件
2書籍1 行 = カテゴリ 1 件
3家電1 行 = カテゴリ 1 件

1 行がそのままカテゴリ 1 件なので、LIMIT 10 はきちんと「カテゴリ 10 件」になる。

JOIN すると「1 件 = 複数行」になる

ところが JOIN FETCH c.products を付けると、商品の数だけカテゴリの行が複製される。

文房具はカテゴリとしては 1 件なのに、結果は 3 行。「件」と「行」がずれてしまった。

だから LIMIT が使えない

このずれた結果に LIMIT 2 を付けると、返ってくるのは先頭 2 行だけ。

JOIN した結果に LIMIT を付けると、エンティティ単位ではなく行単位で切られてしまう

カテゴリは 1 件しか取れず、しかもその getProducts() は本当は 3 件あるのに 2 件しか返さない。嘘のデータを返すエンティティができてしまう。

Hibernate の逃げ道：全件読んでメモリで切る

壊れたデータを返すわけにはいかないので、Hibernate は LIMIT を使うのをあきらめる。代わりにこう動く。

  1. LIMIT を付けずに全件を SELECT する
  2. Java 側で全部をエンティティに組み立てる
  3. そこから10 件を切り出して返す
-- LIMIT / OFFSET が付かない
SELECT c.*, p.*
FROM categories c
LEFT JOIN products p ON p.category_id = c.id;   -- 全行を取得

返ってくる結果は正しい。問題は、1 ページ 10 件が欲しいだけなのに、カテゴリが 10 万件あれば 10 万件すべてをメモリに読み込むこと。開発中はデータ件数が少ないため問題なく動くが、データが増えた本番環境で初めてメモリ不足に陥る。

6. LazyInitializationException

LAZY を使っていると必ず一度は踏む例外。「あとで取りに行く」と言っていたリレーションを、取りに行けなくなった状態で発生する。

何の例外か

Hibernate 独自の実行時例外。検査例外ではないので throws もコンパイルエラーも出ない

org.hibernate.LazyInitializationException
いつ出るか

LAZY にしたカテゴリの中身を、トランザクションの外で使おうとしたとき。商品自身の product.getName() は手元にあるので動くが、カテゴリを読みに行った瞬間に失敗する

product.getCategory().getName()
✗ 例外になるコード 
// Service
public Product find(Long id) {
    return productRepository.findById(id).orElseThrow();
}   // ← ここでトランザクションが終わる

// Controller
Product product = service.find(1L);

product.getName();                 // ✅ OK
product.getCategory().getName();   // 💥 LazyInitializationException

同じ product なのに、商品名は取れてカテゴリ名は取れない。この差がどこから来るのかを 3 ステップで追っていく。

ステップ① LAZY は「引換券」だけを渡している

前提として、エンティティ側はこう書かれているものとする。@ManyToOne は既定が EAGER なので、明示的に LAZY を指定している。

@Entity
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @ManyToOne(fetch = FetchType.LAZY)   // ← 既定は EAGER なので明示する
    @JoinColumn(name = "category_id")
    private Category category;
}

この状態で商品を 1 件取得すると、発行される SQL は products への 1 本だけ。カテゴリの中身はまだ読んでいない。

SELECT * FROM products WHERE id = 1;   -- categories への SQL は走らない

では product.getCategory() には何が入っているのか。中身が空のまま、プロキシと呼ばれる「あとで取りに行くための引換券」が入っている。

Product product = productRepository.findById(1L).orElseThrow();
// product.name     → すでに手元にある値
// product.category → 引換券（プロキシ）だけ。中身は空っぽ

product.getCategory().getName();
// 中身に触った瞬間、引換券を使って DB に取りに行く

ステップ② 引換券が使えるのは、トランザクションの間だけ

引換券を使って DB に取りに行くには、SQL を投げるための窓口が必要になる。この窓口の役割を担っているのが EntityManager（永続化コンテキストとも呼ばれる）。そして EntityManager は、トランザクションが終わると一緒に閉じられる。

ここで「@Transactional をどこにも書いていないのに、なぜトランザクションが始まったり終わったりするのか」という疑問が出てくる。答えは、自分で書かなくても JpaRepository の実装クラスに最初から付いているから。

// Spring Data JPA 内部の実装（抜粋・イメージ）
@Repository
@Transactional(readOnly = true)      // ← クラス全体に付いている
public class SimpleJpaRepository<T, ID> implements JpaRepository<T, ID> {

    @Override
    public Optional<T> findById(ID id) { ... }

    @Transactional                   // ← 更新系は読み取り専用を外してある
    @Override
    public <S extends T> S save(S entity) { ... }
}

そのため @Transactional を書かない場合、トランザクションの範囲は「リポジトリのメソッド 1 回分」だけになる。findById から戻ってきた時点でコミットされて閉じるので、Service のメソッドを抜けるより前に窓口は閉じている。

// Service（@Transactional なし）
public Product find(Long id) {

    return productRepository.findById(id).orElseThrow();
    // ├ findById に入るとトランザクション開始
    // └ findById から戻るとコミットして終了 ← ここで窓口が閉じる
}

窓口が開いている範囲は、設定によって次のように変わる。

ここで見落としやすいのが 2 段目。@Transactional を Service に付けると窓口は Service を抜けるまで開くが、Controller はその外側にある。つまり範囲を広げただけでは解決しない。

// Service
@Transactional(readOnly = true)
public Product find(Long id) {
    Product product = productRepository.findById(id).orElseThrow();

    product.getCategory().getName();   // ✅ ここなら取れる（窓口が開いている）

    return product;
}                                      // ← ここで窓口が閉じる

// Controller
Product product = service.find(1L);
product.getCategory().getName();       // 💥 ここは外。やはり例外になる

エンティティを return で外に渡しても、引換券が使える状態まで一緒に付いてくるわけではない。トランザクションが終わった瞬間に、その product は detached になる。

ステップ③ 窓口が閉じたエンティティは「切り離された」状態になる

トランザクションを抜けた product は detached（切り離された） と呼ばれる状態。すでに読み込んだ値は使えるが、引換券はもう使えない。

// Controller（トランザクションの外）
Product product = service.find(1L);

product.getName();                  // ✅ 手元にある値を返すだけ
product.getCategory().getName();    // 💥 引換券を使おうとしたが窓口が閉まっている

getCategory().getName() は 1 回ごとに DB アクセスが必要なので、ループ 1 周ごとに接続を借りて返すことになる。

1 周目: 接続を借りる → SELECT → コミット → 接続を返す
2 周目: 接続を借りる → SELECT → コミット → 接続を返す
...
（1000 周 = 接続の取得と返却が 1000 回）

SQL の回数は N+1 と同じでも、中身はもっと悪い。

トランザクション内の N+1接続を勝手に開く場合
SQL の回数1 + 1000 回1 + 1000 回
接続の取得1 回（使い回す）1000 回
プールが枯渇すれば他のリクエストが待たされる
同じカテゴリの再取得起きない
一度読んだものはキャッシュされる		毎回起きる
毎回まっさらな状態から読み直す

そして何より、コードを読んでも気づけない。

String categoryName = product.getCategory().getName();
// この 1 行が DB アクセスだとは、コードから読み取れない

例外は制約ではなく、隠れた DB アクセスを表に出すための仕組み。黙って動くと、どこで何回 SQL が走っているか追えなくなる。

対策

解決策は 2 つだけ。引換券を残さないか、引換券を外に出さないかのどちらか。

対策やっていること
JOIN FETCH / @EntityGraphトランザクションの中でカテゴリも一緒に読んでおく（引換券を残さない）
DTO に詰め替えるトランザクションの中で必要な値だけ取り出しておく（引換券を外に出さない）

ひとつめは JOIN FETCH / @EntityGraph。N+1 問題の対策とまったく同じもの（→ 4. N+1 問題）で、商品を取るときにカテゴリも一緒に読み込んでしまう。

✓ 最初からカテゴリも読んでおく Repository 
public interface ProductRepository extends JpaRepository<Product, Long> {

    @EntityGraph(attributePaths = "category")
    Optional<Product> findById(Long id);
}
Controller 
Product product = service.find(1L);
product.getCategory().getName();   // ✅ すでに読み込まれているので例外にならない

カテゴリの中身が最初から入っているため、引換券そのものが残らない。トランザクションの外で触っても DB に行く必要がないので例外にならない。

注意点は、@EntityGraph が「このメソッドではこのリレーションを取る」と Repository 側で固定する仕組みだということ。呼び出す画面によって必要なリレーションが違う場合、1 つのメソッドで全部読み込むと無駄が出る。

// ✗ 全部のリレーションを読み込むメソッドを 1 つだけ用意した場合
@EntityGraph(attributePaths = {"category", "maker", "tags"})
Optional<Product> findById(Long id);

// → 商品名とカテゴリ名しか表示しない画面でも、
//   maker と tags まで JOIN されて取得されてしまう

そのため、画面（用途）ごとにメソッドを分けるのが基本になる。

@EntityGraph(attributePaths = "category")
Optional<Product> findWithCategoryById(Long id);              // 一覧画面用

@EntityGraph(attributePaths = {"category", "maker", "tags"})
Optional<Product> findWithAllRelationsById(Long id);          // 詳細画面用

💬 デメリット: 呼び出し側が何を使うかを、Repository 側で先に決めておく必要がある。

実務でよく使うのは DTO への詰め替え。@Transactional を自分で付けてトランザクションの範囲を Service 全体に広げ、その中で必要な値を取り出してしまう。

✓ トランザクションの中で DTO に詰め替える 
@Transactional(readOnly = true)           // ← 範囲を Service 全体に広げる
public ProductDto find(Long id) {
    Product product = productRepository.findById(id).orElseThrow();
    // findById はこのトランザクションに相乗りするだけなので、まだ閉じない

    return new ProductDto(
        product.getName(),
        product.getCategory().getName()   // ✅ 窓口が開いているので取れる
    );
}                                         // ← ここで初めて終了

ポイントは、Controller に渡るのがエンティティではなく ProductDto になること。DTO の中身は取り出し済みの String だけで、プロキシはどこにも入っていない。

DTO 
public record ProductDto(String name, String categoryName) {}
Controller 
ProductDto dto = service.find(1L);

dto.name();           // ✅ ただの String
dto.categoryName();   // ✅ ただの String。DB には行かない

// dto.getCategory() ← そんなメソッドは存在しないので、呼ぼうとしてもコンパイルエラー

つまり Controller には引換券が一枚も渡らない。getCategory() を呼ぶ手段がないので、例外が起きる余地そのものがなくなるのがこの対策の要点。

💬 デメリット: 例外は起きなくなるが、SQL の回数は減らない。詰め替えはトランザクションの中で動くので、product.getCategory().getName() は普通に SELECT を発行する。一覧処理では件数ぶん繰り返され、N+1 になる。

実務では、まず DTO への詰め替えで例外が起きない形にする。そのうえで件数が多く、性能が問題になりそうな処理だけ @EntityGraph を足す。

先に DTO にしておけば例外は構造的に起きなくなるので、@EntityGraph はあとから必要な場所にだけ足せる。逆の順番だと、画面を変えるたびに例外が出ないか確かめることになる。

なぜ手元の環境では例外が出ないのか

Spring Boot では spring.jpa.open-in-view の初期値が true で、これは画面の描画が終わるまで窓口を開いたままにする設定（上の図の 3 段目）。そのため Controller でも getCategory() が動いてしまい、この例外に遭遇しないことがある。

# application.properties
spring.jpa.open-in-view=false

ただし true のままだと、リクエストの処理が終わるまでずっと DB 接続を握り続ける。アクセスが増えると接続が枯渇するため false にするのが推奨で、その場合は上記の対策が必須になる。

例外が出るのに、なぜ LAZY のままにするのか

「トランザクションの外で取りに行けないなら、最初から EAGER にすればいいのでは」と思えるが、LAZY のままにしておくほうが得。理由は 3 つ。

1大半の処理はトランザクションの中で完結する

例外が出るのは「エンティティをトランザクションの外に持ち出したとき」だけ。Service の中で処理を終えるコードなら、LAZY でも問題なく動く。

@Transactional(readOnly = true)
public int calcTotal(Long id) {
    Order order = orderRepository.findById(id).orElseThrow();

    return order.getItems().stream()      // ← トランザクション内なので取りに行ける
        .mapToInt(OrderItem::getSubtotal)
        .sum();
}

2EAGER は使わないデータまで毎回取ってくる

例外は消えるが、代わりに常に遅くなるという交換になる。

// 商品名の一覧を表示するだけの処理
List<Product> products = productRepository.findAll();   // 1000 件

for (Product p : products) {
    System.out.println(p.getName());   // カテゴリは一切使わない
}
// EAGER だと、ここで使わないカテゴリも全件取りに行く（N+1 問題も発生する）

3EAGER はあとから減らせないいちばん重要

LAZY は既定が最小なので、必要な場面だけ足していける。EAGER はその逆ができない。

設定取得量を増やす取得量を減らす
LAZYJOIN FETCH / @EntityGraph でクエリごとに足せる既定が最小なので不要
EAGER不要（常に取る）クエリごとに外せない

LAZY なら、画面ごとに必要なぶんだけ取るメソッドを用意できる。

@EntityGraph(attributePaths = "category")
List<Product> findAllForDetailView();   // カテゴリも要る画面

List<Product> findAll();                // 商品名だけの画面（カテゴリは取らない）

EAGER にしてしまうと、後者のような「軽く取りたい」クエリが書けなくなる。@EntityGraph で EAGER を LAZY に上書きすることは原則できない。

7. cascade

cascade と、次のセクションで扱う orphanRemoval は、どちらも「親エンティティを操作したとき、子をどうするか」を決める設定。@OneToMany などの属性として書く。

  • cascade … 親への操作（保存・削除など）を子にも伝える
  • orphanRemoval … 親のリストから外された子を削除する（→ 8. orphanRemoval）

書く場所は @OneToMany の括弧の中。mappedBy と並べて指定する。ここでは「注文（Order）と注文明細（OrderItem）」を例にする。

@Entity
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(mappedBy = "order",
               cascade = CascadeType.ALL,   // ← 親への操作を子にも伝える
               orphanRemoval = true)        // ← 外された子を削除する
    private List<OrderItem> items = new ArrayList<>();
}
属性書かなかったとき（既定）よく使う指定
cascade何も伝わらないCascadeType.ALL（保存・削除などをすべて伝える）
orphanRemovalfalse（外しても消えない）true

この 2 行を足すと、親を操作するだけで、子もあわせて変更される。子を 1 件ずつ保存したり削除したりするコードが要らなくなる。

orderRepository.save(order);      // 明細も一緒に INSERT される
orderRepository.delete(order);    // 明細も一緒に DELETE される
order.getItems().remove(item);    // 外した明細だけ DELETE される

親に対して行った操作を、そのまま子にも適用するという指定。何を伝えるかは CascadeType で選ぶ。

CascadeType伝わる操作
PERSIST親を保存すると、子も保存される
MERGE親の変更を反映すると、子の変更も反映される
REMOVE親を削除すると、子も削除される
REFRESH / DETACH再読み込み・切り離しが子にも及ぶ
ALL上記すべて

以降では、cascade を付けていないと何が起きるかを、保存と削除のそれぞれで見ていく。

① 保存：子が保存されない

親に明細を 2 件持たせて保存してみる。

Order order = new Order();
order.addItem(new OrderItem("ボールペン", 2));
order.addItem(new OrderItem("ノート", 1));

orderRepository.save(order);

このコードで INSERT されるのは、orders テーブルの 1 行だけ。order_items テーブルには 1 行も入らない。

Java 上では order.getItems() に明細が 2 件入っているのに、DB にはその 2 件がどこにも残らない。しかも例外は出ないので、保存は成功したように見える。

理由は、@OneToMany(mappedBy = "order") が外部キーを持たない側だから（→ 2. 双方向のリレーションと mappedBy）。

JPA が Order の items リストを見るのは読み取るときだけで、中身が増えても DB には反映しない。

そのため、明細も保存したいなら自分で 1 件ずつ保存する必要がある。

orderRepository.save(order);                  // ① 親を保存

for (OrderItem item : order.getItems()) {
    orderItemRepository.save(item);            // ② 子を 1 件ずつ保存
}

この書き方には 2 つの問題がある。

✗保存漏れが起きやすい 明細を扱うすべての処理で書く必要がある
✗書き忘れても例外が出ない 注文だけ保存され、成功したように見える

CascadeType.ALL（または PERSIST）を付ければ、orderRepository.save(order) の 1 行だけで明細も一緒に保存される。

② 削除：子が取り残される

orders テーブル
idordered_at

order_items テーブル

明細側の order_id = 1 が「どの注文の明細か」を保持している。ここで親の行だけを消すと、この参照先が消えてしまう。

DELETE FROM orders WHERE id = 1;

この結果は、DB に外部キー制約が設定されているかどうかで変わる。

外部キー制約起きること
ある（通常はこちら）DB が削除を拒否してエラーになる。「まだ参照している行があるので消せない」という保護が働く
ない削除は成功するが、存在しない注文を指す明細が残る。集計すると件数が合わないなど、原因の分かりにくい不整合になる
 
ERROR: update or delete on table "orders" violates
       foreign key constraint "fk_order_items_order" on table "order_items"

どちらにしても、先に子を消してから親を消す必要がある。

DELETE FROM order_items WHERE order_id = 1;   -- ① 子を先に
DELETE FROM orders      WHERE id = 1;         -- ② そのあと親

CascadeType.ALL（または REMOVE）を付ければ、orderRepository.delete(order) の 1 行で 子 → 親の順に DELETE を発行してくれる。外部キー制約違反も、孤児になることも起きない。

8. orphanRemoval

cascade が効くのは「親そのものを保存・削除したとき」。一方 orphanRemoval が働くのは、親は残したまま、明細を 1 件だけ取り消したいとき。

たとえば「注文はそのままで、ボールペンの明細だけキャンセルする」という処理を考える。

orders テーブル
idordered_at
12026-10-09注文は残したい
order_items テーブル
idorder_idname
51ボールペンこの明細だけ取り消したい
61ノートこれは残す

JPA では、リストから外すという書き方でこれを表現する。delete を呼ぶわけではない点が特徴。

@Transactional
public void removeItem(Long orderId, Long itemId) {
    Order order = orderRepository.findById(orderId).orElseThrow();

    OrderItem item = order.getItems().stream()
        .filter(i -> i.getId().equals(itemId))
        .findFirst().orElseThrow();

    order.getItems().remove(item);   // ← リストから外すだけ
}                                    // ← コミット時に DELETE が走る

orphanRemoval = true が付いていると、JPA は「リストから消えた子は、もう不要になった」と解釈して DELETE を発行する。

DELETE FROM order_items WHERE id = 5;   -- 外した 1 件だけ消える

2 つの違いを図で見る

きっかけ消えるもの
cascade = REMOVEorderRepository.delete(order)親と、すべての子
orphanRemoval = trueorder.getItems().remove(item)外した子だけ（親は残る）

役割が違うので、親子関係を一括で管理したい場合は両方セットで付けるのが定番。

orphanRemoval を付けないとどうなるか

orphanRemoval の既定は false。この場合、リストから外しても明細は消えない。結果はリレーションの持ち方で変わる。

何が起きるかは、リレーションの持ち方で変わる。比較するのは次の 2 つの形。

双方向（このセクションで使っている形） 
@Entity
public class Order {

    // 所有者は OrderItem 側
    @OneToMany(mappedBy = "order")
    private List<OrderItem> items = new ArrayList<>();
}

@Entity
public class OrderItem {

    // 外部キーを持つ（＝所有者）
    @ManyToOne
    @JoinColumn(name = "order_id")
    private Order order;
}
単方向 
@Entity
public class Order {

    // mappedBy が無く、Order 側が外部キーを管理する
    @OneToMany
    @JoinColumn(name = "order_id")
    private List<OrderItem> items = new ArrayList<>();
}

// OrderItem は Order への参照を持たない
リレーションの持ち方orphanRemoval = false のときに起きること
双方向DB には何も起きない（SQL が 1 本も発行されない）。明細が消えるのはメモリ上のリストからだけで、order_items の行はそのまま残る。次に読み込み直すと、外したはずの明細がまた現れる
単方向UPDATE order_items SET order_id = NULL WHERE id = 5 が走る。行は残るが親を失った明細（孤児）になる

この「親を失って取り残された子」が orphan（孤児）。orphanRemoval は「孤児になった子を削除する」という意味の設定で、ここから名前が来ている。

双方向の場合：なぜ SQL が発行されないのか

理由はセクション 2 で見た「mappedBy 側は所有者ではない」という話と同じ（→ 2. 双方向のリレーションと mappedBy）。DB でリレーションを保持しているのは order_items.order_id だけで、それを管理しているのは OrderItem.order フィールド。

public class Order {
    @OneToMany(mappedBy = "order")       // ← 所有者ではない（読み取り用）
    private List<OrderItem> items;
}

public class OrderItem {
    @ManyToOne
    @JoinColumn(name = "order_id")       // ← こちらが所有者
    private Order order;
}

order.getItems().remove(item) は所有者ではない側のリストをいじっただけなので、JPA は「DB を変更すべき操作」と見なさない。

⚠️ 使ってよいのは、親と子の一生が一致する場合だけ

ここまで便利に見えてきた cascade と orphanRemoval だが、付けてよい関係は限られている。CascadeType.ALL には REMOVE が含まれるため、親を消すと子も消えるという挙動がセットで付いてくる。

判断基準は「親が消えたとき、子だけ残っても意味があるか」。

関係使えるか理由
注文 → 注文明細✅ 使える注文が消えたら、明細だけ残っても意味がない。明細は注文の一部
カテゴリ → 商品❌ 使わないカテゴリを消しても、商品は残したい。商品はカテゴリの一部ではない
ユーザー → プロフィール✅ 使えるユーザーが消えたら、プロフィールも不要
ユーザー → 投稿△ 要件次第退会時に投稿も消すのか、残すのかは仕様で決まる

「明細は注文の一部」「商品はカテゴリの一部ではない」という違いが要点。前者のような関係を親子関係、後者のような関係を参照関係と呼ぶ。

双方向のメソッドと cascade の使い分け
