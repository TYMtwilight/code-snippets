プロジェクション（取得する列の絞り込み）

  • 📅 作成日: 2026-10-10
  • 🔄 更新日: 2026-10-10

🎯概要

プロジェクションとは、エンティティ全体ではなく、必要な列だけを取り出す仕組み。一覧画面で「商品名と価格しか使わない」といった場面で使う。

リポジトリのメソッドの戻り値の型を変えるだけで、Spring Data が必要な列だけを SELECT してくれる。

1 受け取る型を用意するインターフェース、または record / クラス
2 リポジトリの戻り値をその型にするList<Product> → List<ProductSummary>
3 SELECT が絞られるその型で必要な列だけが SQL に乗る

🔍 用語ノート: プロジェクション

projection は「射影」の意味。元のデータから一部の列だけを抜き出して別の形にする操作を指す、リレーショナルデータベースの用語。SQL の SELECT 句そのものが射影にあたる。

💻コード

1. なぜ列を絞るのか

これまでのようにエンティティで受け取ると、使わない列まで含めて全部取ってくる。

✗ エンティティで受け取る（List<Product>）

id name price description spec_sheet created_at updated_at
select p.id, p.name, p.price, p.description, p.spec_sheet, ... from products p

✓ プロジェクションで受け取る（List<ProductSummary>）

id name price description spec_sheet created_at updated_at
select p.id, p.name, p.price from products p

絞ることで得られるものは 2 つ。

  • 転送量が減る：description のような長い文章や画像データを持つ列を読まずに済む
  • 永続化コンテキストに乗らない：プロジェクションは管理対象のエンティティではないので、ダーティチェック用のコピーも作られない

💬 裏を返すと、プロジェクションで取ったオブジェクトは値を書き換えても DB に反映されない。更新したい場合はエンティティで取り直す。

2. インターフェースで受け取る

もっとも手軽な方法。欲しい列のゲッターだけを並べたインターフェースを用意する。実装クラスは不要で、Spring Data が自動で用意してくれる。

public interface ProductSummary {

    Long getId();

    String getName();

    BigDecimal getPrice();
}

あとは、リポジトリの戻り値をこの型にするだけ。

public interface ProductRepository extends JpaRepository<Product, Long> {

    List<ProductSummary> findByCategoryId(Long categoryId);
}

名前の対応ルール

ゲッター名から get を取り除いた部分が、エンティティのフィールド名と一致している必要がある。

✓一致している

Product の name  ↔  getName()

✗一致していない

Product に title は無い  ↔  getTitle()

この場合は呼び出し時にエラーになる。

3. クラス（DTO）で受け取る

インターフェースの代わりに、record やクラスで受け取ることもできる。コンストラクタの引数名でフィールドと対応づけられる。

public record ProductSummary(Long id, String name, BigDecimal price) {
}
List<ProductSummary> findByCategoryId(Long categoryId);

リポジトリ側の書き方はインターフェースのときと変わらない。発行される SQL も同じく id, name, price だけになる。

インターフェース

宣言するだけで済む。そのまま画面に渡す一覧データのような、単純な用途に向く。

クラス / record

ふつうの Java の型なので、メソッドを足したり、そのまま JSON にしたりしやすい。

@Query と組み合わせる場合

クエリメソッドではなく @Query で書くときは、JPQL の中で new を使ってコンストラクタを呼ぶ（コンストラクタ式）。クラスはパッケージ名から書く必要がある。

@Query("""
        select new com.example.app.product.ProductSummary(p.id, p.name, p.price)
        from Product p
        where p.category.id = :categoryId
        """)
List<ProductSummary> findSummaries(@Param("categoryId") Long categoryId);

💬 インターフェースで受け取る場合は new を書かず、select p.id, p.name, p.price のように列を並べる（別名はゲッター名と合わせる）。

4. 関連先も含めて取る（ネスト）

プロジェクションの中で、別のプロジェクションを返すゲッターを宣言できる。関連先から欲しい列だけを取れる。

public interface ProductSummary {

    Long getId();

    String getName();

    CategorySummary getCategory();   // 関連先も絞り込む

    interface CategorySummary {
        String getName();
    }
}

この場合、商品とカテゴリが JOIN された 1 本の SQL で取得される。カテゴリを LAZY にしていても、ここでは追加の SELECT は発行されない。

5. 呼び出すたびに型を変える（動的プロジェクション）

同じ条件でも、画面によって欲しい列が違うことがある。型引数で受け取れば、メソッドを増やさずに使い分けられる。

<T> List<T> findByCategoryId(Long categoryId, Class<T> type);
// 一覧画面：名前と価格だけ
List<ProductSummary> summaries =
        productRepository.findByCategoryId(1L, ProductSummary.class);

// 編集画面：全部必要なのでエンティティで
List<Product> products =
        productRepository.findByCategoryId(1L, Product.class);

渡した Class に応じて、SELECT する列が切り替わる。

リポジトリのメソッドは 1 つだけ

findByCategoryId(1L, 渡す型)
ProductSummary.class →
select p.id, p.name, p.price from products p
Product.class →
select p.id, p.name, p.price, p.description, ... from products p

同じ検索条件を使い回しながら、画面ごとに必要な分だけ取れる。findSummaryByCategoryId、findDetailByCategoryId のように、型の数だけメソッドを並べずに済む。

6. オープン・プロジェクション

インターフェースのゲッターに @Value を付けると、複数のフィールドを組み合わせた値を返せる。

public interface ProductLabel {

    @Value("#{target.name + '（' + target.price + '円）'}")
    String getLabel();
}

target は元のエンティティを指す。上の例なら「ボールペン（150円）」のような文字列が得られる。

⚠️ 列の絞り込みは効かなくなる

@Value の式の中で何を使うかを Spring Data は把握できないため、エンティティ全体が読み込まれる。@Value を使わないもの（クローズド・プロジェクション）だけが SELECT の最適化を受けられる。

文字列の組み立てが目的なら、DTO 側のメソッドでやるほうが素直。

public record ProductSummary(Long id, String name, BigDecimal price) {

    public String label() {
        return name + "（" + price + "円）";
    }
}

7. 使い分けと注意点

どの型で受け取るか

受け取る型SELECT の列更新主な用途
エンティティ全列できる登録・更新処理、詳細画面
インターフェース宣言した列のみできない一覧・検索結果
クラス / record宣言した列のみできない一覧・集計、API のレスポンス

インターフェースと DTO は、どちらも同じように SELECT が絞られる。違うのは受け取ったあとの扱いやすさ。

インターフェースクラス / record
実体Spring が作るプロキシふつうの Java オブジェクト
デバッグ時の見やすさ中身が見えにくいそのまま見える
メソッドの追加@Value + SpEL が必要ふつうに書ける
関連先のネスト入れ子の宣言で簡単new では基本 1 階層まで

📌 迷ったら record の DTO

ふつうの型なので、そのまま JSON にでき、テストでも組み立てられ、あとからメソッドを足せる。層をまたいで持ち回す前提ならこちら。

インターフェースが優るのは、関連先まで絞り込みたいとき（「4.」のネスト）。これは DTO のコンストラクタ式では素直に書けない。

DB 側で絞るか、取ってから詰め替えるか

同じ ProductSummary を返すにしても、どこで列を落とすかで 2 通りの書き方がある。

✓ DB 側で絞る（プロジェクション） 
List<ProductSummary> list = productRepository.findByCategoryId(1L);
✗ 全列取ってから詰め替える 
List<ProductSummary> list = productRepository.findByCategoryId(1L).stream()
        .map(p -> new ProductSummary(p.getId(), p.getName(), p.getPrice()))
        .toList();

下の書き方は、戻り値こそ ProductSummary だが、SQL は全列を読んでいる。列を絞る目的では効果がない。

ただし、詰め替えが適している場面もある。

  • 複数のリポジトリの結果を組み合わせて返す：1 本のクエリでは作れないので、Java 側で組み立てる
  • 更新処理の戻り値を返す：どのみちエンティティを取得しているので、そこから詰め替えるのが自然

読み取り専用の一覧・検索

DB 側で絞る

エンティティを扱う処理のついでに返す

詰め替える

注意点

  • 更新するならエンティティ：プロジェクションは管理対象外なので、書き換えても DB には届かない
  • 最初から全部に適用しなくてよい：件数の多い一覧や、重い列を持つテーブルから順に適用していく

ネイティブクエリで使うときは別名を付ける

ネイティブクエリ（nativeQuery = true）でもプロジェクションは使えるが、対応づけのやり方が変わる。

1通常のクエリ（JPQL）の場合

Spring Data はエンティティの定義を知っているので、getCreatedAt() が createdAt フィールドを指すこと、それが created_at 列であることをたどれる。

getCreatedAt() → エンティティの createdAt → 列 created_at

2ネイティブクエリの場合

書いた SQL がそのまま実行されるだけなので、エンティティを介さない。結果に付いてくる列名とゲッター名を直接照らし合わせる。

getCreatedAt() ↔ 結果の列名 created_at　✗ 一致しない

そのため、SQL 側で as を使ってゲッター名と同じ別名を付ける。

✗ 列名のまま：getCreatedAt() が埋まらない 
select p.id, p.name, p.created_at from products p
✓ 別名を付ける 
select p.id, p.name, p.created_at as createdAt from products p

💬 id や name のように列名とフィールド名がそもそも同じものは、別名を付けなくても対応する。必要になるのは created_at のようなスネークケースの列。
