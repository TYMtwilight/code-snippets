Spring Data Repository の基本

  • 📅 作成日: 2026-10-05
  • 🔄 更新日: 2026-10-05

🎯概要

Spring Boot + JPA の業務アプリでは、リポジトリは JpaRepository を継承するのが標準。インターフェースを宣言するだけで、CRUD・ページング・ソート・JPA 固有の操作がまとめて使えるようになる。実装クラスは自分で書かず、Spring が起動時にプロキシとして自動生成する。

インターフェース位置づけ
JpaRepository実務の標準。下記の機能すべて + JPA 固有の機能
ListCrudRepositoryCRUD（複数件の戻り値が List）。Spring Data 3 以降
CrudRepositoryCRUD（複数件の戻り値が Iterable）
PagingAndSortingRepositoryPageable / Sort を受け取る findAll
Repository<T, ID>メソッドを持たない目印。公開するメソッドを絞りたいときに直接継承する

🔍 用語ノート: プロキシ

インターフェースは「こういうメソッドがある」という約束だけで、処理の中身を持たない。普通は implements したクラスを自分で書いて中身を用意するが、Spring Data ではその中身を持つオブジェクトを Spring が代わりに作ってくれる。この自動で作られるオブジェクトを「プロキシ」と呼ぶ。

① 自分で書くのはインターフェースだけ

public interface ProductRepository extends JpaRepository<Product, Long> {
}

② Spring Data がなければ、本来こういう実装クラスが必要

// ↓ Spring Data を使えば、このクラスは書かなくてよい
@Repository
public class ProductRepositoryImpl implements ProductRepository {

    @PersistenceContext
    private EntityManager em;

    @Override
    public List<Product> findAll() {
        return em.createQuery("select p from Product p", Product.class)
                 .getResultList();
    }

    @Override
    public Optional<Product> findById(Long id) {
        return Optional.ofNullable(em.find(Product.class, id));
    }

    @Override
    public Product save(Product product) {
        em.persist(product);
        return product;
    }

    // ... JpaRepository の残りのメソッドも全部書く必要がある
}

③ ②の代わりに、Spring が自動で作るクラス（＝プロキシ）のイメージ

// ※ 実際のコードではなく、動きを表したイメージ
class $Proxy123 implements ProductRepository {   // ← これがプロキシ

    // 本物の処理を持っているのは Spring Data の SimpleJpaRepository
    private final SimpleJpaRepository<Product, Long> target;

    @Override
    public List<Product> findAll() {
        return target.findAll();       // 自分では処理せず、本物に渡すだけ
    }

    @Override
    public Optional<Product> findById(Long id) {
        return target.findById(id);    // 同じく本物に渡すだけ
    }

    // ...
}

プロキシ自身は処理を持たず、受け取った呼び出しを本物の実装（SimpleJpaRepository）に渡すだけ。本人の代わりに窓口に立つことから「代理人（プロキシ）」と呼ばれる。②のようなクラスを毎回書かなくて済むのは、この仕組みのおかげ。

📦 SimpleJpaRepository とは

Spring Data JPA が用意している JpaRepository の標準の実装クラス。save / findById / findAll などの標準メソッドの中身は、すべてこのクラスに書かれている。プロキシの裏側で自動的に使われるので、自分で new したり直接使ったりすることはまずない。

JpaRepository（インターフェース）  ← 約束だけ
      ▲ implements
SimpleJpaRepository（クラス）       ← 中身を持つ本物の実装

②の ProductRepositoryImpl は、コードの中に Product と直接書いてあるので Product 専用。Order を扱いたければ、OrderRepositoryImpl をもう 1 つ書くことになる。

一方 SimpleJpaRepository は、Product の部分を T、Long の部分を ID という「あとで決まる型」にして書いてある。

// ② 自分で書く場合：Product と書いてある → Product 専用
public Optional<Product> findById(Long id) {
    return Optional.ofNullable(em.find(Product.class, id));
}

// SimpleJpaRepository：Product の部分が T になっている → どのエンティティにも使える
public Optional<T> findById(ID id) {
    return Optional.ofNullable(em.find(domainClass, id)); // domainClass には実際のエンティティのクラスが入る
}

T と ID に何が入るかは、①で書いた JpaRepository<Product, Long> から決まる。

  • ProductRepository 用 → T = Product、ID = Long として動く
  • OrderRepository 用 → T = Order、ID = Long として動く

つまり、この 1 つのクラスをどのエンティティにも使い回せるので、エンティティごとに実装クラスを書く必要がない。

起動時〜呼び出し時に起きていること

  1. 起動時Repository を継承したインターフェースが探される
  2. 起動時見つかったインターフェースごとにプロキシが生成され、Bean として登録される
    → Service でコンストラクタインジェクションして受け取れる 
    @Service
public class ProductService {

    // 型はインターフェース
    private final ProductRepository productRepository;

    // Spring が Bean 登録済みのプロキシを自動で渡してくれる
    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }
}
  3. 呼び出し時Service がメソッドを呼ぶと、まずプロキシが受け取る
  4. 呼び出し時プロキシが、メソッドの種類に応じて処理を振り分ける
    • save / findAll などの標準メソッド

      Service→プロキシ→SimpleJpaRepository→EntityManager→DB

    • findByName など自分で宣言したメソッド

      メソッド名を解析して生成したクエリで実行される

💻コード

1. JpaRepository を継承して定義する

public interface ProductRepository extends JpaRepository<Product, Long> {
    // 何も書かなくても、下表のメソッドがすべて使える
}

実装クラスを書く必要はない。型パラメータ <エンティティの型, ID の型> を指定して継承するだけで、Spring が起動時にプロキシを生成し、Spring Data の機能がそのまま使えるようになる。

継承するだけで使える主なメソッド

メソッド戻り値用途
save(entity)T新規登録・更新
findById(id)Optional<T>1 件取得
findAll()List<T>全件取得
findAll(Sort)List<T>並び順を指定して全件取得
findAll(Pageable)Page<T>ページ単位で取得
deleteById(id)void削除
saveAndFlush(entity)T保存して即座に SQL を発行
deleteAllInBatch()void1 回の DELETE 文でまとめて削除

2. JpaRepository が選ばれる理由

  • 一覧の戻り値が List

    findAll() などがそのまま List で返るので、Stream 処理・件数確認・インデックス指定が変換なしでできる（詳しくは次の「3.」）。

  • ページングとソートが最初から使える

    業務アプリに必ずある一覧画面に、findAll(Pageable) ですぐ対応できる。

  • JPA 固有の便利な機能がある

    saveAndFlush / flush / deleteAllInBatch など、JPA を使っていると欲しくなる操作がそろっている。

  • チームで迷わない

    「とりあえずこれを継承すれば困らない」うえ、公式ガイドや既存コードの多くがこの形なので、新しく入った人も読みやすい。

3. Iterable と List の戻り値の違い

Iterable は「1 件ずつ順番に取り出せる」ことしか約束しない最小限のインターフェース。List は Iterable を継承したうえで、件数や空チェックなどの便利なメソッドを持っている。

やりたいことIterableList
拡張 for 文で 1 件ずつ取り出す○○
0 件かどうか調べる× isEmpty() がない○ isEmpty()
件数を数える× size() がない○ size()
n 番目を取り出す× get() がない○ get(i)
Stream で加工する× stream() がない○ stream()

⚠️ Iterable だと何が面倒か（業務でよくある 3 つの処理）

「商品一覧を取得して、0 件ならエラー、件数をログに出し、レスポンス用の DTO に変換して返す」という処理で比べる。

✗ Iterable の場合（CrudRepository を継承） 
public List<ProductResponse> findAllProducts() {
    Iterable<Product> products = productRepository.findAll();

    // ① 0 件チェック：isEmpty() がないので、iterator を取り出して確認する
    if (!products.iterator().hasNext()) {
        throw new ProductNotFoundException();
    }

    // ② 件数：size() がないので、自分でループして数える
    int count = 0;
    for (Product p : products) {
        count++;
    }
    log.info("取得件数: {}", count);

    // ③ DTO に変換：stream() がないので、StreamSupport で Stream に変換してから使う
    return StreamSupport.stream(products.spliterator(), false)
            .map(ProductResponse::from)
            .toList();
}
✓ List の場合（JpaRepository を継承） 
public List<ProductResponse> findAllProducts() {
    List<Product> products = productRepository.findAll();

    // ① 0 件チェック
    if (products.isEmpty()) {
        throw new ProductNotFoundException();
    }

    // ② 件数
    log.info("取得件数: {}", products.size());

    // ③ DTO に変換
    return products.stream()
            .map(ProductResponse::from)
            .toList();
}
  • 🌀
    遠回りなコードになる Iterable では、同じ処理でもやりたいことを直接書けない
  • 📖
    読む人の負担になる StreamSupport.stream(products.spliterator(), false) のような見慣れない書き方が増える
  • 🏢
    業務では毎回のように発生する 取得した一覧をそのまま加工・チェックする処理がほとんど

💡 だから、List で返ってくる方が圧倒的に扱いやすい

4. Service から使う（findById は Optional）

@Service
public class ProductService {

    private final ProductRepository productRepository;

    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    public Product findProduct(Long id) {
        return productRepository.findById(id)
                .orElseThrow(() -> new ProductNotFoundException(id));
    }

    public List<Product> findAllProducts() {
        return productRepository.findAll(); // JpaRepository なので List で返る
    }

    public Page<Product> findProductPage(Pageable pageable) {
        return productRepository.findAll(pageable);
    }
}

findById の部分を抜き出すと

public Product findProduct(Long id) {
    return productRepository.findById(id)  // ① Optional<Product> が返る
            // ② 空なら例外を投げる
            .orElseThrow(() -> new ProductNotFoundException(id));
}
  • ① findById は、該当する ID のデータがない可能性があるので、Product ではなく Optional<Product>（中身が入っているかもしれない箱）を返す。「見つからない場合」を呼び出し側に必ず意識させるための設計
  • ② orElseThrow は、中身があればそれを取り出し、空なら指定した例外を投げる。見つからなければ例外にするのが定石

Optional の扱いで避けたいこと

✗ get() をいきなり呼ぶ 
public Product findProduct(Long id) {
    return productRepository.findById(id).get();
    // 空のとき NoSuchElementException: No value present
}

データがないと NoSuchElementException が出るが、メッセージは「No value present」だけ。どの ID の何が見つからなかったのかわからず、原因を追いにくい。

✗ isPresent() と get() を組み合わせる 
public Product findProduct(Long id) {
    Optional<Product> result = productRepository.findById(id);
    if (result.isPresent()) {
        return result.get();
    } else {
        throw new ProductNotFoundException(id);
    }
}

動きは正しいが、if (product != null) の null チェックと書き方が変わらない。Optional を使う意味が薄れ、コードも長くなる。

✓ orElseThrow を使う 
public Product findProduct(Long id) {
    return productRepository.findById(id)
            .orElseThrow(() -> new ProductNotFoundException(id));
}

見つからない場合にどの例外を投げるかが一目でわかり、例外に ID も渡せるので原因も追いやすい。

ProductNotFoundException の例

public class ProductNotFoundException extends RuntimeException {

    public ProductNotFoundException(Long id) {
        super("商品が見つかりません: id=" + id);
    }
}
  • RuntimeException を継承した例外（非検査例外）は、try-catch や throws を書かなくてもコンパイルが通る。Exception を継承した検査例外にすると、findProduct にも、それを呼ぶ側にも例外処理を書く必要が出てくる
  • コンストラクタで ID を受け取り、メッセージに含める → ログを見れば「どの ID が見つからなかったか」がすぐわかる
