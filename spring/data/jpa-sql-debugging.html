発行された SQL の追い方（開発・本番）

  • 📅 作成日: 2026-10-10
  • 🔄 更新日: 2026-10-11

🎯概要

Spring Data JPA は SQL を自動で組み立ててくれる。便利な反面、裏で何が発行されているかが見えない。N+1 や意図しないクエリに気づくには、SQL を目に見える形にしておく必要がある。

ただし、開発環境と本番環境では取れる手段が違う。

開発環境本番環境
方針全部出す絞って出す
理由自分しか使わないので、量も性能も気にしなくてよいログの量、性能への影響、個人情報が問題になる
主な手段ログ出力、p6spyAPM（Zipkin など）、遅いクエリだけ記録

このスニペットでは、この 2 つを分けて扱う。最終的に目指すのは、次の 3 つを組み合わせた構成。

p6spy

SQL の中身を見る。値が埋まった状態でログに出る。

Micrometer Tracing

処理時間を計測する。ログにトレース ID も付けてくれる。

Zipkin

計測結果を保存して画面で見せる。

💻開発環境で SQL を追う

開発環境では、とにかく全部出してしまってよい。

1. Hibernate が発行した SQL を出す

方法は 2 つあるが、ログに出すほうを使う。

📌 設定を書く場所

以降に出てくる spring: や logging: で始まるコードは、すべて src/main/resources/application.yml（または「3.」で分ける環境別のファイル）の中身。

application.properties を使っている場合は、階層をドットで繋いだ 1 行で書く。どちらでも動作は同じ。

application.ymlapplication.properties
spring:
  jpa:
    show-sql: true		 spring.jpa.show-sql=true

yml はインデントで階層を表すので、ずれると設定が効かない。タブ文字は使えず、半角スペースのみ。

✗ show-sql：System.out に直接出る 
spring:
  jpa:
    show-sql: true

手軽だがロガーを通らないため、時刻もスレッド名も付かず、出力先も選べない。他のログと混ざって追いにくい。

✓ ロガーのレベルを下げる 
logging:
  level:
    org.hibernate.SQL: debug

spring:
  jpa:
    properties:
      hibernate:
        format_sql: true   # 改行とインデントを付ける
select
    p1_0.id,
    p1_0.name,
    p1_0.price
from
    products p1_0
where
    p1_0.category_id=?

2. パラメータの値も出す

上の出力では、条件の値が ? のままで分からない。実際に渡された値を見るには、もう 1 つログを足す。

logging:
  level:
    org.hibernate.SQL: debug
    org.hibernate.orm.jdbc.bind: trace

すると、「1.」の SQL のあとに 1 行足される。

select
    p1_0.id,
    p1_0.name,
    p1_0.price
from
    products p1_0
where
    p1_0.category_id=?                 ← 「1.」で出ていた部分。値は分からない

binding parameter (1:BIGINT) <- [3]    ← 追加される行
                   │   │         │
                   │   │         └ 渡された値は 3
                   │   └ 型は BIGINT（Long）
                   └ 1 番目の ? のこと

2 つを合わせて読むと、category_id = 3 で検索していたと分かる。? が複数ある場合は、(1:...) (2:...) と左から順に対応する。

⚠️ この設定は開発環境だけにする

パラメータには氏名やメールアドレスなどがそのまま載る。また、クエリ 1 本ごとに数行増えるので、ログの量も一気に膨らむ。

次の「3.」のように、環境ごとのファイルに分けて書くことで、本番では出ない状態にしておく。

3. 設定を環境ごとに分ける

ログの設定は、共通の application.yml には書かない。

src/main/resources/

application.yml 共通設定。SQL ログの設定は書かない
application-dev.yml 開発用。ここにだけ書く

ログレベルは何も書かなければ出力されない。そのため、本番用に「出さない設定」を書く必要はない。dev プロファイルで起動したときだけ出るようになる。

java -jar app.jar --spring.profiles.active=dev

4. p6spy で見やすくする

ここまでの設定だと、SQL とパラメータが別々の行に出るので読みにくい。p6spy を入れると、1 行にまとまる。

プロジェクト直下の build.gradle を開き、dependencies の中に 1 行足す。

// build.gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
    implementation 'org.springframework.boot:spring-boot-starter-web'

    // ← これを追加
    implementation 'com.github.gavlyukovskiy:p6spy-spring-boot-starter:1.9.1'
}
took 23ms | select * from products where category_id = 3
     │                                                  │
     │                                                  └ ? ではなく実際の値
     └ このクエリにかかった時間

依存を足すだけで、値が埋まった SQL と、1 本ごとの実行時間が 1 行で出る。設定は要らない。

「2.」のように SQL とパラメータを突き合わせる必要がなくなるので、開発中はこちらのほうが読みやすい。

💬 書き換えただけでは反映されない。ライブラリの取得が必要。IDE なら通知から「再読み込み」、コマンドなら ./gradlew build を実行してから、アプリを起動し直す。

🔍 用語ノート: p6spy

アプリと DB の間に割り込んで、通った SQL を記録するライブラリ。アプリのコードは 1 行も変えなくてよい。

割り込む場所は DataSource。DataSource とは、DB への接続を取得するための窓口のことで、リポジトリも最終的にはここを通って SQL を実行している。

ProductRepositoryアプリが呼ぶ窓口
保存や検索の呼び出しを渡す
EntityManagerJPA の本体
SQL を実行するために接続を求める
p6spy の DataSource横取りして SQL を記録し、そのまま本物へ渡す
接続を 1 本借りる
本物の DataSource接続を作り置きして使い回す（HikariCP）
SQL を実行する
DB

呼び出す側から見ればどちらも同じ DataSource なので、包まれていることに気づかない。だから設定なしで動く。

5. SQL の本数を数える（N+1 を見つける）

ログを目で追うのは限界があるので、本数を出させると分かりやすい。

spring:
  jpa:
    properties:
      hibernate:
        generate_statistics: true
Session Metrics {
    21 JDBC statements          ← 1 回のはずが 21 回なら N+1 を疑う
}

💬 統計の収集にはコストがかかるので、本番では無効にしておく。

6. 開発プロファイルの設定例

p6spy を使うかどうかで、書く内容が変わる。どちらか一方でよい。

① p6spy を使う場合（おすすめ）

# application-dev.yml
spring:
  jpa:
    properties:
      hibernate:
        generate_statistics: true   # SQL の本数を出す

ログの設定は要らない。p6spy は依存を足すだけで出力されるため。

② p6spy を使わない場合

# application-dev.yml
spring:
  jpa:
    properties:
      hibernate:
        format_sql: true            # SQL を整形する
        generate_statistics: true

logging:
  level:
    org.hibernate.SQL: debug          # SQL 本体
    org.hibernate.orm.jdbc.bind: trace   # パラメータの値

📌 両方入れてしまったときは

同じ SQL が二重に出て読みにくくなる。②のログ 2 行を消せばよい。ログレベルは指定しなければ出力されないので、「止める設定」を書く必要はない。

あとで戻す前提なら、消さずに off を指定してもよい。

logging:
  level:
    org.hibernate.SQL: off

format_sql も Hibernate のログを整形する設定なので、p6spy の出力には効かない。①では省いている。

🚀本番環境で SQL を追う

本番では、開発環境と同じやり方は使えない。

  • ログの量：1 リクエストで数十行増える。保管費用も検索性も悪化する
  • 性能：出力そのものが負荷になる
  • 個人情報：パラメータには氏名やメールアドレスが載る

⚠️ パラメータのログは本番では出さない

「2.」で使った org.hibernate.orm.jdbc.bind は、本番では有効にしない。障害調査でどうしても必要になった場合も、対象を絞って短時間だけにする。

そのうえで、本番で実際に使える構成を見ていく。

1. 3 つを組み合わせる

本番で知りたいのは、どのリクエストが遅く、そのときどんな SQL が出ていたのかということ。これを 1 つで賄える道具はないので、次の 3 つで役割を分ける。

道具役割本番での扱い
Micrometer Tracing処理時間を計測し、ログにトレース ID を付ける常時オン（記録する割合は下げる）
Zipkin計測結果を保存し、画面で見せる常時オン
p6spySQL の中身をログに出す遅いクエリだけに絞る

🔍 用語ノート: APM

Application Performance Monitoring（アプリケーション性能監視）の略。稼働中のアプリの性能を自動で計測して可視化する仕組み。Micrometer Tracing + Zipkin は、これを無料で組む構成にあたる。

リクエスト 1 件ごとに、処理の内訳が時間つきで並ぶ。

GET /products?category=3              [ 1,240ms ]
  └ ProductService.findAll            [ 1,180ms ]
      ├ SELECT products               [    18ms ]
      └ ... 同じクエリが 20 回          ← N+1 が一目で分かる

ログとの違いは、1 リクエスト = 1 本の流れとして記録されること。ログは 1 行ずつ独立しているので、どのリクエスト由来かを後から辿りにくい。

💬 有料の APM（Datadog、New Relic など）は、エージェントを付けるだけで上の図のような画面が出る。Zipkin で同じ形にするには、メソッド単位の計測や SQL の記録を自分で足す必要がある。

🔍 用語ノート: Micrometer Tracing と Zipkin

Micrometer Tracing＝「この処理に何ミリ秒かかったか」を自動で記録するライブラリ。Spring Boot 3 の標準。
Zipkin＝記録を受け取って保存し、画面で見せるサーバー。計測そのものはしない。

アプリMicrometer Tracing が時間を計測する
計測したデータを送る
Zipkin受け取って貯め、検索・表示する

役割が分かれているので、Zipkin を起動しただけでは何も映らない。アプリ側に依存を入れて、はじめてデータが流れてくる。

Micrometer Tracing が自動で計測するのは、おもに次の 3 つ。

  • リクエストを受けてから返すまで
  • 別のアプリに HTTP で問い合わせて、返事が返ってくるまで
  • 定期実行の処理（@Scheduled を付けたメソッド）

この「始まってから終わるまで」1 つ分を スパン と呼ぶ。Zipkin の画面で横棒 1 本として表示される。

2. 設定する

① Zipkin を用意する

動作確認はローカルでもできる。

docker run -d -p 9411:9411 openzipkin/zipkin

💬 既定ではデータをメモリに持つだけなので、本番で使うなら保存先（Elasticsearch など）の設定が要る。

🔍 用語ノート: なぜ Docker が出てくるのか

Zipkin は アプリとは別プロセスで動く独立したサーバーなので、アプリとは別に起動する必要がある。

Docker を使わない場合は、次の手順を自分で踏む。

  • zipkin.jar をダウンロードする
  • 動作する Java のバージョンを揃える
  • java -jar zipkin.jar で起動する

Docker イメージには、この一式が済んだ状態が入っている。だから docker run 1 行で起動できる。

docker run -d -p 9411:9411 openzipkin/zipkin
部分意味
-dバックグラウンドで動かす（ターミナルを占有しない）
-p 9411:9411手元の 9411 番ポートを、コンテナの 9411 番に繋ぐ
openzipkin/zipkinZipkin の公式イメージ名

9411 が 2 回出てくるのは、Zipkin が既定で 9411 番ポートを使うため。この番号が「③」の送信先と対応している。

management.zipkin.tracing.endpoint: http://zipkin:9411/api/v2/spans

起動後は http://localhost:9411 をブラウザで開くと、トレースの画面が出る。

💬 Docker は Zipkin の必須条件ではなく、導入の手間を省くための手段。上の java -jar でも同じように動く。

② 依存を追加する

p6spy と同じく、build.gradle の dependencies に追加する。

implementation 'org.springframework.boot:spring-boot-starter-actuator'
implementation 'io.micrometer:micrometer-tracing-bridge-brave'
implementation 'io.zipkin.reporter2:zipkin-reporter-brave'
依存役割
micrometer-tracing命令の書き方を決めているだけ。自分では測らない
...-bridge-brave実際に時間を測る担当
zipkin-reporter-brave測った結果を Zipkin へ送る担当

③ 本番用の設定を書く

# application-prod.yml
spring:
  application:
    name: order-app
  jpa:
    properties:
      hibernate:
        session.events.log.LOG_QUERIES_SLOWER_THAN_MS: 1000

management:
  tracing:
    sampling:
      probability: 0.1
  zipkin:
    tracing:
      endpoint: http://zipkin:9411/api/v2/spans

logging:
  level:
    p6spy: off

キーが 4 つのブロックに分かれているので、順に見ていく。

1アプリの名前を決める

spring.application.name: order-app

Micrometer Tracing が送るデータにこの名前が入るので、Zipkin の画面で「どのアプリのスパンか」を示すラベルになる。

さらに、このあと「3.」で出てくるログ行の先頭にも入る。

[order-app,a1b2c3d4e5f6,b7c8d9]

複数のアプリを 1 つの Zipkin に送るとき、これがないと区別がつかない。

2遅いクエリを記録する

spring.jpa.properties.hibernate.session.events.log.LOG_QUERIES_SLOWER_THAN_MS: 1000

この設定が何をするかは、次の「④」で扱う。ここで押さえておきたいのは properties という階層の意味。

  • spring.jpa.show-sql のようなキーは、Spring Boot が解釈する
  • spring.jpa.properties 以下は、キーごと Hibernate にそのまま渡される

つまり session.events.log.LOG_QUERIES_SLOWER_THAN_MS は Spring の設定ではなく、Hibernate 独自のキー。だから周りの設定と書き振りが違う。

3計測と送信先を決める

management.tracing.sampling.probability: 0.1

記録する割合。10 件に 1 件だけ記録する。詳しくはこのあとの用語ノート。

management.zipkin.tracing.endpoint: http://zipkin:9411/api/v2/spans

計測結果の送信先。アプリ側が自分でここへ送るので、Zipkin が取りに来るわけではない。

ホスト名が localhost でないことに注意。

  • zipkin … Docker Compose などで同じネットワーク上にいるコンテナの名前
  • localhost … 「①」のように手元で docker run して試す場合

4p6spy の出力を止めておく

logging.level.p6spy: off

p6spy は依存を足すだけで全 SQL を出してしまうため、本番ではこれを止めておく。

p6spy は p6spy という名前のロガーで出力するので、そのロガーを off にすれば黙る。必要になったときだけレベルを上げる（「4.」）。

⚠️ enable-logging: false との違い

p6spy の出力を止める設定は、もう 1 つある。

decorator:
  datasource:
    p6spy:
      enable-logging: false

decorator.datasource は、依存に入れた p6spy-spring-boot-starter のキー。DataSource を包む（decorate する）という役割からこの名前になっている。

ただしこちらは、記録する仕組みそのものを組み込まない設定。ロガーを通る前の段階で止まるため、あとからログレベルを上げても何も出ない。

設定止まる場所後から有効化できるか
logging.level.p6spy: offロガーの段階できる
enable-logging: false記録の段階できない（再起動が必要）

障害調査で一時的に出したいのだから、本番では logging.level.p6spy: off を使う。

🔍 用語ノート: サンプリング

すべてのリクエストを記録すると量が多すぎるため、一定の割合だけを記録すること。probability: 0.1 なら 10 件に 1 件。

傾向をつかむには十分だが、特定の 1 件を調べたいときは記録されていないこともある。開発環境では 1.0（全件）にしておく。

④ 遅いクエリだけを記録する

上の設定に含めた LOG_QUERIES_SLOWER_THAN_MS は、しきい値を超えたクエリだけをログに出す。件数が限られるので、本番でも常時オンにできる。

SlowQuery: 1532 milliseconds.
SQL: 'select p1_0.id, ... from products p1_0 where ...'

出力されるのは SQL 本体だけで、パラメータの値は含まれない。個人情報の心配なく残せる。

💬 あわせて DB 側のスロークエリログも有効にしておくとよい。アプリを通らない経路（バッチ、管理ツール）も拾えるうえ、実行計画と突き合わせられる。

3. 実際に調べる手順

3 つを組み合わせる本当の狙いは、トレース ID でログと画面を突き合わせられることにある。

Micrometer Tracing を入れると、Spring Boot がログの書式を自動で変える。

2026-10-10T12:00:00.123  INFO [order-app,a1b2c3d4e5f6,b7c8d9] ...
  #1 took 1532ms | select p.id, ... from products p where p.category_id = 3

[アプリ名, トレース ID, スパン ID] が全ログ行に付くので、p6spy が出した SQL のログにも同じ ID が載る。

1 Zipkin で遅いリクエストを探す一覧を所要時間で並べ、長いものを開く
2 トレース ID を控える画面に表示されている a1b2c3d4e5f6 のような文字列
3 その ID でログを絞り込むそのリクエストで出た SQL だけが並ぶ
4 原因を特定する同じ SQL が並んでいれば N+1、1 本が長ければクエリ自体が重い

Zipkin だけでは「遅い」までしか分からず、ログだけでは「どのリクエストのものか」が分からない。両方を ID で繋ぐことで、はじめて原因まで辿り着ける。

🔍 用語ノート: トレース ID

1 回のリクエストに対して自動で振られる識別子。そのリクエストの処理中に出たログやスパンには、すべて同じ ID が付く。

アプリが複数に分かれている場合は、呼び出し先にもヘッダーで引き継がれる。これにより、複数のアプリにまたがる処理を 1 本の流れとして追える。この仕組みを分散トレーシングと呼ぶ。

4. それでも足りないとき

しきい値以下のクエリまで見たい場合は、一時的にログを増やす。Actuator を入れていれば、再起動せずに変更できる。

「③」で off にしておいた p6spy のロガーを、その場で DEBUG に上げるという操作にあたる。

# 有効にする
curl -X POST http://localhost:8080/actuator/loggers/p6spy \
  -H "Content-Type: application/json" -d '{"configuredLevel": "DEBUG"}'

# 元に戻す
curl -X POST http://localhost:8080/actuator/loggers/p6spy \
  -H "Content-Type: application/json" -d '{"configuredLevel": null}'

⚠️ 使うなら短時間で

出し続ければログが膨らみ、性能にも響く。確認したらすぐ戻す。

また、このエンドポイントは誰でも叩けてはいけないので、認証を必須にしておく。

⚙️あわせて押さえる設定

ddl-auto：テーブルを誰が作るか

Hibernate は、エンティティの定義からテーブルを自動生成できる。その挙動を決めるのが ddl-auto。

値起動時の挙動使う場面
none何もしない本番
validate定義とテーブルが一致するか確認。ずれていれば起動失敗本番・検証環境
update足りない列を追加する（削除はしない）個人の開発環境
create起動のたびに作り直す（データは消える）テスト
create-dropさらに終了時に削除するテスト

⚠️ 本番で update を使わない

update は列の削除や型の変更をしないため、定義とテーブルが少しずつ食い違っていく。本番は none か validate にして、スキーマの変更は Flyway や Liquibase で管理する。

🔍 用語ノート: update は「足し算」しかしない

エンティティに列を追加したときは、起動時に ALTER TABLE が流れる。

@Entity
public class Member {
    @Id @GeneratedValue
    private Long id;

    private String name;

    // 新しく追加した
    private String email;
}
alter table member add column email varchar(255);

便利なのはここまでで、その逆は何もしない。

エンティティ側の変更update の挙動
列を追加したADD COLUMN を実行する
列を削除した何もしない（テーブルに残る）
型を変えた何もしない（古い型のまま）
列名を変えた新しい名前の列を追加する（古い列も残る）
制約を変えたほとんど反映されない

email を mailAddress に変えた場合を見ると分かりやすい。

// 変更前
private String email;

// 変更後
private String mailAddress;

追加しかしないので、テーブルはこうなる。

member テーブル

id 変更なし
name 変更なし
email 誰も使わないのに残る。NOT NULL だと INSERT が失敗する
mail_address 新しく追加された

これが積み重なると、エンティティの定義とテーブルの実態が一致しない DB ができあがる。

  • 開発・検証・本番で適用した順番が違えば、結果も違う
  • どの ALTER がいつ流れたか記録が残らない
  • 壊れても元に戻す手段がない

結果として「本番だけ動かない」が手元で再現できなくなる。

none と validate の違い

どちらもテーブルを変更しない点は同じで、違うのは確認するかどうか。

none

テーブルに一切触れない。確認もしない。

validate

定義とテーブルを突き合わせ、ずれていたら起動を失敗させる。

食い違ったまま動き続けて実行時に落ちるより、起動した時点で止まるほうが安全。そのため本番は validate が基本になる。

スキーマ変更は Flyway / Liquibase で管理する

スキーマの変更をバージョンを付けた SQL ファイルとして自分で書き、順番に適用する仕組み。

src/main/resources/db/migration/

V1__create_member.sql テーブルを作る
V2__add_email_to_member.sql 列を追加する
V3__rename_email_to_mail_address.sql 列名を変える 
-- V3__rename_email_to_mail_address.sql
ALTER TABLE member RENAME COLUMN email TO mail_address;

Flyway は適用済みのバージョンを DB の管理テーブルに記録するので、update と次の点で決定的に違う。

  • どの環境も同じ順番で同じ状態になる
  • 変更履歴が Git に残り、レビューできる
  • リネームや削除、データの移行も自分で書ける

つまり 本番の DB を Hibernate の推測に任せず、変更は人が書いて記録に残す、というのがこの使い分けの狙い。

open-in-view

Spring Boot では既定で 有効（true）。永続化コンテキストを画面を描き終わるまで開いたままにする設定で、起動時に警告ログが出る。

true（既定）

画面側で遅延ロードしても動く。LazyInitializationException が出にくい。

false

トランザクションの外では遅延ロードできない。想定外のクエリを防げる。

true の問題は、画面の描画中にクエリが飛ぶこと。どこで SQL が発行されたか追いにくく、DB の接続も長く掴んだままになる。SQL を追いやすくするという意味でも、false から始めるほうがよい。

spring:
  jpa:
    open-in-view: false
