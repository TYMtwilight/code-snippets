@DataJpaTest - スライステストとロールバック挙動

  • 📅 作成日: 2026-10-12
  • 🔄 更新日: 2026-10-12

🎯概要

@DataJpaTest は、エンティティとリポジトリだけを起動するテスト用のアノテーション。実際に SQL を発行しながら、リポジトリの動作を検証できる。押さえるべき性質は 2 つある。

スライス

アプリ全体ではなくエンティティとリポジトリだけを起動する。Service も Controller も Bean 登録されない。

ロールバック

テストメソッドがまるごと 1 つのトランザクションで動き、終了時に必ず巻き戻る。

このうち厄介なのがロールバックのほう。テストメソッド全体が 1 つのトランザクションになる結果、テストコードとリポジトリが同じ永続化コンテキストを共有してしまう。そのせいで、テストは通るのに本番では落ちるテストを簡単に書けてしまう。

🔍 用語ノート: 永続化コンテキスト

JPA が「いま扱っているエンティティ」を覚えておく作業場のこと。DB から読んだエンティティはまずここに置かれ、トランザクションが終わると破棄される。

作業場にいる間、エンティティは JPA の監視下にある。そのため save() を呼ばなくても変更が UPDATE される（ダーティチェック）し、同じデータを 2 回取得しても 2 回目は DB を見ずに作業場から返る。

詳細は トランザクションと永続化コンテキスト を参照。

🔍 用語ノート: スライステスト

アプリケーションを層（スライス）ごとに切り出して起動するテストのこと。Spring Boot には層ごとのアノテーションが用意されている。

  • @DataJpaTest … エンティティとリポジトリ
  • @WebMvcTest … Web 層（コントローラ）
  • @JsonTest … JSON のシリアライズ・デシリアライズ

対して @SpringBootTest はすべての Bean を起動する。起動が遅いうえ、失敗したときにどの層が原因なのかも分かりにくい。

💻コード

1. 最小の形

テストクラスに @DataJpaTest を付けて、リポジトリを @Autowired するだけ。

@DataJpaTest
class TodoRepositoryTest {

    @Autowired
    private TodoRepository todoRepository;

    @Test
    void 未完了のTODOだけ取得できる() {
        todoRepository.save(new Todo("買い物", false));
        todoRepository.save(new Todo("掃除", true));

        List<Todo> actual = todoRepository.findByCompleted(false);

        assertThat(actual).hasSize(1);
        assertThat(actual.get(0).getTitle()).isEqualTo("買い物");
    }
}

この @DataJpaTest 1 つに、次の設定がまとめて入っている。

  • JPA 関連の自動設定だけを有効にする
  • 接続先を組み込み DB（H2 など）に差し替える
  • テストメソッドを @Transactional で囲み、終了時にロールバックする
  • TestEntityManager を Bean 登録する

2. 何が起動して、何が起動しないのか

@DataJpaTest は JPA に関係する Bean だけを拾う。関係ない Bean はそもそも生成されないため、注入しようとするとテストの起動時点で失敗する。

対象起動補足
@Entityするスキャンされ、マッピングが検証される
Repository インタフェースする実装が生成され、実際に SQL が飛ぶ
EntityManager / DataSourceする接続先は組み込み DB に差し替わる
@Service / @Componentしない注入すると NoSuchBeanDefinitionException
@RestControllerしないWeb 環境ごと起動しない
自作の @Configurationしない必要なら @Import で個別に取り込む

どうしても Service が要るときは、スライスを壊さずに @Import で 1 つだけ足す。

@DataJpaTest
@Import(TodoService.class)
class TodoServiceTest {

    @Autowired
    private TodoService todoService;
}

ただし、Service の中の条件分岐や計算を検証したいだけなら、リポジトリをモックにした Mockito のテストのほうが速い。DB を起動する必要がない。

@Import する価値があるのは

DB を実際に動かさないと確認できないことを検証するときに限る。

  • Service の @Transactional が効いていて、途中で例外が出たら保存がすべて巻き戻るか
  • 複数のリポジトリにまたがる保存が、DB の制約（外部キーなど）に違反せず通るか

モックを使ったテストでは、リポジトリが「保存したことにしてくれる」だけなので、こうしたDB 側で起きることは検証できない。

3. ロールバック挙動

@DataJpaTest には @Transactional が含まれている。テストメソッドの開始から終了までが 1 つのトランザクションで、終了時には commit ではなくロールバックされる。

@Test
void データを1件保存する() {
    todoRepository.save(new Todo("買い物", false));

    assertThat(todoRepository.count()).isEqualTo(1);
}

@Test
void 前のテストのデータは残っていない() {
    // 前のテストが巻き戻っているので 0 件
    assertThat(todoRepository.count()).isZero();
}

この挙動から言えること

  • テスト同士が干渉しないので、@BeforeEach でのデータ削除は要らない
  • テストの実行順に依存しない
  • 実 DB に向けて流しても、データが残らない

ロールバックさせたくないとき

DB の中身を目で確認したいときなどは、@Rollback(false) を付けると commit される。

@Test
@Rollback(false)
void 保存結果をDBに残す() {
    todoRepository.save(new Todo("買い物", false));
}

常用はしない。commit するとテスト間でデータが残り、実行順に依存した壊れやすいテストになる。

4. 落とし穴: テストとリポジトリが同じトランザクションにいる

テストメソッド全体が 1 つのトランザクションということは、テストコードとリポジトリが同じ永続化コンテキスト（1 次キャッシュ）を共有しているということ。ここから 3 つの問題が生まれる。

(1) save() しても INSERT が飛ばない

save() は「DB に INSERT を打つ」命令ではなく、作業場（永続化コンテキスト）に登録するだけ。ためこんだ SQL をまとめて DB へ送る処理を flush と呼び、これは commit の直前に自動で起きる。

本番（Service の @Transactional）テスト（@DataJpaTest）
① save()作業場に登録するだけ作業場に登録するだけ
② 終了時commit するロールバックする
③ flushcommit の直前に起きる起きない
④ 結果INSERT が発行され、
not null 違反で例外		INSERT が発行されず、
例外も起きない

つまり、DB にたどり着いて初めて分かるはずのエラーが、テストでは DB まで届かないので起きない。制約違反を期待して書いたテストが、何事もなく通ってしまう。

NG 
@Test
void タイトルがnullなら保存に失敗する() {
    Todo todo = new Todo(null, false);

    // INSERT がまだ飛んでいないため not null 制約違反が起きず、
    // 例外を期待しているこのテストは失敗する
    assertThatThrownBy(() -> todoRepository.save(todo))
            .isInstanceOf(DataIntegrityViolationException.class);
}
OK 
@Test
void タイトルがnullなら保存に失敗する() {
    Todo todo = new Todo(null, false);

    // saveAndFlush で INSERT をその場で発行させる
    assertThatThrownBy(() -> todoRepository.saveAndFlush(todo))
            .isInstanceOf(DataIntegrityViolationException.class);
}

DB の制約（not null・unique・桁あふれ）を検証するテストには flush が要る。

ID の採番方式によって挙動が変わる
@GeneratedValue(strategy = IDENTITY) の場合は、ID を DB から受け取る必要があるため save() の時点で INSERT が発行される。一方 SEQUENCE では採番だけ先に済ませ、INSERT は flush まで遅延する。どちらでも確実に動くよう、制約を検証するテストでは明示的に flush する。

(2) save() を呼ばなくても更新されてしまう

取得したエンティティはトランザクションの管理下にある。値を変えるだけでダーティチェックが働き、save() を呼ばなくても反映される。

NG 
@Test
void タイトルを更新する() {
    Todo saved = todoRepository.save(new Todo("買い物", false));

    // save() を呼んでいないのに、この変更は反映される
    saved.setTitle("買い出し");

    assertThat(todoRepository.findById(saved.getId()).orElseThrow().getTitle())
            .isEqualTo("買い出し");
}

これは JPA として正しい挙動で、テストの不備ではない。問題なのは、このテストが「更新処理が save() を呼んでいるか」を何も保証していないこと。本番コードが save() を呼び忘れていても、同じように通ってしまう。

OK: save() を消したら落ちるテストにする

エンティティをいったん作業場の外に出してから更新する。作業場の外にあるエンティティはダーティチェックの対象ではないので、save() を呼ばなければ DB には反映されない。

OK 
@Autowired
private TestEntityManager em;

@Test
void タイトルを更新する() {
    // Given: 更新対象を 1 件用意する
    Todo saved = todoRepository.save(new Todo("買い物", false));
    em.flush();

    // saved を作業場の外に出す（これ以降、監視されない）
    em.clear();

    // When: 本番コードと同じ形で更新する
    saved.setTitle("買い出し");
    todoRepository.save(saved);

    // Then: DB へ書き出し、作業場を空にしてから読み直す
    em.flush();
    em.clear();

    assertThat(em.find(Todo.class, saved.getId()).getTitle())
            .isEqualTo("買い出し");
}

この形なら、todoRepository.save(saved) の行を消すとテストが失敗する。「更新が DB に届いたこと」を検証できている。

🔍 用語ノート: デタッチ

エンティティが作業場（永続化コンテキスト）から外れた状態を「デタッチされた（detached）」と呼ぶ。em.clear() やトランザクションの終了で起きる。

デタッチされたエンティティは、値を書き換えてもダーティチェックされない。DB に反映するには save()（内部では merge）を呼んで、作業場に戻し直す必要がある。

本番コードで「save() の呼び忘れ」が問題になるのはこの状態のとき。たとえば画面から受け取った値で組み立てたエンティティは、デタッチされた状態にある。

(3) findById が DB ではなく 1 次キャッシュから返る

同じトランザクション内では、findById() はさきほど save() したインスタンスをそのまま返す。SELECT すら飛ばないことがあり、マッピングのミスを見逃す。

OK 
@Autowired
private TestEntityManager em;

@Test
void 保存した内容をDBから読み直せる() {
    Todo saved = todoRepository.save(new Todo("買い物", false));

    // DB へ書き出してから、1 次キャッシュを空にする
    em.flush();
    em.clear();

    // ここで初めて本物の SELECT が飛ぶ
    Todo found = todoRepository.findById(saved.getId()).orElseThrow();

    // 別インスタンスとして読み直されている
    assertThat(found).isNotSameAs(saved);
    assertThat(found.getTitle()).isEqualTo("買い物");
}

検証したい内容ごとの対処

検証したいことやること
クエリメソッドの絞り込み・並び順そのままでよい
DB の制約（not null・unique）saveAndFlush() または em.flush()
マッピング・LAZY の挙動・DB の既定値em.flush() + em.clear()

5. TestEntityManager

@DataJpaTest が用意するテスト用のヘルパー。テストデータの準備はリポジトリではなくこちらで行うと、検証対象のリポジトリ自身に頼らずに済む。

@Autowired
private TestEntityManager em;

@Test
void 未完了のTODOだけ取得できる() {
    // Given: 準備は TestEntityManager で行う
    em.persistAndFlush(new Todo("買い物", false));
    em.persistAndFlush(new Todo("掃除", true));
    em.clear();

    // When: 検証対象はリポジトリのメソッドだけ
    List<Todo> actual = todoRepository.findByCompleted(false);

    // Then
    assertThat(actual).hasSize(1);
}

よく使うメソッド

  • persistAndFlush(entity)

    保存して、その場で INSERT を発行する。

  • find(Class, id)

    主キーで取得する。リポジトリを介さずに結果を確かめたいときに使う。

  • flush() / clear()

    ためこんだ SQL を発行する / 1 次キャッシュを空にする。

    2 つはセットで覚える
    flush() だけでは 1 次キャッシュが残ったままなので、「DB から読み直す」には clear() まで必要。

6. テストが使う DB を本番と同じにする

@DataJpaTest は、application.yml に書いた接続先（本番と同じ PostgreSQL など）を無視して、テストの間だけ H2 に差し替える。DB を用意しなくてもテストが動き、起動も速いため、既定でこうなっている。

🔍 用語ノート: 組み込み DB（H2）

アプリと同じプロセスの中で動く DBのこと。別途サーバを立てる必要がなく、メモリ上に作られてテスト終了とともに消える。

何が困るのか

H2 と PostgreSQL は別の DB なので、SQL の書き方や型が違う。問題になるかどうかは、SQL を誰が組み立てているかで分かれる。

クエリの書き方SQL を作るのはH2 でのテスト
クエリメソッド・JPQLHibernate問題ない
ネイティブクエリ自分当てにならない

Hibernate は接続先の DB に合わせて SQL を作り分ける（この差を方言／dialect と呼ぶ）。一方、自分で書いたネイティブクエリはそのまま H2 に投げられる。

// ilike は PostgreSQL 固有の書き方（大文字小文字を区別しない like）
@Query(value = "select * from todos where title ilike :keyword", nativeQuery = true)
List<Todo> searchByTitle(String keyword);

この SQL を H2 に対してテストしても、本番の PostgreSQL で動く保証にはならない。逆に、H2 が解釈できないせいでテストだけが落ちることもある。

差し替えをやめる

replace = NONE を指定すると、application.yml の接続先をそのまま使う。

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
class TodoRepositoryTest {
    // H2 ではなく、本番と同じ PostgreSQL に接続する
}

ただしこれは、テストを動かす全員（と CI）に PostgreSQL が立っていることが前提になる。そこで Testcontainers を使い、テストのたびに Docker で DB を立てる。

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Testcontainers
class TodoRepositoryTest {

    // コンテナで本番と同じバージョンの PostgreSQL を起動する
    // @ServiceConnection が接続情報を Spring に渡してくれる
    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16");
}

使い分け

方針速さ向いている検証
既定（H2 に差し替え）速いクエリメソッド・JPQL・マッピング
replace = NONE + Testcontainers遅い（コンテナ起動を待つ）ネイティブクエリ・DB 固有の型や関数

ふだんは既定の H2 でよい。ネイティブクエリを書いた時点で、本番と同じ DB を立てるテストに切り替える。
