ResponseEntity.created() - リソース作成レスポンスの便利メソッド

  • 📅 作成日: 2026-02-14
  • 🔄 更新日: 2026-10-03

🎯概要

REST APIでリソース作成時に 201 Created レスポンスと Location ヘッダーを返す際、Springの ResponseEntity.created() を使って簡潔に記述する方法。

📏 REST設計の慣習

作成に成功したら 200 OK ではなく 201 Created を返し、Location ヘッダーで作成された新しいリソースのURIをクライアントに教える。

ResponseEntity.created() は、この2つ（ステータスコード + ヘッダー）をまとめて設定してくれる専用メソッド。

リソース
データのまとまり（例: 1件の商品）
URL
そのリソースの場所を一意に指し示す住所（例: /products/123）

📌使用場面

  • @PostMapping でリソースを新規作成し、作成先URIをクライアントに返すとき
  • RESTful APIのベストプラクティスに従った 201 Created レスポンスを返すとき
  • クライアント側が、作成直後にそのリソースへ続けてアクセス（例: 詳細取得やフロントエンドの画面遷移）したいとき

💻コード

1created() と手動指定の比較

✓ 推奨: 便利メソッド
return ResponseEntity
        .created(location)
        .build();
✕ 冗長: 手動で全部指定
return ResponseEntity
        .status(HttpStatus.CREATED)
        .header(HttpHeaders.LOCATION,
                location.toASCIIString())
        .build();
⚙️ created() メソッドが自動で行うこと
  • ステータスコードを 201 Created に設定
  • Location ヘッダーにURIを追加
  • URIの形式チェック（バリデーション）

手動指定に対する利点

🔎 もう一歩

末尾の .build() は何をしているか

ResponseEntity.created(location) が返すのは ResponseEntity そのものではなく、設定を溜めておくビルダー（ResponseEntity.BodyBuilder）。.header(...) などで設定をつないでいき、最後に .build() を呼ぶと、それまでの設定で ResponseEntity が完成する（ビルダーパターン）。

created(location) BodyBuilder201 + Location 設定済み .build() ResponseEntity完成したレスポンス

.build() を呼ばないと ResponseEntity として返せないので、コンパイルエラーになる。

ビルダーの締め方は2通り

メソッド結果
.build()レスポンスボディなしのレスポンス
.body(obj)obj をボディ（JSONなど）として返すレスポンス
// ボディなし: ステータスと Location ヘッダーだけ返す（このスニペットの例）
// → ResponseEntity<Void>
return ResponseEntity.created(location).build();

// ボディあり: 作成した商品もJSONで返す
// → ResponseEntity<Product>
return ResponseEntity.created(location).body(saved);

2実際の使用例

@PostMapping
public ResponseEntity<Void> createProduct(@RequestBody Product newProduct) {
    // ① DBに保存（IDが採番される）
    Product saved = repository.save(newProduct);

    // ② 作成したリソースのURI: /products/123
    URI location = URI.create("/products/" + saved.getId());

    // ③ ボディなしで 201 + Location を返す
    return ResponseEntity.created(location).build();
}
  1. ①repository.save(newProduct) でDBに保存すると、自動採番されたIDを持つエンティティが返ってくる。このIDがあって初めて作成先URIが確定する。
  2. ②URI.create("/products/" + saved.getId()) で、保存後に確定したIDをもとにURIを組み立てている。URI.create() は文字列が不正なURI形式だと IllegalArgumentException を投げるため、単純な文字列連結よりも安全。
  3. ③戻り値の型が ResponseEntity<Void> になっているのは、レスポンスボディを返さず、ステータスコードと Location ヘッダーだけでクライアントに情報を伝えているため。

3レスポンス例

HTTPレスポンス
HTTP/1.1 201 Created
Location: /products/123

クライアントはレスポンスボディを見なくても、Location ヘッダーの値だけで「どこに何が作られたか」がわかる。

なぜ 200 OK ではなく 201 Created なのか

200 OK

「リクエストが成功した」ことしか表さない汎用的なステータス。

201 Created

「新しいリソースがサーバー上に作成された」ことまで明示する。クライアント（や間に入るキャッシュ・監視ツールなど）が意味を正しく解釈できる。

REST APIでは「操作の結果として何が起きたか」をステータスコードで正確に伝えることが重要視される。

📍 なぜ Location ヘッダーが必要なのか

作成したリソースのIDやURLは、サーバー側で採番されることが多く、リクエストを送ったクライアントはあらかじめ知らない。Location ヘッダーにURIを入れて返すことで、クライアントは「作成されたリソースが具体的にどこにあるか」を後続の処理（詳細取得・画面遷移など）にそのまま使える。
