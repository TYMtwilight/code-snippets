ステータスコードとエラー処理の基本

  • 📅 作成日: 2026-09-21
  • 🔄 更新日: 2026-10-03

🎯概要

REST APIのレスポンスまわりで、最初に押さえておきたい2つの書き方をまとめる。

  • 状況に合ったステータスコードを返す: 取得できたら 200 OK、作成したら 201 Created のように、結果に応じたステータスコードをレスポンスに付ける。そのために、戻り値を ResponseEntity で包む。
  • エラー時の処理を1か所にまとめる: 「データが見つからない」「入力値が不正」といったエラーへの対応を、Controllerごとに書くのではなく、専用のクラス（@RestControllerAdvice を付けたクラス）にまとめて書く。

どちらも、まずは動かすのに必要な最低限の形だけを扱う。

📌使用場面

  • 200 OK / 201 Created / 404 Not Foundなどを状況に応じて正しく返したいとき
  • 「見つからない場合」「入力値が不正な場合」などの例外処理を、各コントローラーに個別に書かず一箇所に集約したいとき
  • まずは最低限のエラーハンドリングだけ実装し、後から拡充したいとき

💻コード

この例で登場するクラスは4つ。リクエストを受けてからレスポンスを返すまでの流れは、次のようになる。

正常時
  1. ProductController が処理する
  2. 結果を ResponseEntity で包む
  3. 200 OK / 201 Created を返す
エラー時
  1. Service が ProductNotFoundException を投げる
  2. GlobalExceptionHandler が受け止める
  3. ErrorResponse を 404 Not Found で返す

以下では、ほかのクラスから使われる部品から順に見ていく。

1「見つからない」を表す独自例外を作る

ProductNotFoundException.java
public class ProductNotFoundException extends RuntimeException {
    public ProductNotFoundException(Long id) {
        super("Product not found: id=" + id);
    }
}
  • 役割: 指定したIDの商品が存在しないとき、Service がこの例外を投げる。Controller や GlobalExceptionHandler はこの例外を前提に書くので、最初に用意しておく。
  • RuntimeException を継承する: 非検査例外にするため。理由は次の補足で詳しく見る。

🔍 補足: なぜ RuntimeException を継承するのか

Exception を継承した場合（検査例外）と比べてみる。

✕Exception を継承した場合

ProductNotFoundException.java
public class ProductNotFoundException extends Exception {
    // ...（省略）
}

RuntimeException 以外の Exception を継承すると、検査例外になる。この例外を投げる可能性があるメソッドは、コンパイラから「catch するか throws を書くこと」を求められる。

ProductService.java
@Service
public class ProductService {

    // ...（省略）

    // 投げる側は throws が必要
    public ProductResponse findById(Long id) throws ProductNotFoundException {
        return productRepository.findById(id)
                .map(ProductResponse::from)
                .orElseThrow(() -> new ProductNotFoundException(id));
    }
}

orElseThrow で検査例外を投げるので、findById に throws ProductNotFoundException を書かないとコンパイルエラーになる。

ProductController.java
@RestController
public class ProductController {

    // ...（省略）

    // 呼び出す側にも throws が必要（または catch）
    @GetMapping("/{id}")
    public ResponseEntity<ProductResponse> getById(@PathVariable Long id)
            throws ProductNotFoundException {
        return ResponseEntity.ok(productService.findById(id));
    }
}

呼び出す findById が throws を宣言しているので、getById にも throws（または catch）が必要になる。Service の throws が、Controller にも広がってしまう。

✓RuntimeException を継承した場合

ProductNotFoundException.java
public class ProductNotFoundException extends RuntimeException {
    // ...（省略）
}

RuntimeException を継承すると、非検査例外になる。コンパイラは catch も throws も求めない。

ProductService.java
@Service
public class ProductService {

    // ...（省略）

    // throws 不要
    public ProductResponse findById(Long id) {
        return productRepository.findById(id)
                .map(ProductResponse::from)
                .orElseThrow(() -> new ProductNotFoundException(id));
    }
}

orElseThrow で例外を投げる点は同じだが、throws の宣言は要らない。

ProductController.java
@RestController
public class ProductController {

    // ...（省略）

    // throws も catch も不要
    @GetMapping("/{id}")
    public ResponseEntity<ProductResponse> getById(@PathVariable Long id) {
        return ResponseEntity.ok(productService.findById(id));
    }
}

throws も catch も書かなくてよい。投げられた例外はそのまま Controller の外へ抜けていき、手順4の GlobalExceptionHandler が受け止める。

2Controller で状況に合ったステータスコードを返す

ProductController.java
@RestController
@RequestMapping("/api/products")
public class ProductController {

    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    @GetMapping("/{id}")
    public ResponseEntity<ProductResponse> getById(@PathVariable Long id) {
        // 見つからなければ ProductNotFoundException が投げられる
        ProductResponse product = productService.findById(id);
        return ResponseEntity.ok(product); // 200 OK
    }

    @PostMapping
    public ResponseEntity<ProductResponse> create(@Valid @RequestBody ProductCreateRequest request) {
        ProductResponse created = productService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(created); // 201 Created
    }
}

📦 ResponseEntity で包む

Controller のメソッドが ProductResponse をそのまま返すと、ステータスコードは必ず 200 OK になる。ResponseEntity は「返すデータ」と「ステータスコード」をセットで持てる入れ物で、これで包むとステータスコードを自分で選べる。

<> の中には、返すデータの型を書く（この例では ResponseEntity<ProductResponse>）。

書き方ステータスコード使う場面
ResponseEntity.ok(product)200 OK取得に成功した（getById）
ResponseEntity.status(HttpStatus.CREATED).body(created)201 Created新しく作成した（create）

🚫 エラー時の処理は Controller に書かない

getById にも create にも try-catch がない。エラーが起きると例外がそのまま Controller の外へ抜けていき、手順4の GlobalExceptionHandler がまとめて受け止める。

404 Not Found

getById で商品が見つからない

Service が ProductNotFoundException を投げる

400 Bad Request

create で入力値が不正

Spring（@Valid による入力チェック）が MethodArgumentNotValidException を投げる

@Valid の入力チェックは、create の中身が実行される前に行われる。チェックのルールは、ProductCreateRequest のフィールドに付けた @NotBlank などのアノテーションで決める。

3エラー時に返すボディの形を決める

ErrorResponse.java
public record ErrorResponse(String message) {}

エラー時のレスポンスは、エラーの種類が違ってもすべてこの形で返す。404 でも 400 でも、返ってくるJSONは message というキーが1つあるだけで、違うのは中の文章だけになる。

404 Not Found（商品が見つからない）
{ "message": "Product not found: id=1" }
400 Bad Request（入力値が不正）
{ "message": "name: 空白は許可されていません" }

形をそろえる理由

✕形がばらばらだと

// 404
{ "error": "Product not found" }

// 400
{ "errors": [ ... ] }

クライアントは「404 なら error、400 なら errors 配列」と、エラーの種類ごとに読み取り方を書き分けることになる。

✓形がそろっていれば

// 404 も 400 も
{ "message": "..." }

「エラーが返ってきたら message を表示する」という処理を1つ書くだけで済む。

4例外を1か所でまとめて受け止める

GlobalExceptionHandler.java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 404: リソースが見つからない
    @ExceptionHandler(ProductNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(ProductNotFoundException ex) {
        ErrorResponse body = new ErrorResponse(ex.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(body);
    }

    // 400: @Valid によるバリデーションエラー
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
        String message = ex.getBindingResult().getFieldErrors().stream()
                .map(err -> err.getField() + ": " + err.getDefaultMessage())
                .collect(Collectors.joining(", "));
        return ResponseEntity.badRequest().body(new ErrorResponse(message));
    }
}

@RestControllerAdvice

クラスに付ける

このクラスを、すべての Controller に共通する「例外の受け皿」にする。どの Controller から例外が抜けてきても、ここで受け止められる。メソッドの戻り値は、@RestController と同じくJSONとしてレスポンスに書き込まれる。

@ExceptionHandler(例外.class)

メソッドに付ける

指定した例外が投げられたときに、このメソッドが呼ばれる。投げられた例外は引数（ex）で受け取れるので、ex.getMessage() などでエラーの内容を取り出せる。

どの例外が、どのメソッドで、何になるか

ProductNotFoundException → handleNotFound() → 404 Not Found
MethodArgumentNotValidException → handleValidation() → 400 Bad Request
  • handleNotFound: 例外のメッセージ（"Product not found: id=1"）をそのまま ErrorResponse に入れて返す。
  • handleValidation: ex.getBindingResult().getFieldErrors() で、チェックに引っかかった項目の一覧を取り出す。それを「フィールド名: メッセージ」の形にして ", " でつなぎ、1つの文章にして返す（例: "name: 空白は許可されていません, price: 0 以上の値にしてください"）。
