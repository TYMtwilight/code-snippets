@Valid とBean Validation

  • 📅 作成日: 2026-09-20
  • 🔄 更新日: 2026-09-20

🎯概要

@Validは、DTOに宣言された入力チェックのルール(Bean Validation)を「今チェックしろ」と実行させるアノテーション。ルールの「定義」(DTO側の@NotBlank等)と「チェックの実行」(Controller引数の@Valid)を分離することで、Controllerにif文だらけのチェックコードを書かずに済む。

📌使用場面

  • リクエストボディ(@RequestBody)の必須項目チェック・文字数制限・数値範囲チェックなどをControllerに書きたくないとき
  • 入力チェックのルールをDTOクラス側に集約し、使い回したいとき
  • @ExceptionHandler(MethodArgumentNotValidException.class)と組み合わせて、バリデーションエラーのレスポンス形式を統一したいとき

💻コード

DTOにルールを定義する

public class TodoRequest {

    @NotBlank(message = "タイトルは必須です")
    @Size(max = 100, message = "タイトルは100文字以内で入力してください")
    private String title;

    // getter / setter
}

Controllerでチェックを実行する

@PostMapping
public ResponseEntity<TodoResponse> create(
        @Valid @RequestBody TodoRequest request) {
    // ここに到達した時点で、バリデーションは通過済み
}

違反時にキャッチする(@ExceptionHandler)

@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
    String message = ex.getBindingResult().getFieldErrors().stream()
            .map(FieldError::getDefaultMessage)
            .collect(Collectors.joining(", "));
    return ResponseEntity.badRequest()
            .body(new ErrorResponse("VALIDATION_ERROR", message));
}

💡説明

1. そもそも何を解決したいのか

  • APIがリクエストを受け取るとき、「タイトルが空じゃないか」「文字数が長すぎないか」といった入力チェックが必要
  • これを手動でif文だらけにすると、Controllerがどんどん汚くなる

2. 「ルールの定義」と「チェックの実行」を分離する

  • Bean Validationでは、@NotBlankや@SizeのようなアノテーションでDTO側に「ルール」を宣言できる
  • これらはルールを定義しているだけで、この時点ではまだ何もチェックしていない
  • @ValidをControllerのメソッド引数に付けると、Springが「リクエストボディをDTOに変換する際、そのクラスに書かれたルールを実際にチェックしろ」と実行してくれる
何を書くかどこに書くか
ルールの定義(@NotBlank, @Sizeなど)DTOクラスのフィールド
ルールを今チェックしろという指示(@Valid)そのDTOを使う側(Controllerのメソッド引数)

⚠️ @Valid はどこに付ける？

TodoRequestクラス自体には@Validを付けない。@NotBlank/@Sizeは「制約(ルール)」を定義するだけのもので、@Validは「このルールを今チェックしろ」という指示だから、DTOを使う側(Controllerのメソッド引数)に付ける。

3. チェックに引っかかったらどうなるか

  • ルール違反があると、Springは自動的にMethodArgumentNotValidExceptionという例外を投げる。Controller内でif文を書く必要は一切ない
  • @ExceptionHandler(MethodArgumentNotValidException.class)がこの例外をキャッチし、ex.getBindingResult().getFieldErrors()で「どのフィールドがどう違反したか」の一覧を取り出す
  • 各フィールドの@NotBlank(message = "...")などで指定したメッセージを結合してレスポンスに詰める

4. handleValidation() のコードを1行ずつ読む

ex.getBindingResult()には、「どのフィールドが」「どんなルール違反をしたか」という情報が全部詰まっている。以下はその中身を取り出してレスポンス用の文字列に変換する処理。

String message = ex.getBindingResult()      // ① チェック結果を取得
        .getFieldErrors()                    // ② 違反したフィールドの一覧を取得(List<FieldError>)
        .stream()                            // ③ 1件ずつ処理するための流れに変換
        .map(FieldError::getDefaultMessage)  // ④ 各違反を「メッセージ文字列」に変換
        .collect(Collectors.joining(", "));  // ⑤ 複数のメッセージをカンマ区切りで1つの文字列に結合
処理役割
getBindingResult()入力チェックの結果全体(BindingResult)を取得
getFieldErrors()違反したフィールドの一覧(List<FieldError>)を取得。FieldErrorは「どのフィールドで」「どんなメッセージのエラーが起きたか」を持つオブジェクト
stream()リストの中身を1件ずつ処理していく「流れ作業のパイプライン」(Stream)に変換
map(FieldError::getDefaultMessage)各FieldErrorを、そのメッセージ文字列だけに変換する。message = "..."で指定した文言が返る
collect(Collectors.joining(", "))変換後の複数の文字列を、カンマ区切りの1つの文字列にまとめる
  • FieldError::getDefaultMessageはメソッド参照という書き方。fieldError -> fieldError.getDefaultMessage()というラムダ式と全く同じ意味で、「各要素を受け取ってそのメソッドを呼んだ結果を返す」処理を短く書ける
  • 例: titleが空文字かつ100文字超で送られてきた場合、["タイトルは必須です", "タイトルは100文字以内で入力してください"] → 結合後は "タイトルは必須です, タイトルは100文字以内で入力してください"

最後にレスポンスを組み立てる部分:

return ResponseEntity.badRequest()
        .body(new ErrorResponse("VALIDATION_ERROR", message));
  • ResponseEntity.badRequest()はResponseEntity.status(HttpStatus.BAD_REQUEST)の省略形。HTTPステータス400のレスポンスを作り始める
  • .body(new ErrorResponse("VALIDATION_ERROR", message))で、レスポンスボディに自作DTOをセットする。第1引数はエラー種別コード、第2引数が先ほど組み立てたメッセージ

5. 全体の流れ

クライアントが不正なリクエスト送信
  → @Valid が TodoRequest をチェック
  → NG なら MethodArgumentNotValidException が発生
  → @ExceptionHandler(MethodArgumentNotValidException.class) がキャッチして 400 を返す

6. よく使う制約アノテーション

アノテーション意味
@NotNullnullを許さない
@NotBlanknull・空文字・空白のみを許さない(文字列専用)
@NotEmptynull・空を許さない(文字列/コレクション)
@Size(min=, max=)文字数・要素数の範囲を指定
@Min / @Max数値の範囲を指定
@Emailメール形式かどうか
