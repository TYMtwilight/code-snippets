@Valid とBean Validation

  • 📅 作成日: 2026-09-20
  • 🔄 更新日: 2026-10-04

🎯概要

@Validは、DTOに定義した入力チェックのルール(Bean Validation)を、実際に実行させるためのアノテーション。ルールの「定義」はDTO側(@NotBlankなど)、「チェックの実行」はController側(引数の@Valid)と役割を分けることで、Controllerにif文でチェック処理を書き並べる必要がなくなる。

どの層の、どこに書くのか

@Validは主にController層で使い、Controllerメソッドの引数(DTOの前)に書く。

@RestController
@RequestMapping("/todos")
public class TodoController {

    @PostMapping
    public ResponseEntity<TodoResponse> create(
            @Valid @RequestBody TodoRequest request) {   // ← ここ
        ...
    }
}

クラスの上やメソッドの上には書かない。書くのはチェックしたい引数の直前だけ。

なぜControllerの引数なのか

役割書く場所
ルールの定義(@NotBlank, @Sizeなど)DTOクラスのフィールド
「今そのルールでチェックしろ」という指示(@Valid)DTOを受け取る側＝Controllerメソッドの引数

重要 1🚪 Controllerはアプリの入口。不正な入力はここで止める

外部から来たリクエストは、Controllerがアプリの入口で最初に受け取る。不正な入力は、Service層に渡す前にここで止めるのが基本。

リクエスト → Controllerここで止める → Service → Repository / DB

入口で止めておけば、Service より奥の処理は「データの中身は正しい」という前提で書ける。チェックが漏れると、不正なデータがDBまで届いてしまう。

重要 2⏱️ チェックはメソッド本体が動く前に終わる

@RequestBodyでJSONをDTOに変換した直後に、Springがバリデーションを実行する。違反があるとMethodArgumentNotValidExceptionが投げられ、メソッド本体は実行されない。

  • メソッド本体に入れた時点で、requestの中身はルールを満たしている。本体にチェック用のif文は要らない
  • 例外を投げるのはControllerではなくSpringなので、Controllerにtry-catchやthrowsは書かない。違反時の処理は@ExceptionHandlerに任せる(→ 4.)

💻コード

1. そもそも何を解決したいのか

  • APIでは「タイトルが空でないか」「長すぎないか」などの入力チェックが必要
  • これをif文で書くと、Controllerのコードが長く読みにくくなる

2. DTOにルールを定義する

public class TodoRequest {

    @NotBlank(message = "タイトルは必須です")
    @Size(max = 100, message = "タイトルは100文字以内で入力してください")
    private String title;

    // getter / setter
}
  • Bean Validationでは、@NotBlankや@SizeのようなアノテーションでDTO側に「ルール」を宣言できる
  • これらはルールを定義しているだけで、この時点ではまだ何もチェックしていない

3. Controllerでチェックを実行する

@PostMapping
public ResponseEntity<TodoResponse> create(
        @Valid @RequestBody TodoRequest request) {
    // ここに到達した時点で、バリデーションは通過済み
}
  • @ValidをControllerのメソッド引数に付けると、Springが「リクエストボディをDTOに変換する際、そのクラスに書かれたルールを実際にチェックしろ」と実行してくれる

⚠️ @Valid はどこに付ける？

@ValidはDTOクラス(TodoRequest)ではなく、DTOを受け取る側(Controllerのメソッド引数)に付ける。DTOの役割はルールを定義するところまでで、チェックの実行を指示するのは受け取る側の役割になる。

🔍 @Valid がない場合とある場合で、同じ不正なリクエスト {"title": ""} の行き先を比べる。

✕@Valid を付け忘れた場合

@PostMapping
public ResponseEntity<TodoResponse> create(
        @RequestBody TodoRequest request) {          // @Valid がない
    // title が "" のまま、ここまで来てしまう
    TodoResponse created = todoService.create(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(created);
}
{"title": ""} → Controller素通り → Service → DB空のタイトルで保存処理へ

DTOにルールが書いてあっても、チェックは実行されない。不正なデータが入口を通り抜けて、奥の処理まで届いてしまう。

✓@Valid を付けた場合

@PostMapping
public ResponseEntity<TodoResponse> create(
        @Valid @RequestBody TodoRequest request) {
    // ↑ メソッドが呼ばれる前に、Spring が次の2つを済ませている
    //   ① JSON を TodoRequest に変換する
    //   ② TodoRequest のルールでチェックする（違反なら例外を投げ、ここには来ない）

    // ここに来た request は、必ずルールを満たしている
    TodoResponse created = todoService.create(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(created);
}
{"title": ""} → Spring がチェックここで止まる → 400 Bad Request

Controllerのメソッド本体も、Service も DB も、一度も呼ばれない。

Controllerに書かなくてよいもの理由
チェック用の if文本体に来た時点で、ルールのチェックは終わっている
try-catch例外は本体が動く前に、Spring が投げる。違反時の処理は @ExceptionHandler に任せる(→ 4.)
throws例外を投げるのは Controller ではなく Spring だから(→ 4. の補足)

4. 違反時にキャッチする(@ExceptionHandler)

@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
    String message = ex.getBindingResult().getFieldErrors().stream()
            .map(FieldError::getDefaultMessage)
            .collect(Collectors.joining(", "));
    return ResponseEntity.badRequest()
            .body(new ErrorResponse("VALIDATION_ERROR", message));
}
  • ルール違反があると、Springは自動的にMethodArgumentNotValidExceptionという例外を投げる。Controller内でif文を書く必要は一切ない
  • @ExceptionHandler(MethodArgumentNotValidException.class)がこの例外をキャッチし、違反内容のメッセージをまとめて400エラーとして返す(処理の中身は5.で解説)

💡 補足: Controllerに throws も書かなくてよい

MethodArgumentNotValidExceptionは検査例外なので、通常なら投げるメソッドにthrowsを書く必要がある。

しかし、この例外を投げるのはSpringで、そのタイミングはControllerのメソッドが呼ばれる前。違反があった時点で、Controllerのメソッドは呼ばれないまま処理が終わる。そのため、Controllerにthrowsを書く必要はない。

5. handleValidation() のコードを1行ずつ読む

@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
    // 5-2. エラーメッセージを組み立てる
    String message = ex.getBindingResult().getFieldErrors().stream()
            .map(FieldError::getDefaultMessage)
            .collect(Collectors.joining(", "));

    // 5-3. レスポンスを返す
    return ResponseEntity.badRequest()
            .body(new ErrorResponse("VALIDATION_ERROR", message));
}

handleValidation()がしていることは、次の2つだけ。その前提として、まずBindingResultを理解しておく。

  1. 違反内容から、エラーメッセージの文字列を組み立てる(5-2)
  2. そのメッセージを入れて、400エラーのレスポンスを返す(5-3)

5-1. 前提: BindingResult とは

BindingResultは、リクエストの値をDTOに詰めてチェックした結果を記録しておく「成績表」のようなオブジェクト。Springが用意しているインターフェース。

名前は2つの言葉に分けると分かりやすい。

  • Binding(バインド): リクエストの値(JSONやフォームの値)を、DTOのフィールドに結びつけて詰めること
  • Result(結果): その詰め込みと、ルールによるチェックの結果

中で何が起きているか:

リクエスト{"title": ""}
  1. SpringがTodoRequestに値を詰める(バインド)
  2. @Validによって、@NotBlankなどのルールでチェックする
  3. 違反があれば、その内容をBindingResultに記録する

📋 BindingResult

FieldError

field
"title"
rejectedValue
""
defaultMessage
"タイトルは必須です"
  • 違反が1件あればFieldErrorが1つ、3件あれば3つ記録される
  • MethodArgumentNotValidExceptionは、このBindingResultを持った状態で投げられる。ex.getBindingResult()は、例外の中からそれを取り出すメソッド

💡 補足: BindingResult / FieldError のよく使うメソッド

メソッド取れるもの
bindingResult.getFieldErrors()違反したFieldErrorの一覧
bindingResult.hasErrors()違反が1件でもあるかどうか(true/false)
fieldError.getField()違反したフィールド名(例: "title")
fieldError.getRejectedValue()送られてきた値(例: "")
fieldError.getDefaultMessage()message = "..."で指定したメッセージ

5-2. エラーメッセージを組み立てる

BindingResultから違反メッセージだけを取り出し、1つの文字列にまとめる。

String message = ex.getBindingResult()      // ① チェック結果を取得
        .getFieldErrors()                    // ② 違反したフィールドの一覧を取得(List<FieldError>)
        .stream()                            // ③ 1件ずつ処理するための流れに変換
        .map(FieldError::getDefaultMessage)  // ④ 各違反を「メッセージ文字列」に変換
        .collect(Collectors.joining(", "));  // ⑤ 複数のメッセージをカンマ区切りで1つの文字列に結合
処理役割
getBindingResult()入力チェックの結果全体(BindingResult)を取得
getFieldErrors()違反したフィールドの一覧(List<FieldError>)を取得。FieldErrorは「どのフィールドで」「どんなメッセージのエラーが起きたか」を持つオブジェクト
stream()リストの中身を1件ずつ処理していく「流れ作業のパイプライン」(Stream)に変換
map(FieldError::getDefaultMessage)各FieldErrorを、そのメッセージ文字列だけに変換する。message = "..."で指定した文言が返る
collect(Collectors.joining(", "))変換後の複数の文字列を、カンマ区切りの1つの文字列にまとめる

例: titleに空白だけの101文字が送られてきた場合(@NotBlankと@Sizeの両方に違反)

getFieldErrors() + map(...) の結果
["タイトルは必須です", "タイトルは100文字以内で入力してください"]

↓ joining(", ") で結合

message の中身
"タイトルは必須です, タイトルは100文字以内で入力してください"

※ メッセージの並び順は保証されない。

💡 補足: FieldError::getDefaultMessage はメソッド参照

FieldError::getDefaultMessageはメソッド参照という書き方。fieldError -> fieldError.getDefaultMessage()というラムダ式と全く同じ意味で、「各要素を受け取ってそのメソッドを呼んだ結果を返す」処理を短く書ける。

メソッド参照では、メソッド名の後ろに()を付けない。::は「このメソッドを使ってね」とメソッドを指定するだけで、その場では呼び出さないから。実際に呼び出すのはmap()の側で、要素を1件ずつ渡しながら呼んでくれる。

書き方結果
.map(FieldError::getDefaultMessage)正しい(メソッド参照)
.map(fieldError -> fieldError.getDefaultMessage())正しい(ラムダ式。ここでは呼び出すので()が付く)
.map(FieldError::getDefaultMessage())コンパイルエラー

5-3. レスポンスを返す

組み立てたメッセージを入れて、400エラーのレスポンスを返す。

return ResponseEntity.badRequest()
        .body(new ErrorResponse("VALIDATION_ERROR", message));
  • ResponseEntity.badRequest()はResponseEntity.status(HttpStatus.BAD_REQUEST)の省略形。HTTPステータス400のレスポンスを作り始める
  • .body(new ErrorResponse("VALIDATION_ERROR", message))で、レスポンスボディに自作DTOをセットする。第1引数はエラー種別コード、第2引数が先ほど組み立てたメッセージ

6. 全体の流れ

  1. クライアントが不正なリクエストを送信
  2. @ValidがTodoRequestをチェック
  3. NGならMethodArgumentNotValidExceptionが発生Controllerのメソッド本体は実行されない
  4. @ExceptionHandler(MethodArgumentNotValidException.class)がキャッチして400を返す
