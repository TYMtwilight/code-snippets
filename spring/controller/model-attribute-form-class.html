Formクラスでリクエストパラメータを受け取る

  • 📅 作成日: 2026-01-29
  • 🔄 更新日: 2026-10-03

🎯概要

Spring BootでFormクラス（DTO）を使って、パラメータ形式（name=Taro&age=20 の形）で届くデータをまとめて受け取るパターン。

Thymeleafの画面専用の仕組みではない。React + REST APIの構成でも、JSON以外の形式で届くデータ（GETの検索条件、ファイルアップロードなど）はこの仕組みで受け取る。

📌使用場面

受け取り方は、画面の作り方ではなくフロントがどの形式でデータを送るかで決まる。

パラメータ形式で届く → Formクラスで受け取る

ケース届き方の例Content-Type
Thymeleafの画面からフォーム送信<form method="post"> の送信application/x-www-form-urlencoded
REST APIの検索（条件が多いGET）/users?name=Taro&minAge=20&page=0なし（URLのクエリ）
REST APIのファイルアップロードReactから FormData で送信multipart/form-data

JSONで届く → @RequestBody で受け取る

  • Reactから fetch(url, { body: JSON.stringify(data) }) で送る登録・更新APIなど
  • 受け取るクラスはrecordで書くのが主流
  • このスニペットの対象外

💻コード

1Formクラス（DTO）

UserSearchForm.java
package com.example.demo.user;

import lombok.Data;

@Data
public class UserSearchForm {
    private String name;     // 名前（部分一致）
    private Integer minAge;  // 最低年齢
    private Integer page;    // ページ番号
}
💡 ポイント

@Data（Lombok）でGetter/Setter/toString/equals/hashCode/必須フィールドのコンストラクタを自動生成

🔍 詳しく: @Data

1@Dataの中身

@Dataは、次の5つのLombokアノテーションをまとめて付けたのと同じ意味になる。

アノテーション生成されるもの
@Getter全フィールドのGetter（getName()など）
@Setterfinalでない全フィールドのSetter（setName(String)など）
@ToString全フィールドを並べたtoString()
@EqualsAndHashCode全フィールドを比較するequals()とhashCode()
@RequiredArgsConstructorfinalまたは@NonNullのフィールドを引数に取るコンストラクタ

UserSearchFormにはfinalフィールドがないので、@RequiredArgsConstructorが作るのは引数なしのコンストラクタになる。

❓ なぜfinalフィールドにしないのか

1

finalにするとSetterでバインドできなくなる

new UserSearchForm()空のオブジェクトを作る → setName("Taro") …Setterで1つずつ値を入れる

Springはこの順番で値を詰める（詳しくは下の「2. Formクラスで@Dataが役立つ理由」）。finalフィールドはSetterを作れず、コンストラクタで値を入れる必要があるので、どちらのステップも使えなくなる。

2

Formでは値が欠けているのが正常な状態

検索条件は、指定されたものだけが送られてくる。/users?name=Taroなら、minAgeとpageはnullのまま。finalで「必ず値が入っている」ことを保証する必要はない。

必須の条件があるなら、@NotNullなどのバリデーションでチェックする

💡 finalにしたい場合は、recordでも書ける。Springはコンストラクタの引数名とパラメータ名を突き合わせて、値をまとめて渡す（Spring 6 / Spring Boot 3以降）。

recordで書いた場合
public record UserSearchForm(String name, Integer minAge, Integer page) {}

Lombokを使わずに書くと、おおよそ次のコードと同じ。

Lombokなしで書いた場合
public class UserSearchForm {
    private String name;
    private Integer minAge;
    private Integer page;

    public UserSearchForm() {}  // 引数なしのコンストラクタ

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public Integer getMinAge() { return minAge; }
    public void setMinAge(Integer minAge) { this.minAge = minAge; }
    public Integer getPage() { return page; }
    public void setPage(Integer page) { this.page = page; }

    @Override
    public String toString() {
        return "UserSearchForm(name=" + name + ", minAge=" + minAge + ", page=" + page + ")";
    }

    // equals() と hashCode() も全フィールドを使って生成される（省略）
}

2Formクラスで@Dataが役立つ理由

Springは、リクエストパラメータを次の順番でUserSearchFormに詰める。

  1. ①引数なしのコンストラクタでnew UserSearchForm()を作る
  2. ②パラメータ名に対応するSetterを呼ぶname=TaroならsetName("Taro")、minAge=20ならsetMinAge(20)
💡 結論

引数なしのコンストラクタとSetterがあればバインドできる。@Dataはこの両方を1行で用意してくれる。

Controller側ではform.getName()のようにGetterで値を取り出せる。toString()もあるので、log.info("{}", form)で受け取った検索条件をそのままログに出せる。

3@Dataを使うときの注意

🚫 JPAのEntityには使わない方がよい

equals()/hashCode()が全フィールドを使うため、IDが採番される前後で値が変わってしまう。また、関連する（互いを参照し合う）Entity同士だとtoString()がお互いを呼び合ってStackOverflowErrorになる。

⚠️ 機密情報がログに出る

パスワードなどを持つクラスでは、toString()経由でログに出てしまう。該当フィールドに@ToString.Excludeを付けて除外する。

⚠️ 値を誰でも書き換えられる

Setterがあるので、作成後も値を変更できる。値を変えさせたくない場合は、上のrecordで書く方法がある。

2Controller

UserSearchController.java
package com.example.demo.user;

import java.util.List;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class UserSearchController {

    private final UserService userService;

    public UserSearchController(UserService userService) {
        this.userService = userService;
    }

    // GET /users?name=Taro&minAge=20&page=0
    @GetMapping("/users")
    public List<UserResponse> search(UserSearchForm form) {
        return userService.search(form);
    }
}
Reactから呼ぶ場合
const params = new URLSearchParams({ name: "Taro", minAge: "20", page: "0" });
// GET /users?name=Taro&minAge=20&page=0
const res = await fetch(`/users?${params}`);
const users = await res.json();
💡 ポイント
  • クエリパラメータを1つずつ@RequestParamで受けると引数が増えるので、Formクラスでまとめて受け取る
  • パラメータ名と一致するSetterをSpringが呼んで値を入れる（name=TaroならsetName("Taro")）。@DataはそのSetterを生成しているだけで、名前の突き合わせはSpringの仕事
  • 指定されなかったパラメータはnullになる。検索条件は「指定がなければ絞り込まない」ことが多いので相性がよい
🔍 詳しく: @RequestParamとは

クエリパラメータを1つずつメソッド引数で受け取るアノテーション。

基本の書き方
// GET /users?name=Taro
@GetMapping("/users")
public List<UserResponse> search(@RequestParam String name) {
    ...
}

引数名とパラメータ名が一致すれば値が入る。必須かどうかやデフォルト値は、次のように指定する。

書き方意味
@RequestParam String name必須。パラメータがないと400 Bad Requestになる
@RequestParam(required = false) Integer minAge任意。パラメータがなければnull
@RequestParam(defaultValue = "0") Integer page任意。パラメータがなければ0（指定すると自動で任意扱いになる）
@RequestParam("min_age") Integer minAgeパラメータ名（min_age）と引数名が違うときに名前を指定する

Formクラスと比べると

今回の検索条件を@RequestParamで受けると、次のようになる。

@RequestParamで書いた場合
@GetMapping("/users")
public List<UserResponse> search(
        @RequestParam(required = false) String name,
        @RequestParam(required = false) Integer minAge,
        @RequestParam(defaultValue = "0") Integer page) {
    return userService.search(name, minAge, page);
}
💡 使い分け
  • パラメータが1〜2個なら@RequestParamで十分。必須・デフォルト値もアノテーションだけで指定できる
  • パラメータが多い・増えそうならFormクラス。引数が1つで済み、Serviceにもそのまま渡せる。条件が増えてもControllerのシグネチャは変わらない
📏 上のコードは@ModelAttributeを省略した形

上のsearch(UserSearchForm form)には何もアノテーションが付いていないが、実際には@ModelAttributeが省略されている。省略せずに書くと次のようになり、動きはまったく同じ。

上のコード（省略形）
public List<UserResponse> search(UserSearchForm form)
省略せずに書いた場合
public List<UserResponse> search(@ModelAttribute UserSearchForm form)

省略できるのは、アノテーションが付いていない引数がFormクラスのようなオブジェクトの場合、Spring MVCが自動的に@ModelAttributeとして扱うから。実務では省略形で書くことが多い。

🔍 詳しく: 省略されている@ModelAttributeの役割
  • 上のコードでは、送られてきたname・minAge・pageパラメータをUserSearchFormのフィールドに自動バインドしているのが、この省略された@ModelAttribute
  • 読み取る対象はリクエストパラメータ（URLのクエリ文字列と、x-www-form-urlencoded・multipart/form-dataのボディ）。JSONのボディは読まない

3ファイルアップロードでの使用例

ファイルはJSONに入れられないので、REST APIでもmultipart/form-data（パラメータ形式）で送る。これもFormクラスで受け取れる。

ProfileForm.java
@Data
public class ProfileForm {
    private String displayName;
    private MultipartFile icon;  // ファイルもフィールドとして受け取れる
}
ProfileController.java
@RestController
public class ProfileController {

    @PostMapping("/profile")
    public String update(ProfileForm form) {
        return form.getDisplayName() + " / " + form.getIcon().getOriginalFilename();
    }
}
Reactから送る場合
const body = new FormData();
body.append("displayName", "Taro");
body.append("icon", file);  // <input type="file"> で選んだファイル

// FormData を body に渡すと multipart/form-data になる（Content-Typeは指定しない）
await fetch("/profile", { method: "POST", body });
💡 ポイント

appendした名前とFormクラスのフィールド名が一致すれば、テキストもファイルもまとめて受け取れる。

4@RequestBodyとの違い

Formクラス（@ModelAttribute）@RequestBody
読み取る対象リクエストパラメータリクエストボディのJSON
Content-Typex-www-form-urlencoded
multipart/form-data
（GETのクエリも可）		application/json
変換するものSpringのDataBinderJackson
主な用途検索条件、ファイルアップロード、画面のフォーム送信REST APIの登録・更新
🚫 よくあるミス: JSONを送っているのに@RequestBodyを付け忘れる
✕ 全フィールドがnull
// JSONで送られてくるのに @RequestBody がない
@PostMapping("/users")
public UserResponse register(UserRequest request) {
    ...
}

アノテーションがないので@ModelAttributeとして扱われ、Springはリクエストパラメータを探す。JSONのボディは読まないため、エラーにならずに全フィールドがnullのまま処理が進む。逆に、@RequestBodyを付けた引数にパラメータ形式で送ると415 Unsupported Media Typeになる。
