DIの考え方 — コンストラクタインジェクションとレイヤー分離

  • 📅 作成日: 2026-09-21
  • 🔄 更新日: 2026-09-21

🎯概要

フィールドインジェクションではなくコンストラクタインジェクションを使う理由と、@Service層/@Repository層を分けてControllerに直接DB処理を書かない設計意図を整理する。

📌使用場面

  • 新しい@Serviceクラスを実装するとき
  • クラス間の依存関係を設計するとき
  • 単体テストを書きやすい構造にしたいとき

💻コード

悪い例: フィールドインジェクション

@Service
public class SnippetService {

    @Autowired
    private SnippetRepository snippetRepository; // finalにできない、テストで差し替えにくい

    public SnippetReviewDto findById(Long id) {
        Snippet snippet = snippetRepository.findById(id)
                .orElseThrow(() -> new SnippetNotFoundException(id));
        return SnippetReviewDto.from(snippet, calculateNextReview(snippet));
    }
}

良い例: コンストラクタインジェクション

@Service
public class SnippetService {

    private final SnippetRepository snippetRepository; // finalにできる = 不変
    private final ReviewScheduleCalculator reviewScheduleCalculator;

    public SnippetService(SnippetRepository snippetRepository,
                           ReviewScheduleCalculator reviewScheduleCalculator) {
        this.snippetRepository = snippetRepository;
        this.reviewScheduleCalculator = reviewScheduleCalculator;
    }

    public SnippetReviewDto findById(Long id) {
        Snippet snippet = snippetRepository.findById(id)
                .orElseThrow(() -> new SnippetNotFoundException(id));
        LocalDateTime nextReview = reviewScheduleCalculator.calculate(snippet);
        return SnippetReviewDto.from(snippet, nextReview);
    }
}

// テストではSpringコンテキストを起動せず、直接newしてモックを渡せる
@Test
void findById_returnsSnippet() {
    SnippetRepository mockRepo = mock(SnippetRepository.class);
    ReviewScheduleCalculator mockCalc = mock(ReviewScheduleCalculator.class);
    SnippetService service = new SnippetService(mockRepo, mockCalc);
    // ...
}
  • コンストラクタインジェクションの利点:
    • フィールドをfinalにできるため、初期化後に依存が差し替わらないことが保証される(不変性)。
    • コンストラクタの引数を見るだけで「このクラスが何に依存しているか」が一目でわかる(暗黙のフィールド注入より依存が明示的)。
    • Springのコンテキストを起動しなくても、new Service(mockA, mockB)のように直接インスタンス化してユニットテストが書ける。フィールドインジェクションだとリフレクションを使うか@SpringBootTest相当の重いテストになりがち。

レイヤー分離: ControllerはServiceだけを見る

@RestController
@RequestMapping("/api/snippets")
public class SnippetController {

    private final SnippetService snippetService; // SnippetRepositoryではない

    public SnippetController(SnippetService snippetService) {
        this.snippetService = snippetService;
    }

    @GetMapping("/{id}")
    public ResponseEntity<SnippetReviewDto> getById(@PathVariable Long id) {
        return ResponseEntity.ok(snippetService.findById(id));
    }
}
  • @Service層と@Repository層を分ける意味: Controllerは「HTTPリクエスト/レスポンスの変換」に、Serviceは「業務ロジック」に、Repositoryは「永続化(DBアクセス)」に、それぞれ責務を限定する。ControllerがEntityやSQLを直接扱い始めると、HTTPの都合と業務ロジックとDBアクセスが混ざり、変更の影響範囲が広がりテストもしづらくなる。
  • Lombokを使う場合、@RequiredArgsConstructorでfinalフィールドのコンストラクタを自動生成でき、上記のボイラープレートを省略できる。
