@ExceptionHandler - 例外を受け取ってレスポンスに変える

  • 📅 作成日: 2026-09-26
  • 🔄 更新日: 2026-09-30

🎯概要

@ExceptionHandler は、Controller の処理中に投げられた例外を受け取り、それをHTTPレスポンス(ステータスコード＋ボディ)に変換するメソッドに付けるアノテーション。Controller のメソッド本体から try-catch を追い出し、「正常系の処理」と「エラー時の返し方」を分けて書けるようになる。

実務では、@ExceptionHandler メソッドは @RestControllerAdvice を付けた専用クラスにまとめて書くのが基本。こうすると、すべての Controller で起きた例外を1か所で受け取れて、Controller には正常系の処理だけが残る。

🔍 用語ノート: 例外ハンドラ(Exception Handler)

例外が起きたときに呼ばれる専用のメソッドのこと。Controller のメソッドが例外を投げると、Spring はその例外を横取りし、型が合う @ExceptionHandler メソッドを探して呼び出す。ハンドラの戻り値が、そのままクライアントへのレスポンスになる。見つからなければ Spring Boot の既定のエラーレスポンス(500 など)が返る。

🔍 用語ノート: @RestControllerAdvice

複数の Controller に共通する処理(例外ハンドラなど)を、Controller の外にまとめて置くためのアノテーション。@ControllerAdvice と @ResponseBody を合わせたもので、ハンドラの戻り値がそのままJSONのレスポンスボディになる。

「Advice」の由来: AOP
AOP(Aspect-Oriented Programming／アスペクト指向プログラミング)は、ログ出力・トランザクション・例外処理のように多くのクラスに共通する処理を本体のコードから切り離し、「横から差し込む」ための考え方。「Advice(助言)」は AOP の用語で、この「本体の処理に横から差し込む処理」のことを指す。

🔍 補足: 「try-catch を追い出して、正常系とエラー時を分ける」とはどういうことか

Before: @ExceptionHandler を使わず、Controller で try-catch する

@GetMapping("/{id}")
public ResponseEntity<?> findById(@PathVariable Long id) {
    try {
        UserResponse user = userService.findById(id);           // ← 正常系(本当にやりたいこと)
        return ResponseEntity.ok(user);
    } catch (UserNotFoundException e) {                         // ← エラー時の返し方 ①
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorBody("USER_NOT_FOUND", e.getMessage()));
    } catch (Exception e) {                                     // ← エラー時の返し方 ②
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new ErrorBody("INTERNAL_ERROR", "予期しないエラーが発生しました"));
    }
}

@PutMapping("/{id}")
public ResponseEntity<?> update(@PathVariable Long id, @RequestBody UserForm form) {
    try {
        return ResponseEntity.ok(userService.update(id, form));
    } catch (UserNotFoundException e) {                         // ← findById と同じ catch をコピペ
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorBody("USER_NOT_FOUND", e.getMessage()));
    } catch (Exception e) {                                     // ← これもコピペ
        ...
    }
}

1つのメソッドの中に「ユーザーを取ってきて返す」という正常系と、「例外をステータスコード＋エラーボディに変える」というエラー時の処理が混ざっている。これが次のような問題を生む。

  • 本題が埋もれる: 本当にやりたいことは userService.findById(id) の1行なのに、メソッドの大半が catch で占められる
  • 同じ catch がメソッドの数だけ増える: 「UserNotFoundException なら404」という同じルールを、findById・update・delete…と、さらに OrderController などにも書くことになる
  • 返し方がばらつく: ある場所ではコードを "NOT_FOUND"、別の場所では "USER_NOT_FOUND" と書いてしまう、catch を書き忘れて500になる、といったずれが起きやすい
  • 戻り値の型があいまいになる: 成功時は UserResponse、失敗時は ErrorBody を返すので、戻り値を ResponseEntity<?> にするしかない。メソッドの宣言を見ても、何を返すAPIなのか分からない
  • 変更に弱い: エラーボディの形式を変えたくなったら、すべての catch を探して直すことになる

After: try-catch を追い出し、2か所に分けて書く

// 正常系: Controller には「うまくいったら何を返すか」だけを書く
@GetMapping("/{id}")
public UserResponse findById(@PathVariable Long id) {
    return userService.findById(id);
}

@PutMapping("/{id}")
public UserResponse update(@PathVariable Long id, @RequestBody UserForm form) {
    return userService.update(id, form);
}

// エラー時: 「どの例外を、どのレスポンスに変えるか」は GlobalExceptionHandler に1回だけ書く
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ErrorBody> handleUserNotFound(UserNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorBody("USER_NOT_FOUND", ex.getMessage()));
    }
}
  • Controller のメソッドは1行になり、戻り値の型も UserResponse とはっきり書ける
  • 「UserNotFoundException → 404」のルールは1か所だけ。どの Controller のどのメソッドで起きても同じレスポンスになる
  • エラー形式を変えるときは GlobalExceptionHandler だけを直せばよい
書く場所書く内容
正常系Controllerリクエストを受けて Service を呼び、成功したときの結果を返す
エラー時の返し方GlobalExceptionHandler例外の種類ごとに、ステータスコードとエラーボディを決める

追い出した catch は、誰がやっているのか

try-catch が消えても、例外が放置されるわけではない。Controller の外へ飛び出した例外は、Controller を呼び出した Spring(DispatcherServlet)が受け止める。つまり catch の役目を Spring が引き受け、受け止めた後の処理として @ExceptionHandler メソッドを呼んでいる。 

// Spring が内部でやっていることのイメージ(疑似コード)
try {
    Object result = userController.findById(id);        // 正常系: Controller を呼ぶ
    レスポンスに書き出す(result);
} catch (Exception ex) {
    Method handler = 型が合う @ExceptionHandler を探す(ex);
    Object result = handler.invoke(ex);                  // エラー時: ハンドラを呼ぶ
    レスポンスに書き出す(result);
}

Controller に書いていた try と catch のうち、try の中身だけが Controller に残り、catch の中身が @ExceptionHandler メソッドに移った、と考えると分かりやすい。

すべての try-catch が不要になるわけではない

追い出すのは「例外をレスポンスに変えるための catch」。後述の「検査例外を非検査例外に包み直す」ための catch(Service に書く)は目的が違うので、そのまま書く。また、例外が起きても処理を続けたい(例: 外部APIが失敗したら既定値を使う)ような場面も、その場で catch するのが正しい。

📌使用場面

  • 「ユーザーが見つからない → 404」のように、独自例外を特定のステータスコードとエラーボディに対応付けたいとき
  • 各 Controller メソッドに try-catch を書かず、エラー時の返し方をアプリ全体で1か所にまとめたいとき(@RestControllerAdvice に書く)
  • API 全体でエラーレスポンスの形式をそろえたいとき

💻コード

1. 基本形: 例外ハンドラを @RestControllerAdvice に集約する

独自例外: RuntimeException を継承する

public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(Long id) {
        super("ユーザーが見つかりません: id=" + id);
    }
}

🔍 補足: これは「検査例外を非検査例外に包み直す」ための例外ではない

UserNotFoundException は、最初の例外を自分で作るための独自例外。ユーザーが見つからないとき、userRepository.findById() は例外を投げず、空の Optional を返すだけなので、包む元になる検査例外はそもそも存在しない。「見つからない」という状況を、orElseThrow の中で自分で new して例外として表している。そのため、コンストラクタに cause(元の例外)を受け取る引数もない。

後述の ReportNotFoundException が、包み直し用の例外。コンストラクタを見比べると違いが分かる。

// 包み直し用: 元の検査例外(NoSuchFileException)を cause として受け取る
public ReportNotFoundException(Long id, Throwable cause) {
    super("レポートが見つかりません: id=" + id, cause);
}

// 最初から作る用: cause はない
public UserNotFoundException(Long id) {
    super("ユーザーが見つかりません: id=" + id);
}
UserNotFoundExceptionReportNotFoundException
元の例外なし(空の Optional から自分で作る)NoSuchFileException(検査例外)がライブラリから届く
目的「ユーザーが見つからない」という業務上の意味を例外で表す届いた検査例外を、業務上の意味を持つ非検査例外に作り直す
cause 引数なしあり
  • orElseThrow に検査例外を作る処理(() -> new Exception(...) など)を渡すと、呼び出し側に throws が必要になる。そのため非検査例外を渡すのが普通
  • findById() が DB 接続エラーなどで失敗したときは、Spring が DataAccessException(非検査例外)を投げる。これも catch 不要で、GlobalExceptionHandler の Exception 用ハンドラで 500 として返る

では、なぜ RuntimeException を継承しているのか

包み直しとは関係なく、独自の業務例外は非検査例外で作るのが Spring での定番だから。Service や Controller に throws を書かなくて済み、呼び出し元で個別に catch せず @ExceptionHandler でまとめて処理する設計と相性がよい。詳しくは後述の「補足: Controller に throws を書かなくていいのはなぜ?」を参照。

Service: 見つからなければ独自例外を投げる

@Service
public class UserService {

    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    // 非検査例外を投げるので、メソッド宣言に throws は不要
    public UserResponse findById(Long id) {
        User user = userRepository.findById(id)
                .orElseThrow(() -> new UserNotFoundException(id));
        return UserResponse.from(user);
    }
}

Controller: 正常系の処理だけを書く

// try-catch も @ExceptionHandler も書かない
@RestController
@RequestMapping("/api/users")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @GetMapping("/{id}")
    public UserResponse findById(@PathVariable Long id) {
        // Service が UserNotFoundException を投げても、そのまま外へ飛び出す(throws も不要)
        return userService.findById(id);
    }
}

🔍 補足: Controller に throws を書かなくていいのはなぜ?

UserService が投げる UserNotFoundException が、RuntimeException を継承した非検査例外だから。非検査例外は throws を書かなくても、メソッドの外へそのまま飛び出していける。そのため UserService.findById() にも UserController.findById() にも throws がない。

検査例外と非検査例外の違い

種類親クラスthrows例
検査例外(checked)Exception(RuntimeException 以外)必須(書かないとコンパイルエラー)IOException, SQLException
非検査例外(unchecked)RuntimeException不要IllegalArgumentException, NullPointerException

もし検査例外にしたら

extends Exception(検査例外)にすると、例外が通過する Service・Controller のメソッドすべてに throws が必要になる。throws を書けば @ExceptionHandler で同じように受け取れるが、記述が煩雑になる。

// 検査例外にした場合(非推奨)
public class UserNotFoundException extends Exception { ... }

// Service にも Controller にも throws が必要になる
public UserResponse findById(Long id) throws UserNotFoundException { ... }

@GetMapping("/{id}")
public UserResponse findById(@PathVariable Long id) throws UserNotFoundException {
    return userService.findById(id);
}

そのため Spring では、独自の業務例外は RuntimeException を継承して作るのが定番。

  • メソッドごとに throws を並べなくて済む
  • 「呼び出し元で個別に対処せず、@ExceptionHandler で1か所にまとめて処理する」設計と相性がよい

ライブラリが投げる検査例外は、Service で非検査例外に包み直す

IOException のようにライブラリが用意した例外は、検査例外として作られているので、使う側が非検査例外に変えることはできない。このときは Service で catch し、業務的な意味を持つ非検査例外を作り直して投げる(「包み直す」)。こうすれば Controller に throws を書かずに済み、@ExceptionHandler ではその非検査例外を受け取ればよい。

例外クラス(ReportNotFoundException.java):

// 包み直し用の非検査例外: 元の例外を cause として受け取る
public class ReportNotFoundException extends RuntimeException {
    public ReportNotFoundException(Long id, Throwable cause) {
        super("レポートが見つかりません: id=" + id, cause);
    }
}

Service(ReportService.java):

// Service: 検査例外を catch して、非検査例外に包み直す
public ReportResponse loadReport(Long id) {
    try {
        String content = Files.readString(Path.of("reports", id + ".txt"));
        return new ReportResponse(id, content);
    } catch (NoSuchFileException e) {
        throw new ReportNotFoundException(id, e);   // 元の例外 e を必ず渡す
    }
}

例外ハンドラ(GlobalExceptionHandler.java):

// GlobalExceptionHandler: 包み直した非検査例外を受け取って 404 にする
@ExceptionHandler(ReportNotFoundException.class)
public ResponseEntity<ErrorBody> handleReportNotFound(ReportNotFoundException ex) { ... }

元の例外 e を第2引数(cause)に渡しておくと、ログに Caused by: java.nio.file.NoSuchFileException ... と本当の原因が残る。

例外ハンドラ: すべての Controller の例外がここに届く

@RestControllerAdvice
public class GlobalExceptionHandler {

    // どの Controller で UserNotFoundException が投げられても、ここが呼ばれる
    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ErrorBody> handleUserNotFound(UserNotFoundException ex) {
        ErrorBody body = new ErrorBody("USER_NOT_FOUND", ex.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(body);
    }

    // 最後の砦: 個別のハンドラがない想定外の例外は 500 で返す
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorBody> handleUnexpected(Exception ex) {
        ErrorBody body = new ErrorBody("INTERNAL_ERROR", "予期しないエラーが発生しました");
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(body);
    }
}

エラーレスポンス用のDTO

public record ErrorBody(String code, String message) {}

GET /api/users/99 で該当ユーザーがいない場合のレスポンス(ステータス 404 Not Found):

{
  "code": "USER_NOT_FOUND",
  "message": "ユーザーが見つかりません: id=99"
}

処理の流れ

  1. Service

    例外が投げられる

    UserService.findById() の中で UserNotFoundException が投げられる。

  2. Service → Controller → Spring

    例外が外へ飛び出す

    例外は Service から Controller へ、さらに Controller の外へ飛び出し、Spring(DispatcherServlet)が受け取る。

  3. Spring

    扱えるハンドラを探す

    「この例外を扱える @ExceptionHandler はあるか」を探す。まず投げた Controller の中を見て、なければ @RestControllerAdvice のクラスを見る。

  4. GlobalExceptionHandler

    ハンドラが呼ばれる

    handleUserNotFound() が見つかり、呼ばれる。

  5. クライアント

    レスポンスが返る

    ハンドラが返した ResponseEntity が、そのままクライアントへのレスポンス(404 Not Found)になる。

ハンドラは Controller から切り離されているので、OrderController など別の Controller で同じ UserNotFoundException が投げられても、同じ 404 のレスポンスが返る。

2. ハンドラメソッドの書き方(対象の例外・引数・戻り値)

@ExceptionHandler メソッドは、次の3つの部分でできている。それぞれに複数の書き方がある。

@ExceptionHandler(UserNotFoundException.class)              // ① 対象の例外: どの例外を受け取るか
public ResponseEntity<ErrorBody>                            // ③ 戻り値: どんなレスポンスを返すか
        handleUserNotFound(UserNotFoundException ex) {       // ② 引数: 何を受け取るか
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorBody("USER_NOT_FOUND", ex.getMessage()));
}

以下のコードは、いずれも GlobalExceptionHandler(@RestControllerAdvice)の中に書くメソッド。書き方の比較のために並べているので、同じ例外を扱うハンドラを実際に同じクラスへ2つ書くとエラーになる(→「3. どのハンドラが選ばれるか」)。

2-1. 対象の例外を指定する

書き方受け取る例外
@ExceptionHandler(UserNotFoundException.class)指定した例外(基本形)
@ExceptionHandler(値なし)メソッド引数に書いた例外の型
@ExceptionHandler({A.class, B.class})列挙した複数の例外
@ExceptionHandler(親クラス.class)その親クラスを継承したすべての例外

値を省略する: 次の2つは同じ意味になる。

@ExceptionHandler(UserNotFoundException.class)
public ResponseEntity<ErrorBody> handle(UserNotFoundException ex) { ... }

@ExceptionHandler   // 値なし → 引数の型 UserNotFoundException が対象になる
public ResponseEntity<ErrorBody> handle(UserNotFoundException ex) { ... }

複数の例外を1つのメソッドで扱う: 引数は、列挙した例外に共通する親クラスで受ける。

@ExceptionHandler({UserNotFoundException.class, OrderNotFoundException.class})
public ResponseEntity<ErrorBody> handleNotFound(RuntimeException ex) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorBody("NOT_FOUND", ex.getMessage()));
}

親クラスを指定する: そのサブクラスの例外もまとめて届く。例外が増えても、ハンドラを書き足さなくて済む。

public class NotFoundException extends RuntimeException { ... }
public class UserNotFoundException extends NotFoundException { ... }
public class OrderNotFoundException extends NotFoundException { ... }

@ExceptionHandler(NotFoundException.class)   // User〜 も Order〜 も受け取る
public ResponseEntity<ErrorBody> handleNotFound(NotFoundException ex) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorBody("NOT_FOUND", ex.getMessage()));
}

2-2. 引数で受け取るもの

発生した例外オブジェクトを受け取り、ex.getMessage() でメッセージを取り出してレスポンスに詰めるのが定番。例外のほかに HttpServletRequest(リクエストURLのログ出力など)、WebRequest、Locale なども受け取れる。

// 例外と一緒にリクエスト情報も受け取り、ログに残す
@ExceptionHandler(UserNotFoundException.class)
public ResponseEntity<ErrorBody> handleUserNotFound(UserNotFoundException ex,
                                                    HttpServletRequest request) {
    log.warn("{} {} : {}", request.getMethod(), request.getRequestURI(), ex.getMessage());
    // → GET /api/users/99 : ユーザーが見つかりません: id=99
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorBody("USER_NOT_FOUND", ex.getMessage()));
}

例外オブジェクトを使わないなら、引数なしでもよい。

@ExceptionHandler(UserNotFoundException.class)
public ResponseEntity<Void> handleUserNotFound() {
    return ResponseEntity.notFound().build();
}

2-3. 戻り値でレスポンスを決める

@RestControllerAdvice には @ResponseBody が含まれているので、戻り値はJSONに変換されてレスポンスボディになる(@RestController のハンドラと同じ)。戻り値の書き方は主に3通り。

戻り値ステータスの決め方向いている場面
A. ResponseEntity<DTO>メソッドの中で組み立てるステータスやヘッダーを自由に決めたい(基本はこれ)
B. DTO@ResponseStatus で固定するステータスが常に同じで、短く書きたい
C. ProblemDetail生成時に指定するエラー形式を自前で決めず、標準形式に合わせたい

A. ResponseEntity を返す: ステータス・ヘッダー・ボディをすべてメソッドの中で組み立てる。

@ExceptionHandler(UserNotFoundException.class)
public ResponseEntity<ErrorBody> handleUserNotFound(UserNotFoundException ex) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorBody("USER_NOT_FOUND", ex.getMessage()));
}

B. DTO だけを返す: ステータスは @ResponseStatus で固定する。

@ExceptionHandler(IllegalArgumentException.class)
@ResponseStatus(HttpStatus.BAD_REQUEST)
public ErrorBody handleBadRequest(IllegalArgumentException ex) {
    return new ErrorBody("BAD_REQUEST", ex.getMessage());
}

ステータスコードに注意
DTOだけを返して @ResponseStatus も付けないと、エラーなのに 200 OK が返ってしまう。

// NG: ステータスを指定していないので 200 OK でエラーボディが返る
@ExceptionHandler(UserNotFoundException.class)
public ErrorBody handle(UserNotFoundException ex) {
    return new ErrorBody("USER_NOT_FOUND", ex.getMessage());
}

C. ProblemDetail を返す(Spring 6 / Spring Boot 3 以降): エラーレスポンスの標準形式(RFC 9457)で返す。

@ExceptionHandler(UserNotFoundException.class)
public ProblemDetail handleUserNotFound(UserNotFoundException ex) {
    return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
}

レスポンス(ステータス 404 Not Found):

{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "ユーザーが見つかりません: id=99",
  "instance": "/api/users/99"
}

@ControllerAdvice と間違えない
@ResponseBody を含まない @ControllerAdvice に書いてDTOを返すと、戻り値がJSONにならず、ビュー名として扱われてしまう。REST API では @RestControllerAdvice を使う。

// NG: @ControllerAdvice だと、ErrorBody がJSONにならない
@ControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(UserNotFoundException.class)
    public ErrorBody handle(UserNotFoundException ex) { ... }
}

// OK: @RestControllerAdvice なら、ErrorBody がJSONのボディになる
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(UserNotFoundException.class)
    public ErrorBody handle(UserNotFoundException ex) { ... }
}

3. どのハンドラが選ばれるか(優先順位)

状況呼ばれるハンドラ
GlobalExceptionHandler に Exception 用と UserNotFoundException 用がある 投げられた例外に継承関係がより近い方(UserNotFoundException 用)
Controller 内と @RestControllerAdvice の両方に同じ例外用がある Controller 内の方(個別の設定が全体の設定より優先)
同じクラスに、同じ例外を扱うハンドラが2つある どちらを呼ぶか決められないため IllegalStateException(Ambiguous @ExceptionHandler method)

この仕組みがあるので、基本形のように「最後の砦」として @ExceptionHandler(Exception.class) を置いても、より具体的なハンドラの邪魔にはならない。

4. 例外的な使い方: Controller 内に書く

@ExceptionHandler は Controller クラスの中にも書ける。ただしそのハンドラはその Controller で起きた例外だけを扱い、他の Controller には効かない。そのため、使うのは「基本は GlobalExceptionHandler の返し方でよいが、この Controller だけは別の返し方にしたい」という場合に限られる。

@RestController
@RequestMapping("/api/legacy/users")
public class LegacyUserController {

    // 旧クライアント向けAPIだけ、見つからないときに 404 ではなく 204 を返す必要がある
    // → GlobalExceptionHandler の handleUserNotFound() より、こちらが優先される
    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<Void> handleUserNotFound(UserNotFoundException ex) {
        return ResponseEntity.noContent().build();
    }
}

「とりあえず Controller 内に書く」を繰り返すと、同じハンドラが Controller ごとに増え、エラーの返し方もばらついていく。上書きしたい理由がないなら @RestControllerAdvice に書く。

5. 捕まえられない例外

  • Filter で起きた例外: Spring Security の認証エラーなど、Controller に届く前の Filter で投げられた例外は、@RestControllerAdvice でも受け取れない。Filter や Security 側の仕組み(AuthenticationEntryPoint など)で処理する
  • ハンドラ自身が投げた例外: @ExceptionHandler メソッドの中でさらに例外が起きると、他のハンドラには回されず既定のエラー処理(500)になる
  • Advice の適用範囲外の Controller: @RestControllerAdvice(basePackages = "com.example.api") のように範囲を絞ると、範囲外の Controller の例外は受け取らない(指定しなければ全 Controller が対象)
