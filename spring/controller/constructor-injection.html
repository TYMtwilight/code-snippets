フィールドインジェクションではなくコンストラクタインジェクションを使う理由

  • 📅 作成日: 2026-09-21
  • 🔄 更新日: 2026-10-03

🎯概要

依存オブジェクトの受け取り方として、フィールドインジェクションではなくコンストラクタインジェクションを使うべき理由をまとめる。

💻コード

✕ 悪い例フィールドインジェクション

@Service
public class UserService {

    @Autowired
    private UserRepository userRepository; // final を付けられない、テストでモックに差し替えにくい

    public List<User> getAllUsers() {
        return userRepository.findAll();
    }
}
🔍 詳しく: フィールドインジェクションのデメリット
💡 結論

UserService は、仕事をするために UserRepository を使います。このように、あるクラスが動くのに必要な別のオブジェクトを「依存」と呼びます。

フィールドインジェクションを使うと、userRepository フィールドが null のままの UserService を作れてしまうという弱点があります。本来、final を付ければ、こうしたミスはコンパイラが防いでくれます。しかし、フィールドインジェクションでは final を付けられません。

以下では、「なぜ final を付けられないのか」と「付けられないと何が困るのか」を順に説明します。

1final のルール

final を付けたフィールドには、Javaで次のルールが決められています。

📏 ルール

宣言時か、コンストラクタの中で、必ず1回だけ値を代入しなければならない

ルールを守っていない例
✕ コンパイルエラー
public class Sample {
    private final int count;

    public Sample() {
        // コンストラクタの中で count に値を代入していない → コンパイルエラー
    }
}
ルールを守っている例
✓ OK
public class Sample {
    private final int count;

    public Sample(int count) {
        this.count = count;  // コンストラクタの中で count に値を代入している → OK
    }

    public int getCount() {
        return count;
    }
}
このルールで何が保証されるか

ルールを守っている方の Sample クラスを使ってみます。

Sample sample = new Sample(10);
sample.getCount();  // 10 が返る

1行目の new Sample(10) を実行すると、まずコンストラクタが動き、count に 10 が代入されます。コンストラクタの処理が終わると、できあがったオブジェクトが変数 sample に入ります。

final フィールドには、コンストラクタの中で値を代入する決まりがあります。そのため、変数 sample にオブジェクトが入った時点で、count の値はもう決まっています。2行目以降で sample を使うときも、count には必ず値が入っています。

2フィールドインジェクションで final を付けられない理由

Springが値を入れる手順
@Service
public class UserService {
    @Autowired
    private UserRepository userRepository;
}

Springは、このクラスを次の順番で準備します。

  1. ①new UserService() を実行するコンストラクタが動く（userRepository はまだ null）
  2. ②コンストラクタが終わり、オブジェクトができあがる
  3. ③Springが userRepository に値を入れる

③では、Springがリフレクション（private フィールドでも外から書き換えられる仕組み）を使って値を入れます。

final のルールと比べる

上の手順に、final のルールを書き足すと次のようになります。

  1. ①new UserService() を実行するコンストラクタが動く⏰ final フィールドは、ここで値を入れる必要がある
  2. ②コンストラクタが終わるここが締め切り
  3. ③Springが値を入れる
    💉 フィールドインジェクションは、ここで値を入れる

final フィールドには、コンストラクタが終わるまでに値を入れなければなりません。いわば「コンストラクタの終わり」が締め切りです。

ところが、フィールドインジェクションでは、Springが値を入れるのはコンストラクタが終わった後です。締め切りに間に合いません。

コンパイラから見た状況
✕ コンパイルエラー
@Autowired
private final UserRepository userRepository;  // コンパイルエラー

コンパイラはソースコードを読み、コンストラクタの中に userRepository への代入があるかを確認します。しかし、代入はどこにも書かれていません。

@Autowired は「後でSpringが値を入れる」という目印です。ただし、コンパイラはこの目印の意味を知りません。そのため、「final なのに、コンストラクタの中で代入していない」と判断して、エラーにします。

このように、フィールドインジェクションでは final を付けられません。

3final を付けられないと何が困るか

困ること① Repositoryを渡し忘れても、実行するまで気づけない

上の悪い例の UserService を、Springを使わずにテストしてみます。

@Test
void getAllUsersのテスト() {
    UserService service = new UserService();  // コンパイルは通る
    service.getAllUsers();                    // ここでエラーになる
}

このコードはコンパイルできます。しかし、テストを実行すると次のエラーで失敗します。

実行結果
java.lang.NullPointerException: Cannot invoke "UserRepository.findAll()"
    because "this.userRepository" is null

Springを使わずに new UserService() でオブジェクトを作ったので、③の処理が行われていません。そのため、userRepository は null のままです。この状態で userRepository.findAll() を呼んだので、エラーになりました。

⚠️ ここが問題

final が付いていれば、渡し忘れはコンパイルの時点で分かります。しかし、フィールドインジェクションでは、実行するまで分かりません。

困ること② テストでモックを渡すのが面倒

テストでは、本物のデータベースにつながないよう、偽物のRepository（モック）を UserService に渡すのが一般的です。ところが、普通に書こうとすると、どれもコンパイルエラーになります。

✕ コンパイルエラー
@Test
void getAllUsersのテスト() {
    UserRepository mockRepo = Mockito.mock(UserRepository.class);
    UserService service = new UserService();

    service.userRepository = mockRepo;      // コンパイルエラー（private なので外から代入できない）
    service.setUserRepository(mockRepo);    // コンパイルエラー（このメソッドは存在しない）
    new UserService(mockRepo);              // コンパイルエラー（このコンストラクタは存在しない）
}

フィールドは private で、セッターも引数付きのコンストラクタもありません。そのため、通常のJavaの書き方ではモックを渡せず、次のどちらかの方法を使うことになります。

方法A：リフレクションでフィールドを書き換える

@Test
void getAllUsersのテスト() {
    UserRepository mockRepo = Mockito.mock(UserRepository.class);
    UserService service = new UserService();

    // フィールド名を文字列で指定して、private フィールドに値を入れる
    ReflectionTestUtils.setField(service, "userRepository", mockRepo);

    service.getAllUsers();
}

フィールド名を文字列で指定しているので、後でフィールド名を変えても、コンパイラは間違いを指摘してくれません。

方法B：Springを起動してモックを入れてもらう

@SpringBootTest
class UserServiceTest {

    @MockitoBean
    UserRepository mockRepo;

    @Autowired
    UserService service;

    @Test
    void getAllUsersのテスト() {
        service.getAllUsers();
    }
}

テストしたいのは UserService だけです。それでもSpringのアプリ全体を起動するので、テストに時間がかかります。

✓ 良い例コンストラクタインジェクション

@Service
public class UserService {

    private final UserRepository userRepository; // final を付けられる = 不変

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;  // コンストラクタの中で代入
    }

    public List<User> getAllUsers() {
        return userRepository.findAll();
    }
}
🔍 詳しく: コンストラクタインジェクションで何が変わるか

4コンストラクタインジェクションの場合

上の良い例では、Springは①でコンストラクタを呼ぶときに、UserRepository を引数として渡します。代入がコンストラクタの中にあるので、締め切りに間に合います。そのため、final を付けられます。

@Autowired を書かなくてよい理由

良い例のコードには @Autowired がありません。Spring 4.3以降では、コンストラクタが1つしかないクラスであれば、Springがそのコンストラクタを自動で使い、必要なオブジェクトを渡してくれるからです。

// コンストラクタが1つだけなので、@Autowired は省略できる
public UserService(UserRepository userRepository) { ... }

コンストラクタが2つ以上ある場合、Springはどれを使えばよいか判断できません。その場合は、使ってほしいコンストラクタに @Autowired を付けます。

テストコード
@Test
void getAllUsersのテスト() {
    UserRepository mockRepo = Mockito.mock(UserRepository.class);

    UserService service = new UserService();          // コンパイルエラー（引数が足りない）
    UserService service = new UserService(mockRepo);  // 正しい書き方

    service.getAllUsers();
}
✅ 解決できること
困ること①Repositoryを渡し忘れても、実行するまで気づけない
→
解決渡し忘れると、その場でコンパイルエラーになる
困ること②テストでモックを渡すのが面倒
→
解決モックは引数で渡すだけ。リフレクションもSpringの起動も要らない

✓まとめ

フィールドインジェクションコンストラクタインジェクション
値を入れるタイミングコンストラクタが終わった後コンストラクタの中
final付けられない付けられる
Repositoryの渡し忘れ実行するまで分からないコンパイル時に分かる
テストでモックを渡す方法リフレクションか、Springの起動が必要引数で渡すだけ
💡 ひとことで

フィールドインジェクションでは、値が入るのはコンストラクタが終わった後です。そのため final を付けられず、Repositoryの渡し忘れをコンパイラが見つけられません。テストも書きにくくなります。

🌟 コンストラクタインジェクションの利点

🔒

依存が途中で変わらない

フィールドに final を付けられるので、一度入れた UserRepository を後から差し替えることはできません。

👀

何に依存しているかが一目で分かる

コンストラクタの引数を見れば、このクラスが使うオブジェクトがすべて分かります。

🧪

テストが書きやすい

new UserService(mockRepo) のように、Springを起動せずにモックを渡してテストできます。
