Controllerにおける例外の対処法 - 検査例外・非検査例外

  • 📅 作成日: 2026-09-26

🎯概要

  1. 検査例外と非検査例外: RuntimeException の子孫なら非検査例外(対処は任意)、それ以外の Exception の子孫なら検査例外(対処しないとコンパイルエラー)
  2. throw と try-catch: throw で発生した例外は、try-catch で受け止められるまで呼び出し元へさかのぼる
  3. throws の役割: 例外を投げることがあると知らせる宣言。必要なのは、検査例外を catch せず呼び出し元へ渡すときだけ
  4. 検査例外と非検査例外を分ける理由: 検査例外はプログラムの外が原因(ファイルがない、通信が切れた)で、コードでは防げないので、対応を強制する。非検査例外はプログラムの中が原因(バグ、不正な値)で、コードを直せば防げるので、強制せずに予防する
  5. Webアプリで例外が起きたとき: 例外で止まるのはそのリクエストだけ。Spring が @ExceptionHandler などを使ってエラーレスポンスを返す
  6. Controller での対処法: Controller では try-catch を書かない。Service で検査例外を非検査例外に包み直し、@RestControllerAdvice で HTTP レスポンスに変換する
  7. やってはいけない対処: 例外の握りつぶし、とりあえずの throws Exception、何でも catch (Exception e)
  8. 対処の使い分け: 対処は「予防」「回復」「最後に受け止める」の3種類を使い分ける

🔍 用語ノート: 例外(Exception)を「投げる」とは

処理を続けられない異常が起きたとき、「何が起きたか」を表すオブジェクト(例外)を作り、今の処理を中断して呼び出し元へ放り投げること。投げられた例外がどう進むかは、下の 2. で説明する。

1. 例外の2種類と、例外クラスの家系図

Java の例外は、次の2種類に分かれる。

  • 検査例外: 対処を書かないとコンパイルエラーになる(例: IOException)
  • 非検査例外: 対処を書かなくてもコンパイルできる(例: IllegalArgumentException)

どちらの種類になるかは「先祖に RuntimeException がいるかどうか」だけで決まる。NumberFormatException は IllegalArgumentException の子で、その親が RuntimeException なので非検査例外になる。

代表的な例外

例外種類いつ起きるか性質
IOException検査ファイルが読めない、通信が切れたプログラムが正しくても起こりうる(外部要因)
SQLException検査DBに接続できない、SQLの実行に失敗した外部要因
IllegalArgumentException非検査メソッドに不正な値が渡された呼び出し側の誤り
NullPointerException非検査null に対してメソッドを呼んだプログラムのバグ
Exception検査(すべての例外の親として、まとめて受け取るときに使う)—

2. 例外の発生と受け止め(throw と try-catch)

2-1. 例外を発生させる(throw)

例外は throw 文で発生させる。throw new 例外クラス(メッセージ) の形で、例外オブジェクトを作って投げる。throw が実行された瞬間にそのメソッドの処理は中断され、後ろの行は実行されない。

public void validate(Long id) {
    if (id <= 0) {
        throw new IllegalArgumentException("id は1以上");   // ここで例外を発生させる
    }
    System.out.println("チェックOK");   // id が 0 以下なら、この行は実行されない
}

なお、NullPointerException や ArithmeticException(0 での割り算)のように、throw 文を書かなくても JVM が自動で発生させる例外もある。

2-2. 例外を受け止める(try-catch)か、呼び出し元へさかのぼるか

発生した例外は、try-catch で受け止めることができる。例外が起きうる処理を try で囲み、catch に受け止めたときの処理を書く。catch した時点で例外はそこで止まり、それより上の呼び出し元には伝わらない。

public void register(Long id) {
    try {
        validate(id);
        System.out.println("登録しました");   // validate() で例外が起きたら、実行されない
    } catch (IllegalArgumentException e) {   // 飛んできた例外をここで受け止める
        System.out.println("入力エラー: " + e.getMessage());
    }
    System.out.println("処理終了");           // 受け止めた後は、ここから処理が続く
}

catch は、実行時に飛んできた例外の型を見て動く。catch (IllegalArgumentException e) の IllegalArgumentException は受け止める例外の型で、飛んできた例外がその型に当てはまれば受け止め、当てはまらなければ素通りする。当てはまるのは同じクラスだけでなく、親クラスや先祖クラスを指定した場合も含む。

try {
    validate(id);   // IllegalArgumentException が飛んでくる
} catch (RuntimeException e) {        // ✅ 親クラスなので受け止められる
}

try {
    validate(id);
} catch (Exception e) {               // ✅ 先祖クラスなので受け止められる
}

try {
    validate(id);
} catch (IllegalStateException e) {   // ❌ 兄弟クラスなので素通りし、呼び出し元へさかのぼる
}

複数の型を受け止めたいときは、次の2つの書き方がある。

  • catch を複数並べる: 上から順に判定され、最初に当てはまった catch だけが実行される。子クラスを先に書く必要があり、親クラスを先に書くと、後ろの子クラスの catch に届かないためコンパイルエラーになる
  • 1つの catch に | で複数の型を書く(マルチキャッチ): 受け止めたときの処理が同じ場合に使う
// catch を複数並べる
try {
    validate(id);
} catch (IllegalArgumentException e) {   // 先に判定される
    System.out.println("入力エラー");
} catch (RuntimeException e) {           // 上に当てはまらなかった RuntimeException 系がここに来る
    System.out.println("想定外のエラー");
}

// マルチキャッチ
try {
    validate(id);
} catch (IllegalArgumentException | IllegalStateException e) {
    System.out.println("エラー: " + e.getMessage());
}

try-catch がなければ、例外は呼び出し元へ飛び出す。呼び出し元にも try-catch がなければ、さらにその呼び出し元へ、と受け止められるまで順にさかのぼっていく。例外が通過したメソッドは、どれもその場で処理が中断される。最後まで誰も catch しなければ、プログラム(Webアプリならそのリクエストの処理)が異常終了する。

public void handle(Long id) {
    register(id);                        // ③ register() からも飛び出してくる
    System.out.println("完了");          // 実行されない
}

public void register(Long id) {
    validate(id);                        // ② validate() から例外が飛び出してくる
    System.out.println("登録しました");   // 実行されない
}

public void validate(Long id) {
    if (id <= 0) {
        throw new IllegalArgumentException("id は1以上");   // ① ここで発生
    }
}

この例で register() に先ほどの try-catch があれば、例外は register() で止まり、handle() には伝わらない。

3. throws の定義と、使う必要がある場面

3-1. throws の定義

throws は throw と名前は似ているが、別物。

  • 書く場所: メソッド宣言の末尾
  • 役割: 「このメソッドは例外を投げることがある」と呼び出し元に知らせる
public void check(int id) throws IOException {   // throws: この例外を投げることがあると宣言する
    throw new IOException("失敗");                // throw: 実際に例外を発生させる
}

注意したいのは、throws を書かなくても例外は呼び出し元へ飛んでいくこと。次の2つは、実行したときの動きがまったく同じになる。

// A: throws なし(2. の validate() と同じ)
public void validate(Long id) {
    if (id <= 0) {
        throw new IllegalArgumentException("id は1以上");
    }
}

// B: throws あり
public void validate(Long id) throws IllegalArgumentException {
    if (id <= 0) {
        throw new IllegalArgumentException("id は1以上");
    }
}

public void register(Long id) {
    validate(id);   // A でも B でも、例外はここへ飛んでくる
}

例外を呼び出し元へ飛ばしているのは throw と、2-2 で見た「さかのぼる」仕組みで、throws ではない。throws は例外を外へ出すための仕組みではなく、「このメソッドはこの例外を投げることがある」とコンパイラと呼び出し元に知らせる宣言だ。

3-2. throws を使う必要があるとき

throw で例外を投げるときに、いつも throws が必要なわけではない。

throws が必要になるのは、検査例外をメソッドの中で catch せず、呼び出し元へそのまま渡すときだけ。検査例外には「その場で処理する(catch)か、呼び出し元に任せると宣言する(throws)か」のどちらかが必須で、これを Catch or Specify ルールと呼ぶ。

投げる例外メソッドの中で catch するかthrows
非検査例外(IllegalArgumentException、自作の RuntimeException 系など)どちらでもよい不要
検査例外(IOException など)する不要
検査例外(IOException など)しない(呼び出し元へ渡す)必要
// ✅ 非検査例外は、throws を書かなくても throw できる
public void validate(Long id) {
    if (id <= 0) {
        throw new IllegalArgumentException("id は1以上");
    }
}

// ✅ 検査例外でも、メソッドの中で catch すれば throws は要らない
public String readOrDefault(Path path) {
    try {
        return Files.readString(path);
    } catch (IOException e) {
        return "";
    }
}

// ❌ 検査例外を呼び出し元へ渡すのに throws がないと、コンパイルエラーになる
public void save() {
    throw new IOException("失敗");
}
// error: unreported exception IOException; must be caught or declared to be thrown
//        (IOException が処理されていない。catch するか、throws で宣言すること)

このルールが守られているかは、コンパイル時にコンパイラが確かめている。確かめる手順は次のとおりで、メソッドごとに行われる。

  1. メソッドの中で、検査例外が発生しうる箇所を探す。該当するのは次の2つ。
    • throw new IOException(...) のように、自分で検査例外を投げている文
    • Files.readString() のように、検査例外を投げることがあるメソッドを呼んでいる箇所(呼ばれる側のメソッドが throws IOException と宣言している)
  2. その例外が try-catch で捕まえられているかを確認する
  3. 捕まえられていなければ、メソッド宣言に throws があるかを確認する
  4. どちらもなければ、コンパイルエラーにする

throws で宣言した場合は、今度は呼び出す側が同じチェックを受ける。

public String load(Path path) throws IOException {   // ✅ 宣言したので load() はOK
    return Files.readString(path);
}

public void show(Path path) {
    String text = load(path);   // ❌ 今度は show() が「catch するか、throws で宣言して」と言われる
}

呼び出す側も throws で済ませると、その呼び出し元がまたチェックを受ける。こうして Repository → Service → Controller と、呼び出し経路すべてに throws が広がっていく(検査例外の連鎖)。

非検査例外については、コンパイラはこのチェックを一切しない。そのため throws で宣言しなくても、catch しなくても、コンパイルは通る。なお、3-1 の B のように非検査例外に throws を書くこともできるが、その場合も呼び出し元に対処は強制されず、「この例外が起きることがある」と伝える説明の役割だけを持つ。

🔍 補足: 検査例外に限っては、宣言がないと catch も書けない

検査例外については、try の中で投げられる可能性がない(宣言されていない)ものを catch すると、コンパイルエラーになる。起こりえない例外を catch する、無意味なコードを防ぐためのルールだ。

try {
    System.out.println("hello");       // IOException を投げる可能性がない
} catch (IOException e) {              // ❌ exception IOException is never thrown in body of corresponding try statement
}

そのため検査例外では、結果として「宣言されていないものは catch できない」関係になっている。ただし、これは宣言の目的ではなく副次的なルール。catch (Exception e) のような親クラスでの catch は、この制限を受けない。

4. なぜ検査例外と非検査例外に分けるのか

非検査例外は、対処を書かなくてもコンパイルが通る。だからといって、放っておいてよいわけではない。どちらの例外にも対処は必要で、違うのは対処の方法だ。対処の方法が分かれるのは、2種類の例外で原因の性質が違うためだ。

検査例外非検査例外
原因プログラムの外(ファイルがない、通信が切れた)プログラムの中(バグ、不正な値)
正しく書けば防げる?防げない。コードが完璧でもファイルは消えうる防げる。null チェックや入力チェックで事前に避けられる
適した対処起きた後に回復する(再試行、別の値で続行、利用者に知らせる)起きる前に予防する(コードを直す)

検査例外: 防げないから、気づかせて忘れさせない

検査例外の原因(ファイルがない、通信が切れた)は、コードを正しく書いても防げない。そのため、呼び出す側は起きたときの対応を必ず用意しておく必要がある。

ところが、呼び出す側のプログラマーは、メソッドの中身までは読まないことが多い。たいていは public String load(Path path) throws IOException のようなメソッドの宣言(1行目)だけを見て、使い方を判断する。もし宣言がなければ、どんな例外が飛んでくるかに気づけず、catch を書こうとすら思わない。そこで Java は、次の2段構えにしている。

  1. 呼ばれる側に throws で宣言させる(知らせる)
  2. 呼び出す側に catch か throws を書かせる(忘れさせない)

この2段構えで、気づかずに放置する事態を防いでいる。強制されるのは「その場で処理すること」ではなく「どう対応するか決めること」なので、その場で処理できなければ throws で呼び出し元に任せてもよい。

非検査例外: 対処を強制すると、コードが破綻する

NullPointerException はほぼすべてのメソッド呼び出しで起こりうる。IllegalArgumentException、配列の範囲外アクセス、0 での割り算も同様。これらに対処を強制すると、次のようになる。

try {
    String name = user.getName();          // NullPointerException の可能性
    try {
        int age = Integer.parseInt(input); // NumberFormatException の可能性
        ...
    } catch (NumberFormatException e) { ??? }
} catch (NullPointerException e) { ??? }
  • 全行が try-catch だらけになる
  • しかも catch の中に書くことがない。原因はバグなので、その場で正しく回復する方法が存在しない

非検査例外への正しい対処は、catch ではなく予防。

if (user == null) { ... }                  // null を事前にチェック
@Valid @RequestBody UserRequest request    // 入力を Controller の入口で検証

それでも漏れたものは、最後に @ExceptionHandler(Exception.class) が受け止めて 500 を返し、ログに残す。

🔍 補足: 予防しきれなかった例外を @ExceptionHandler(Exception.class) で受け止める流れ

たとえば、null チェックを忘れたバグがあるとする。try-catch はどこにも書いていないので、例外はこの Controller の外へ飛び出す。

@RestController
public class UserController {
    @GetMapping("/api/users/{id}")
    public UserResponse get(@PathVariable Long id) {
        User user = userService.find(id);          // 見つからないと null が返る
        return new UserResponse(user.getName());   // null チェックを忘れた → NullPointerException
    }
}

これを受け止めるのが、アプリに1つだけ作る「最後の受け皿」。@RestControllerAdvice を付けたクラスに書くと、すべての Controller に共通で効く。

@RestControllerAdvice   // すべての Controller に共通で効く
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(Exception.class)   // Exception とその子孫 = ほぼすべての例外を受け止める
    public ResponseEntity<ErrorResponse> handleUnexpected(Exception e) {
        log.error("想定外のエラー", e);                      // ① スタックトレースごとログに残す
        return ResponseEntity
                .status(HttpStatus.INTERNAL_SERVER_ERROR)   // ② 500 を返す
                .body(new ErrorResponse("サーバーでエラーが発生しました"));
    }
}

実際に GET /api/users/99 でバグが起きると、次のように動く。

  1. クライアントが GET /api/users/99 を送る
  2. Controller で NullPointerException が発生し、Controller の外へ飛び出す
  3. Spring が @ExceptionHandler(Exception.class) の handleUnexpected() を呼ぶ
  4. サーバーのログに、次のように出力される 
    ERROR ... 想定外のエラー
java.lang.NullPointerException: Cannot invoke "User.getName()" because "user" is null
    at com.example.UserController.get(UserController.java:6)
  5. クライアントに、次のレスポンスが返る 
    500 Internal Server Error
{"message": "サーバーでエラーが発生しました"}

この仕組みのポイントは、次の2つ。

ポイント1: Controller ごとに try-catch を書かなくていい

@RestControllerAdvice の受け皿を1つ作れば、すべての Controller のすべてのメソッドに自動で効くので、Controller は正常な処理だけを書けばよい。

ポイント2: クライアントとログで、見せる情報を分ける

例外には、クラス名、ファイルのパス、SQL 文など、アプリの内部の情報が含まれることがある。これをそのままクライアントに返すと、攻撃者にアプリの作りを知る手がかりを与えてしまう。しかも利用者にとっては意味のない情報だ。

// ❌ 例外のメッセージをそのまま返した場合
{"message": "Cannot invoke \"User.getName()\" because \"user\" is null"}

// ✅ 中身を伏せた場合
{"message": "サーバーでエラーが発生しました"}

一方、開発者がバグを直すには詳しい情報が必要になる。そこで詳細はサーバーのログにだけ残す。

まとめると

  • 検査例外: 原因はプログラムの外 → コードを直しても防げない → どう対応するかを必ず決めさせる(その場で処理するか、呼び出し元に任せるか)
  • 非検査例外: 原因はプログラムの中 → コードを直して予防すべき → 対応は任意(漏れたものは最後の受け皿で受け止める)

5. 例外で処理が止まったらどうなるか(Webアプリの場合)

Webアプリで例外が起きても、止まるのはそのリクエストの処理だけ。サーバー全体が止まるわけではなく、同時に来ている他のリクエストは普通に処理される。止まったリクエストにも、「エラーでした」という返事がきちんと返る。

たとえば GET /api/reports/99 の処理中に、「レポートが見つからない」という例外が起きた場合の流れは次のとおり。

  1. クライアントが GET /api/reports/99 を送る
  2. Controller → Service と処理が進む
  3. Service で ReportNotFoundException が throw される。Service と Controller の残りの処理は実行されない(ここが「止まる」)
  4. 例外が Controller の外へ飛び出し、Spring が受け取る
  5. Spring が、この例外を扱う @ExceptionHandler メソッドを探して呼ぶ
  6. クライアントに、404 Not Found とエラー内容の JSON が返る

404 や 400、500 は、レスポンスの結果を表す HTTPステータスコード。クライアントはこれを見て、「入力を直して送り直す」「見つかりませんと表示する」のように次の動きを決める。

コード意味例外の例
400 Bad Requestリクエストの内容がおかしい(クライアント側の問題)IllegalArgumentException
404 Not Found指定されたものが存在しないReportNotFoundException(自作)
500 Internal Server Errorサーバー側で想定外の失敗が起きたNullPointerException などのバグ

例外ごとにどのステータスで返すかを決めるのが @ExceptionHandler の役割。対応するハンドラがなくても、サーバーが落ちることはなく、Spring が用意した受け皿がエラーレスポンスを返す(下の補足を参照)。いずれにしても、処理を止めてエラーを返すことも立派な対処。

むしろ、無理に処理を続ける方が危険な場合がある。

try {
    paymentService.charge(order);      // 決済に失敗
} catch (Exception e) {
    // 何もせず続行…
}
orderService.markAsPaid(order);        // ❌ お金を受け取っていないのに「支払済み」になる

おかしな状態のまま進むより、止めてエラーを返す方が安全。目指すのは「止めないこと」ではなく、止まったときに正しく後始末とエラー応答をすること。

🔍 補足: 対応する @ExceptionHandler が見つからなかったら?

例外が Controller の外へ飛び出すと、Spring は次の順に受け皿を試し、最初に当てはまったものでレスポンスを返す。

  1. 対応する @ExceptionHandler はある?
    → あれば、そのメソッドがレスポンスを作る(ここで終わり)
  2. Spring 自身が定義している「よくある例外」?
    → Spring が決めたステータスで返す
  3. どれにも当てはまらない
    → Spring Boot の既定エラー処理が 500 を返す

① 対応する @ExceptionHandler がある例外

「対応する」とは、@ExceptionHandler に指定した型に、飛んできた例外が当てはまること。catch と同じく、同じクラスだけでなく親クラスや先祖クラスを指定した場合も当てはまる。当てはまるハンドラが複数あれば、いちばん近い型(より具体的な型)のハンドラが選ばれる。

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ReportNotFoundException.class)   // ReportNotFoundException はここ → 404
    public ResponseEntity<ErrorResponse> handleNotFound(ReportNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorResponse(e.getMessage()));
    }

    @ExceptionHandler(Exception.class)                 // それ以外の例外はここ → 500
    public ResponseEntity<ErrorResponse> handleUnexpected(Exception e) {
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new ErrorResponse("サーバーでエラーが発生しました"));
    }
}

ReportNotFoundException はどちらのハンドラにも当てはまるが、型が近い handleNotFound() が選ばれる。なお、@ExceptionHandler(Exception.class) を用意していると、ほぼすべての例外が①で受け止められるので、②・③には進まない。

② Spring が扱い方を知っている例外(一部)

例外起きる場面ステータス
MethodArgumentNotValidException@Valid の入力チェックに失敗400
HttpMessageNotReadableException送られてきたJSONが壊れている400
MissingServletRequestParameterException必須のクエリパラメータがない400
HttpRequestMethodNotSupportedExceptionGET用のURLにPOSTした405

これらは、Controller のメソッドを呼ぶ前後で Spring 自身が投げる例外。リクエストの JSON を読み取ったり、@Valid で入力をチェックしたりするのは Spring の仕事なので、そこで失敗したときにどのステータスを返すかも、Spring があらかじめ決めている。

たとえば @Valid のチェックに失敗すると、Spring が MethodArgumentNotValidException を投げ、上の表のとおり 400 を返す。JSON は③と同じ形なので、どの項目がダメだったかは含まれない。詳細を返したい場合は、この例外用の @ExceptionHandler を自分で書く。

③ どれにも当てはまらない例外

①・②のどちらにも当てはまらない例外は、Spring Boot がまとめて 500 で返す。たとえば次のような例外がここに来る。

  • 対応する @ExceptionHandler がない自作例外
  • NullPointerException のようなバグ

このとき、サーバーとクライアントには次のものが残る。

  • サーバーのログ: 例外のスタックトレース(どこで何が起きたか)が ERROR として出力される
  • クライアント: 次のような既定の JSON が返る
{
  "timestamp": "2026-09-26T10:00:00.000+00:00",
  "status": 500,
  "error": "Internal Server Error",
  "path": "/api/reports/99"
}

このJSONに例外のメッセージが含まれないのは、内部の情報を外に漏らさないよう、Spring Boot の初期設定でメッセージを出さないようにしているため。

6. Controller での対処法: 非検査例外にして Spring に任せる

Controller のメソッドは、自分で呼び出すものではなく、HTTPリクエストが来たときに Spring が呼び出すもの。つまり Controller の呼び出し元は Spring だ。

2-2 で見たとおり、例外は catch されなければ呼び出し元へさかのぼる。Controller で catch しなかった例外は、呼び出し元の Spring に届き、Spring が @ExceptionHandler を探してHTTPレスポンスに変換してくれる。そのため、Controller では例外を catch せず、Spring に任せればよい。

❌ よくない例: Controller の中で try-catch する

// Service 側が throws IOException と宣言している前提
@GetMapping("/{id}")
public ResponseEntity<?> findReport(@PathVariable Long id) {
    try {
        return ResponseEntity.ok(reportService.loadReport(id));
    } catch (NoSuchFileException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body("見つかりません");
    } catch (IOException e) {
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body("エラー");
    }
}
// → 全メソッドに同じ try-catch が並び、エラーの形式もメソッドごとにバラバラになりがち

ただし、IOException のような検査例外をそのまま Spring まで流そうとすると問題がある。3-2 の Catch or Specify ルールにより、Service にも Controller にも throws IOException を書き続けなければならない。

そこで、Service で検査例外を catch し、非検査例外を作り直して投げる。これを「包み直す」という。非検査例外なら catch も throws も要らないので、Controller は何も書かずに例外を Spring まで流せる。作り直すときに ReportNotFoundException のような名前を付けておけば、「見つからない → 404」のように返し方も決めやすくなる。

✅ よい例: 層ごとに役割を分ける

① 包み直し用の例外クラス: RuntimeException を継承し(非検査例外)、元の検査例外を cause として受け取る

public class ReportNotFoundException extends RuntimeException {
    public ReportNotFoundException(Long id, Throwable cause) {
        super("レポートが見つかりません: id=" + id, cause);
    }
}

public class ReportStorageException extends RuntimeException {
    public ReportStorageException(String message, Throwable cause) {
        super(message, cause);
    }
}

② Service: 検査例外を catch し、意味のある非検査例外に「包み直す」(Controller に throws を書かせないため)

@Service
public class ReportService {

    public ReportResponse loadReport(Long id) {
        try {
            String content = Files.readString(Path.of("reports", id + ".txt"));
            return new ReportResponse(id, content);
        } catch (NoSuchFileException e) {                 // 子クラス(IOException の子)を先に
            throw new ReportNotFoundException(id, e);     // 元の例外 e を原因として渡す
        } catch (IOException e) {                         // 親クラス(NoSuchFileException の親)を後に
            throw new ReportStorageException("レポートの読み込みに失敗しました: id=" + id, e);
        }
    }
}

③ Controller: try-catch も throws も書かない。正常系だけに集中する

@RestController
@RequestMapping("/api/reports")
public class ReportController {

    private final ReportService reportService;

    public ReportController(ReportService reportService) {
        this.reportService = reportService;
    }

    @GetMapping("/{id}")
    public ReportResponse findReport(@PathVariable Long id) {
        if (id <= 0) {
            throw new IllegalArgumentException("id は1以上を指定してください: " + id);
        }
        return reportService.loadReport(id);
    }
}

④ @RestControllerAdvice: 例外 → HTTPレスポンスへの変換を1か所に集約する

@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<ErrorBody> handleBadRequest(IllegalArgumentException ex) {
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
                .body(new ErrorBody("BAD_REQUEST", ex.getMessage()));
    }

    @ExceptionHandler(ReportNotFoundException.class)
    public ResponseEntity<ErrorBody> handleNotFound(ReportNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorBody("REPORT_NOT_FOUND", ex.getMessage()));
    }

    // 想定外の例外すべての受け皿(ReportStorageException もここに来る)
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorBody> handleUnexpected(Exception ex) {
        log.error("想定外のエラー", ex);   // 詳細はログにだけ残す
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new ErrorBody("INTERNAL_ERROR", "サーバーでエラーが発生しました"));
    }
}

public record ErrorBody(String code, String message) {}

層ごとの役割

層例外に対してやること
ライブラリ・外部I/OIOException などの検査例外を投げてくる
Service検査例外を catch し、業務的な意味を持つ非検査例外に包み直して throw する
Controller何もしない(try-catch も throws も不要)。入力が不正なら IllegalArgumentException などを throw するだけ
@RestControllerAdvice例外の型ごとに、HTTPステータスとエラーボディに変換する

🔍 補足: なぜ「非検査例外に包み直す」のか

理由1: throws の連鎖を止められる

Service で IOException を throws すると、Controller にも throws IOException が必要になる。Service で包み直せば、Controller にわざわざ throws を書かなくて済む。

理由2: 例外に業務的な意味を持たせられる

IOException だけでは「見つからない(404)」のか「読み込みに失敗した(500)」のか区別できない。ReportNotFoundException のような名前にすると、ハンドラで適切なステータスを選べる。

理由3: Spring 自身もこの方針

Spring は JDBC の検査例外 SQLException を、非検査例外 DataAccessException の仲間に変換して投げ直す。また @Transactional は、既定では非検査例外のときだけロールバックする。

注意: 元の例外(cause)を必ず渡す

new ReportStorageException("...", e) のように第2引数に元の例外を渡すと、ログのスタックトレースに Caused by: java.nio.file.NoSuchFileException ... と本当の原因が残る。渡し忘れると、調査の手がかりが消えてしまう。

7. やってはいけない対処

// ❌ 握りつぶし: 例外が起きたことが誰にも伝わらない
try {
    return Files.readString(path);
} catch (IOException e) {
    e.printStackTrace();
    return null;          // 呼び出し元では、あとで NullPointerException として別の場所で爆発する
}

// ❌ とりあえず throws Exception: 何が起きうるのか呼び出し元に伝わらない
public ReportResponse loadReport(Long id) throws Exception { ... }

// ❌ 何でも catch (Exception e): 想定外のバグ(NullPointerException など)まで隠してしまう
try {
    ...
} catch (Exception e) {
    return ResponseEntity.ok().build();   // エラーなのに 200 OK
}

8. まとめ

「対処」は3種類ある

対処どこで主な対象
予防(起きないようにする)コードを書く時点非検査例外(バグ、不正な入力)
回復(起きたら別の方法で続ける)起きた場所の近くで try-catch検査例外のうち、回復手段があるもの
最後に受け止める(止めてエラーを返す)@ExceptionHandler で1か所に回復できないものすべて

どちらの例外にも対処は必要。ただし全部を try-catch で書くのではなく、この3つを使い分ける。

判断フロー

例外が起きうるコードを書くときは、次の順に考える。1 で回復できなかった例外は、2 か 3 を経て、4 で受け止められる。

  1. その場で回復できる?(デフォルト値で続行できる、再試行できる など)
    → できるなら、その場で try-catch して回復する。例: ファイルが読めなければ空文字で続行する(3-2 の readOrDefault())
  2. 回復できない検査例外?
    → Service などで catch し、意味のある非検査例外に包み直して throw する(6. の②)。こうすれば Controller に throws を書かずに済む
  3. 回復できない非検査例外?
    → 何も書かない。そのまま Controller の外へ流れていく
  4. Controller の外に出た例外は?
    → @RestControllerAdvice の @ExceptionHandler が、型ごとに HTTP レスポンスへ変換する。想定している例外(ReportNotFoundException → 404 など)は専用のハンドラで、想定外の例外は最後の砦の @ExceptionHandler(Exception.class) で 500 を返す

つまり、try-catch を書くのは「回復できるとき」と「包み直すとき」の2つだけ。それ以外は何も書かず、最後に1か所でまとめて受け止める。
