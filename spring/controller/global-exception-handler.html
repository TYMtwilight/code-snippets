@RestControllerAdvice - 例外の種類ごとに共通形式のエラーJSONを返す

  • 📅 作成日: 2026-03-21
  • 🔄 更新日: 2026-09-30

🎯概要

@RestControllerAdvice を付けたクラスに @ExceptionHandler メソッドを集めると、アプリ全体の Controller で起きた例外を1か所で受け取り、統一フォーマットのJSONエラーレスポンスを返せる。実務での例外ハンドリングは、この形で書くのが基本。

📌使用場面

  • バリデーションエラー(@Valid)を 400 Bad Request で返したい時
  • 存在しないリソースへのアクセスを 404 Not Found で返したい時
  • 各 Controller にエラーハンドリングを散在させず、エラーレスポンスの形式をAPI全体でそろえたい時

💻コード

1全体像: 例外がエラーレスポンスになるまで

Controller や Service では try-catch を書かず、例外はすべて GlobalExceptionHandler に任せる。例外は次の順に処理される。

処理の流れ

  1. Controller や Service の処理中に例外が発生する(try-catch は書かない)
  2. 例外が Controller の外へ飛び出し、Spring が受け取る
  3. GlobalExceptionHandler の中から、例外の型に合う @ExceptionHandler メソッドが呼ばれる
  4. そのメソッドが作った ErrorResponse(共通形式の JSON)がクライアントに返る

このページでは、次の3つのパターンを扱う。

パターン受け取る例外投げるのはステータスハンドラ
① バリデーションエラーMethodArgumentNotValidExceptionSpring(@Valid)400handleValidation()
② リソース未検出ResourceNotFoundException自分(Service)404handleNotFound()
③ 想定外の例外①②以外のすべて―500handleUnexpected()

3つのハンドラは、すべて1つのクラスにまとめて書く。

@RestControllerAdvice
public class GlobalExceptionHandler {

  // ① バリデーションエラー → 400
  @ExceptionHandler(MethodArgumentNotValidException.class)
  public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
    ...
  }

  // ② リソース未検出 → 404
  @ExceptionHandler(ResourceNotFoundException.class)
  public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex) {
    ...
  }

  // ③ 想定外の例外 → 500
  @ExceptionHandler(Exception.class)
  public ResponseEntity<ErrorResponse> handleUnexpected(Exception ex) {
    ...
  }
}

どのパターンも、ErrorResponse(status, error, message, timestamp) を作って ResponseEntity で返す、という同じ形になっている(ErrorResponse の中身は「6. エラーレスポンスの形式」)。違うのは、受け取る例外・ステータスコード・メッセージの作り方の3点。

補足

2つのアノテーションの役割

@RestControllerAdvice とは

  • @ControllerAdvice + @ResponseBody の合成アノテーション。ハンドラの戻り値がそのままJSONのレスポンスボディになる
  • @Controller(@RestController 含む)全体に横断的に適用される

@ExceptionHandler の基本

  • Spring MVCのアノテーションで、Controller で発生した例外を専用のメソッドでキャッチして処理するためのもの。通常は @RestControllerAdvice のクラスに書く
  • @ExceptionHandler(ResourceNotFoundException.class)のように対象の例外クラスを指定し、そのメソッドで例外を受け取ってレスポンスを組み立てる
  • 複数の例外クラスを1つのメソッドでまとめて扱うことも可能: @ExceptionHandler({FooException.class, BarException.class})

2Controller: エラー処理は書かない

例外を処理するコードは、Controller には1行もない。正常系の処理だけを書く。

@RestController
@RequestMapping("/api/todos")
public class TodoController {

  private final TodoService todoService;

  public TodoController(TodoService todoService) {
    this.todoService = todoService;
  }

  // 見つからなければ Service が ResourceNotFoundException を投げる → GlobalExceptionHandler が 404 に変換
  @GetMapping("/{id}")
  public TodoResponse findById(@PathVariable Long id) {
    return todoService.findById(id);
  }

  // 入力ルール違反なら MethodArgumentNotValidException → GlobalExceptionHandler が 400 に変換
  @PostMapping
  public ResponseEntity<TodoResponse> create(@Valid @RequestBody TodoRequest request) {
    TodoResponse created = todoService.create(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(created);
  }
}

何が嬉しいか

  • try-catchをコントローラーの各メソッドに書かなくて済む(関心の分離)。上の TodoController には正常系の処理しかない
  • 例外の種類ごとにHTTPステータスコードやレスポンス形式を統一的に定義できる

3パターン① バリデーションエラー → 400

入力ルールを定義する

入力ルールは、リクエスト DTO に Bean Validation のアノテーションで定義する。

public class TodoRequest {

  @NotBlank(message = "タイトルは必須です")
  @Size(max = 100, message = "タイトルは100文字以内で入力してください")
  private String title;

  // getter / setter
}
@PostMapping
public ResponseEntity<TodoResponse> create(
    @Valid @RequestBody TodoRequest request) {

⚠️ @Valid はどこに付ける？

1つ目のコード例の TodoRequest クラス自体には @Valid が付いていないが、これで正しい。@Valid はDTOクラス自体には付けない。

@NotBlank / @Size は「制約(ルール)」を定義するだけのもので、@Valid は「このルールを今チェックしろ」という指示。だからDTOを使う側(Controllerのメソッド引数)に付ける。

Service の引数には付けなくてよい。リクエストは必ず Controller を通るので、必須・文字数などの形式のチェックは、入口の Controller で1回やれば十分。

400 になるまでの流れ

処理の流れ

  1. クライアントが不正なリクエストを送る
  2. @Valid が TodoRequest をチェックする
  3. ルール違反なら MethodArgumentNotValidException が発生する
  4. handleValidation() が例外を受け取り、400 のエラーレスポンスを返す

ハンドラのコード

@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handleValidation(
    MethodArgumentNotValidException ex) {
  String message = ex.getBindingResult().getFieldErrors().stream()
      .map(FieldError::getDefaultMessage)
      .collect(Collectors.joining(", "));

  ErrorResponse error = new ErrorResponse(
      HttpStatus.BAD_REQUEST.value(),
      "Bad Request",
      message,
      LocalDateTime.now());
  return ResponseEntity.badRequest().body(error);
}

  1. 受け取る例外: MethodArgumentNotValidException

    リクエストの中身が入力ルール(@NotBlank など)に合わなかったときに、Spring が自動で投げる例外。@Valid を付けた引数でだけ発生する。自分で throw する必要はなく、このハンドラで受け取るだけでよい。

    補足

    MethodArgumentNotValidException は検査例外

    RuntimeException を継承していないので、検査例外になる(Spring 5.3 以降は BindException を継承。それより前は Exception を直接継承)。

    継承関係

    • Exception
      • BindException(Spring)
        • MethodArgumentNotValidException

    検査例外なのに Controller や Service に throws を書かなくていいのは、自分のコードの中で投げられる例外ではないから。リクエストが届いてからの順番は次のとおり。

    例外が投げられるタイミング

    1. リクエストが届く
    2. Spring が JSON を TodoRequest に変換し、@Valid のチェックを実行する。違反があれば、ここで MethodArgumentNotValidException を投げる
    3. チェックを通ったときだけ、TodoController.create() が呼ばれる
    • 例外が投げられるのは、Spring が Controller のメソッドを呼び出す前、引数を準備している段階。違反があると create() はそもそも呼ばれず、例外は Controller を一度も通らない
    • 投げるのも受け取るのも Spring 側のコードで、throws の宣言が必要なのも Spring の内部メソッド(そちらではきちんと宣言されている)
    • 検査例外で throws が必要になるのは、その例外が自分の書いたメソッドを通過するときだけ。この例外は通過しないので、throws はいらない
    • @ExceptionHandler は検査例外か非検査例外かに関係なく受け取れるので、このハンドラでそのまま扱える

  2. エラー一覧を取り出す: ex.getBindingResult().getFieldErrors()

    例外の中には、チェックの結果(BindingResult)が入っている。getFieldErrors() で、そこから違反したフィールドのエラーを一覧(List<FieldError>)で取り出す。1つの FieldError には「どのフィールドが」「どのメッセージで」違反したかが入っている。

  3. メッセージを1つの文字列にまとめる: stream() 〜 Collectors.joining(", ")

    エラー一覧からメッセージだけを取り出し、カンマ区切りの1つの文字列にする。メッセージは、@NotBlank(message = "タイトルは必須です") の message に書いた文言。

    補足

    stream() 〜 Collectors.joining() で何をしているか

    ex.getBindingResult().getFieldErrors()   // List<FieldError>  違反したフィールドのエラー一覧
    .stream()                            // 一覧を「1件ずつ流して加工できる形」にする
    .map(FieldError::getDefaultMessage)  // 各 FieldError → メッセージ文字列 に変換
    .collect(Collectors.joining(", "));  // 文字列を ", " でつないで1つにする

    データの形は次のように変わっていく(dueDate は説明のための仮のフィールド)。

    データの変化

    1. はじめ: FieldError の一覧。[FieldError(title, "タイトルは必須です"), FieldError(dueDate, "期限は必須です")]
    2. .stream() の後: 同じ FieldError が1件ずつ流れてくる
    3. .map(FieldError::getDefaultMessage) の後: 中身が文字列に変わる。"タイトルは必須です"、"期限は必須です"
    4. .collect(Collectors.joining(", ")) の後: 1つの String になる。"タイトルは必須です, 期限は必須です"
    stream()
    List を Stream にする。Stream にすると、map(変換)や filter(絞り込み)を順につなげて書ける
    map(...)
    流れてくる要素を1件ずつ別の値に変換する。ここでは FieldError → String
    FieldError::getDefaultMessage
    メソッド参照。ラムダ式 error -> error.getDefaultMessage() の省略形で、「各要素の getDefaultMessage() を呼ぶ」という意味
    collect(...)
    流れてきた要素を最後にまとめて、1つの結果にする
    Collectors.joining(", ")
    まとめ方の指定。文字列を ", " を区切りにしてつなげる(最後の要素の後ろには付かない)

    Collectors とは

    collect() に渡す「まとめ方」を用意してくれるクラス(java.util.stream.Collectors)。collect() は「流れてきた要素を最後に1つにまとめる」メソッドだが、「どうまとめるか」は自分では決めず、まとめ方(Collector)を引数で受け取る。Collectors は、よく使うまとめ方をあらかじめ用意した道具箱のようなもの。

    collect()
    Stream のメソッド。「まとめる」処理を実行する
    Collector
    「まとめ方」を表すインターフェース
    Collectors(s付き)
    Collector を作って返す static メソッドを集めたクラス。Collections(List を操作するクラス)とは別物

  4. 400 で返す: ResponseEntity.badRequest()

    まとめたメッセージを ErrorResponse に詰め、400 Bad Request として返す。HttpStatus.BAD_REQUEST.value() は数値の 400。ResponseEntity.badRequest() は ResponseEntity.status(HttpStatus.BAD_REQUEST) の省略形。

    ErrorResponse error = new ErrorResponse(
    HttpStatus.BAD_REQUEST.value(),   // 400
    "Bad Request",
    message,                          // 1つ前の項目でまとめた違反メッセージ
    LocalDateTime.now());             // 今の日時
return ResponseEntity.badRequest().body(error);

    ResponseEntity は「① ステータスコードを決める → ② .body(...) でボディを入れる」の2段階でレスポンスを組み立てる。①の 400 の指定方法は次の3通りあり、どれか1つを書けばよい(どれでも同じレスポンスになる)。

    書き方400 の指定方法
    ResponseEntity.badRequest()400 専用のメソッドを使う。名前自体が 400 を意味する(このコードで採用)
    ResponseEntity.status(HttpStatus.BAD_REQUEST)汎用の status() に、400 を表す定数を渡す
    ResponseEntity.status(400)汎用の status() に、数値の 400 を直接渡す。何のステータスか読み取りにくいので、あまり使わない

    よく使うステータスには badRequest() のような専用メソッドが用意されている(ok() は 200、notFound() は 404)。専用メソッドがないステータスは status(HttpStatus.XXX) で指定する。

    補足

    ErrorResponse の構造

    エラー時に返す JSON の形を決める DTO(record)。①〜③のどのハンドラもこれを返すので、エラーの種類が違っても JSON の形は常に同じになる。

    status(int)
    HTTP ステータスコードの数値。ここでは 400
    error(String)
    ステータスの名前。ここでは "Bad Request"
    message(String)
    何が起きたかの説明。ここでは1つ前の項目でまとめた違反メッセージ
    timestamp(LocalDateTime)
    エラーが起きた日時。ログと突き合わせて調べるときに使う

    フィールド名がそのまま JSON のキーになり、次のようなレスポンスが返る。

    {
  "status": 400,
  "error": "Bad Request",
  "message": "タイトルは必須です",
  "timestamp": "2026-03-21T10:00:00.123456"
}

    各フィールドの詳しい説明や、②③のハンドラが入れる値は「6. エラーレスポンスの形式」を参照。

4パターン② リソース未検出 → 404

独自例外を用意する

「見つからない」ことを表す独自例外を用意し、Service で見つからなかったときに投げる。

public class ResourceNotFoundException extends RuntimeException {
  public ResourceNotFoundException(String message) {
    super(message);
  }
}

// Service 側で投げる
throw new ResourceNotFoundException("TODO が見つかりません：id = " + id);

ハンドラのコード

@ExceptionHandler(ResourceNotFoundException.class)
public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex) {
  ErrorResponse error = new ErrorResponse(
      HttpStatus.NOT_FOUND.value(),
      "Not Found",
      ex.getMessage(),
      LocalDateTime.now());
  return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
}

  1. 受け取る例外: ResourceNotFoundException

    Service で「見つからない」ときに自分で投げる独自例外。

  2. メッセージ: ex.getMessage()

    例外を投げたときにコンストラクタへ渡した文言(例: "TODO が見つかりません：id = 99")をそのままレスポンスに入れる。自分で作った例外なので、メッセージに何が入るかを把握でき、クライアントに見せても問題ない。

  3. 404 で返す: ResponseEntity.status(HttpStatus.NOT_FOUND)

    404 Not Found として返す。ResponseEntity.notFound() という専用メソッドもあるが、こちらはボディを入れられないため、ここでは status() を使っている。

⚠️ RuntimeException をまとめて 404 にしない

404 用のハンドラを @ExceptionHandler(RuntimeException.class) にすると、NullPointerException などのバグまで「見つかりません(404)」として返ってしまう。404 にしたい例外は専用の独自例外にして、それだけを指定する。

5パターン③ 想定外の例外(最後の砦) → 500

ハンドラのコード

@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleUnexpected(Exception ex) {
  ErrorResponse error = new ErrorResponse(
      HttpStatus.INTERNAL_SERVER_ERROR.value(),
      "Internal Server Error",
      "予期しないエラーが発生しました",
      LocalDateTime.now());
  return ResponseEntity.internalServerError().body(error);
}

  1. 受け取る例外: Exception

    Exception.class を指定すると、ほぼすべての例外が対象になる。ただし①②のようにより具体的なハンドラがある例外はそちらが優先されるので、ここに届くのは他のどれにも当てはまらない例外だけ(「7. @ExceptionHandler の優先順位」)。

  2. メッセージ: 固定の文言

    ex.getMessage() は使わない。想定外の例外のメッセージには、SQL文やクラス名など内部の情報が含まれることがあり、クライアントに見せるべきではないため。代わりに、実務では log.error("...", ex) で例外をログに残しておくと、原因を調べやすい。

  3. 500 で返す: ResponseEntity.internalServerError()

    500 Internal Server Error として返す。ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR) の省略形。

6エラーレスポンスの形式(ErrorResponse)

ErrorResponse は、エラー時に返す JSON の形を決めるための DTO。どのハンドラーも、この同じ DTO を返す。

public record ErrorResponse(
    int status,              // HTTP ステータスコードの数値
    String error,            // ステータスの名前
    String message,          // 何が起きたかの説明
    LocalDateTime timestamp  // エラーが起きた日時
) {}

各フィールドの意味

フィールド型中身例
statusintHTTP ステータスコードの数値400, 404, 500
errorStringステータスの名前"Bad Request", "Not Found"
messageString何が起きたかの具体的な説明。クライアントが画面に表示したりする"タイトルは必須です"
timestampLocalDateTimeエラーが起きた日時。ログと突き合わせて調べるときに使う2026-03-21T10:00:00

status と error は、HTTP のステータス行(400 Bad Request)と同じ情報。ヘッダーだけでなくボディにも入れておくことで、クライアントは JSON を読むだけで状況が分かる。

3つのハンドラが入れる値

ハンドラstatuserrormessage
① handleValidation()400"Bad Request"違反メッセージをカンマでつないだもの
② handleNotFound()404"Not Found"ex.getMessage()(例外を投げたときの文言)
③ handleUnexpected()500"Internal Server Error"固定の "予期しないエラーが発生しました"

どのハンドラも同じ ErrorResponse を返すので、エラーの種類が違っても JSON の形は常に同じになる。クライアントは「エラーなら message を表示する」という1つの処理で、すべてのエラーに対応できる。これが「統一エラーハンドリング」の「統一」の意味。

JSON への変換

record のフィールド名が、そのまま JSON のキーになる(Spring Boot に入っている Jackson が変換する)。

new ErrorResponse(400, "Bad Request", "タイトルは必須です", LocalDateTime.now())
{
  "status": 400,
  "error": "Bad Request",
  "message": "タイトルは必須です",
  "timestamp": "2026-03-21T10:00:00.123456"
}

LocalDateTime は、Spring Boot の初期設定では ISO 形式の文字列になる。LocalDateTime.now() はミリ秒以下も持っているので、.123456 のような小数部分も出力される。

なぜ record なのか

  • フィールド・コンストラクタ・getter・equals/toString を自動で作ってくれるので、短く定義できる
  • 値を後から変更できない(イミュータブル)。「作って返すだけ」のレスポンス DTO に向いている

7@ExceptionHandler の優先順位

同一クラス内に複数の @ExceptionHandler がある場合、投げられた例外に継承関係がより近いハンドラが優先される。たとえば ResourceNotFoundException は Exception のサブクラスでもあるが、より具体的な handleNotFound() の方にマッチする。handleUnexpected() に届くのは、他のどれにも当てはまらない例外だけ。

継承関係

  • Exception … 最も汎用的(handleUnexpected(): 最後のフォールバック)
    • RuntimeException
      • ResourceNotFoundException … より具体的(handleNotFound(): こちらが選ばれる)

なお、Controller 内にも同じ例外用の @ExceptionHandler がある場合は、Controller 内の方が @RestControllerAdvice より優先される。

🚀発展

Advice が扱う Controller の範囲は絞り込める。何も指定しなければ全 Controller が対象になる。

// com.example.api パッケージ配下の Controller だけに適用
@RestControllerAdvice(basePackages = "com.example.api")
public class ApiExceptionHandler { ... }

// 特定の Controller クラスだけに適用
@RestControllerAdvice(assignableTypes = {TodoController.class})
public class TodoExceptionHandler { ... }

API 用と画面用で返し方を分けたいときなどに使う。範囲外の Controller の例外は、その Advice では受け取らない。
