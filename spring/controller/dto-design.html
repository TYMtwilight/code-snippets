DTO設計 — EntityとAPIレスポンスを切り離す

  • 📅 作成日: 2026-09-21
  • 🔄 更新日: 2026-09-21

🎯概要

Entityをそのままレスポンスとして返さない理由と、リクエスト用DTO/レスポンス用DTOを分ける考え方、Java 17以降のrecordを使った簡潔な書き方を整理する。

① Entityを直接返さない理由

  • 内部情報・監査情報が漏れる: Entityはあくまで「DBのテーブルをそのまま表したクラス」であり、本来クライアントに見せる必要のない内部管理用のカラムや監査情報まで持っている。これをそのままJSONで返すと、それらの情報まで外部に漏れてしまう。

    📎補足(監査情報とは): 「誰が・いつ・どう操作したか」を記録する管理用のメタデータのこと。代表例: createdAt/createdBy(作成日時・作成者)、updatedAt/updatedBy(更新日時・更新者)、version(楽観ロック用の更新回数)、削除フラグ(deletedAtなど)。

  • 遅延ロードによる意図しない不具合: JPAの遅延ロード(@OneToMany等)が絡むと、シリアライズ時に問題が起きることがある。例として、ブログ記事を表すPostが@OneToManyでList<Comment> commentsを、Comment側も@ManyToOneでPost postを持つ、双方向の関連を考える。

    Post

    @OneToMany
    comments

    ── 取得 ──▶ ◀── 参照 ──

    Comment

    @ManyToOne
    post

    これをそのままJSONに変換しようとすると、大きく2つの問題が起きる。

    1. ムダなSQLが増える(N+1問題)
      遅延ロードのフィールドは、実際にアクセスされた瞬間に初めてSQLが発行される。一覧APIで100件のPostをJSONに変換すると、getComments()が呼ばれるたびに追加のSELECTが走り、最大100回もの余分なクエリが発生しうる。
    2. 無限ループになる(循環参照)
      双方向の関連をそのままシリアライズすると、Jacksonが互いのgetterを行き来し続けてスタックオーバーフローになることがある。

      JacksonがそのままJSON変換すると…
      Post → comments → Comment → post → comments → … と辿り続け、無限ループ(StackOverflowError)になってしまう。

      📎補足(Jacksonとは): JavaオブジェクトとJSONを相互に変換するライブラリ。Spring Boot(spring-boot-starter-web)に標準で含まれており、@RestControllerのメソッドが返したオブジェクトを自動でJSONに変換(シリアライズ)したり、@RequestBodyで受け取ったJSONをオブジェクトに変換(デシリアライズ)したりする。シリアライズ時は基本的にオブジェクトのgetter(getXxx())を呼んで値を取り出すため、双方向の関連があるとpost.getComments() → comment.getPost() → post.getComments() → … と呼び出しが終わらなくなる。

    DTOを使うと、どちらの問題も防げる。JSONに変換される対象が、EntityではなくDTOになるからだ。

    ❌ Entity(Post)を返す

    JacksonがPostのgetterをすべて呼ぶ
    ↓
    getComments()も呼ばれる

    追加のSQL・無限ループが起きる

    ✅ DTO(PostDto)を返す

    PostDtoはidとtitleだけを持つ
    ↓
    getComments()は存在しないので呼ばれない

    どちらの問題も起きない

    💡 JSONに含める項目をDTOで先に絞っておけば、Jacksonが遅延ロードのフィールドに触れることはない。

② リクエストDTOとレスポンスDTOを分ける理由

「受け取ってよい項目」と「返してよい項目」は一致しない。idやcreatedAtはサーバー側が決める値であり、クライアントが指定するものではない。

例: ユーザー登録APIが、Userエンティティ(id・name・email・roleを持つ)でリクエストを受け取る場合に、次のJSONが送られてきたとする。

{
  "name": "山田太郎",
  "email": "yamada@example.com",
  "id": 1,
  "role": "ADMIN"
}

このうち、後ろの2つはクライアントが指定してはいけない項目。

送り込まれた項目起きること
"id": 1既存ユーザー(id=1)のデータが上書きされる
"role": "ADMIN"一般ユーザーが自分に管理者権限を与えられる

❌ User(Entity)で受け取る

idやroleのフィールドも持っている
↓
送られてきた値がそのままセットされる

上書き・権限昇格が起きる

✅ UserCreateRequest(DTO)で受け取る

nameとemailだけを持つ
↓
idやroleは受け皿が無いので無視される

どちらの問題も起きない

③ Java 17以降のrecordを使った簡潔な書き方

DTOは「値を保持して運ぶだけ」の単純なクラスであり、通常のclassで書くとフィールド・コンストラクタ・getter・equals/hashCode/toStringを自前で用意する必要がある。recordを使うと、これらが自動生成され、数行で不変(immutable)なDTOを定義できる。

public record UserCreateRequest(
        @NotBlank String name,
        @NotBlank String email
) {}

この短い定義だけで、フィールドname/email、コンストラクタ、name()/email()という形のgetter、equals/hashCode/toStringまで揃う。DTOのように「ただデータを運ぶだけ」のクラスと相性が良い。

📎 補足(コンストラクタを書いていないのにnewできる理由)

recordは、ヘッダーに書いた引数リストから、全フィールドを受け取るコンストラクタを自動で作る。これを正規コンストラクタという。上のUserCreateRequestなら、コンパイラが裏で次のコードを作ってくれる。

// 自動生成されるもの(実際には書かなくてよい)
private final String name;
private final String email;

public UserCreateRequest(String name, String email) {
    this.name = name;
    this.email = email;
}

そのためnew UserCreateRequest("山田太郎", "yamada@example.com")のように、ヘッダーと同じ順番・型で引数を渡せばインスタンスを作れる。普通のclassで自動生成されるのは「引数なし」のデフォルトコンストラクタだが、recordでは「全フィールドを受け取る」コンストラクタになる、と考えるとわかりやすい。

recordは必ず不変(immutable)になる。理由は次の3つ。

  1. コンストラクタで渡した値は、finalフィールドに格納される
  2. finalフィールドは、一度入れた値を再代入できない
  3. setterも自動生成されない

つまり、作ったあとに値を変える手段がそもそも無い。

UserCreateRequest req = new UserCreateRequest("山田太郎", "yamada@example.com");

req.name();              // "山田太郎"  ← 読み取りはできる
req.setName("佐藤花子");  // コンパイルエラー: setterが存在しない
📎 補足(DTOをimmutableにするメリット)
  • スレッドセーフになる: 1つのDTOインスタンスが複数のリクエスト/スレッドから参照されても、値が変わらないことが保証されていれば同期処理を気にせず安全に共有できる。
  • 意図しない書き換えを防げる: DTOは「受け取った値」や「返す値」をそのまま表す入れ物。途中でうっかり値を書き換えてしまうと、リクエストの内容と実際に処理された内容がズレてバグの原因になるが、setterがなければそのミスは起こり得ない。
  • 「データが正しい」という前提を安心して使い回せる: 一度バリデーション(@Valid)を通ったDTOは、その後どこに渡しても値が変わらないと保証される。

📌使用場面

  • 新しいAPIエンドポイントのレスポンス形式を設計するとき
  • Entityの内部構造(パスワードハッシュ、他テーブルとのリレーション、監査カラム等)を外部に漏らしたくないとき
  • 入力値のバリデーション対象と、DB保存対象の形が違うとき

💻コード

// --- Entity: DBのテーブル構造そのもの ---
@Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String email;
    private String passwordHash;    // 外部に絶対出してはいけない情報
    private String role;            // 権限(USER / ADMIN)
    private LocalDateTime createdAt;
    // getter/setterは省略
}

// --- リクエスト用DTO(record): クライアントから受け取る最小限の項目 ---
public record UserCreateRequest(
        @NotBlank String name,
        @NotBlank String email
) {}

// --- レスポンス用DTO(record): クライアントに公開してよい項目のみ ---
public record UserResponse(
        Long id,
        String name,
        String email,
        long postCount   // Entityには無い、集計結果のフィールドも足せる
) {
    public static UserResponse from(User entity, long postCount) {
        return new UserResponse(
                entity.getId(),
                entity.getName(),
                entity.getEmail(),
                postCount
        );
    }
}

Entity: User

@Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String email;
    private String passwordHash;
    private String role;
    private LocalDateTime createdAt;
    // getter/setterは省略
}

DBのテーブル構造をそのまま表すクラス。passwordHashやroleのような、外部に出すべきでないフィールドも含めて、テーブルの全カラムを持つ。このクラスをAPIレスポンスとして直接返すと、これらの情報までクライアントに漏れてしまう。

@Table(name = "users")は、このEntityクラスがどのDBテーブルに対応するかを指定するアノテーション。クラス名User(単数形)とテーブル名users(複数形)のように名前が異なる場合に、その対応関係を明示する。省略した場合はクラス名がそのままテーブル名とみなされる。

📎 補足(@Entityと@Tableの役割分担)

@Entityは、このクラスがJPAの管理対象(=DBに永続化されるオブジェクト)であることを示すアノテーションで、これだけでも「Entityと DBが紐づく」という大枠は成立する。@Tableはその中で「具体的にどのテーブル名に対応するか」を指定する、いわば微調整・上書き用のアノテーション。つまり紐付けの主役は@Entityで、@Tableはテーブル名(や必要ならスキーマ名)を明示的に指定したいときだけ添えるオプション。

リクエスト用DTO: UserCreateRequest

public record UserCreateRequest(
        @NotBlank String name,
        @NotBlank String email
) {}

クライアントが登録時に指定してよい項目(name、email)だけを持つ。idやroleのようなフィールドがそもそも存在しないため、クライアントが既存データを上書きしたり、自分に管理者権限を与えたりする心配がない。recordで書くことでgetterやequals等を自前で書く必要もなくなる。

レスポンス用DTO: UserResponse

public record UserResponse(
        Long id,
        String name,
        String email,
        long postCount   // Entityには無い、集計結果のフィールドも足せる
) {
    public static UserResponse from(User entity, long postCount) {
        return new UserResponse(
                entity.getId(),
                entity.getName(),
                entity.getEmail(),
                postCount
        );
    }
}

クライアントに公開してよい項目だけを持つ。passwordHashやroleは含めない。またpostCountのように、Entityには無い集計結果のフィールドを足すこともできる。UserからUserResponseへの変換は、上記のように静的ファクトリメソッド(from)をDTO側に置くか、Service層・専用のMapperクラスに書くのが一般的。

📎 補足(postCountとは)

「そのユーザーの投稿数」を表すフィールド。投稿のテーブルを集計(COUNT)して求める値であり、Userエンティティ自体は持たない。Service層でRepositoryから取得した値をfromに渡す想定。画面表示に必要な計算・集計結果だけをレスポンスDTOに含められる、という例として挙げている。

fromの中のnew UserResponse(...)は、③で説明した正規コンストラクタ(recordが自動で作るコンストラクタ)を呼んでいる。fromがしていることは、次の2ステップだけ。

  1. User(Entity)と、集計済みのpostCountを受け取る
  2. それらをヘッダーと同じ順番(id → name → email → postCount)に並べて、正規コンストラクタに渡す
new UserResponse(
        entity.getId(),      // 1番目の引数 id に対応
        entity.getName(),    // 2番目の引数 name に対応
        entity.getEmail(),   // 3番目の引数 email に対応
        postCount            // 4番目の引数 postCount に対応
);

つまりfromは、Userエンティティの各フィールドを、recordの引数の並び順に詰め替えて渡すだけのヘルパーメソッド。呼び出し側(Serviceなど)で毎回new UserResponse(u.getId(), u.getName(), u.getEmail(), ...)と書く代わりにUserResponse.from(user, postCount)と書けるようにし、変換ロジックをDTO側に閉じ込めることで呼び出し側のコードをシンプルにしている。

📎 補足(ヘルパーメソッドとは)

特定の処理を切り出して、他のコードから使い回せるようにした補助的なメソッドのこと。それ自体がアプリの主目的(APIを提供する、画面を表示するなど)ではなく、あくまで他のコードの手助け(help)をするための存在なので、こう呼ばれる。

fromで言うと、主目的はUser(Entity)のデータをUserResponseに変換すること。ヘルパーが無い場合、Service層など変換が必要な箇所すべてで毎回new UserResponse(user.getId(), user.getName(), user.getEmail(), postCount)と書く必要があり、呼び出し側のコードが長くなる上、書き方がバラバラになるリスクもある。ヘルパーがあればUserResponse.from(user, postCount)と1行で済み、変換のロジックはfromメソッド1箇所にまとまる。

つまり「本質的な処理ではないが、同じような手間を何度も書かなくて済むように用意された、再利用可能な小さなメソッド」がヘルパーメソッド。日付のフォーマット変換用メソッドや文字列のバリデーション用メソッドなど、「地味だけど繰り返し使う処理」を切り出したものは大体ヘルパーメソッドと呼ばれる。
