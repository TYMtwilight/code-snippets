REST Controller - 基本パターン(CRUD)

  • 📅 作成日: 2026-03-21
  • 🔄 更新日: 2026-09-22

🎯概要

@RestControllerと@RequestMappingを使ったREST APIコントローラーの基本パターン。GET / POST / PUT / PATCH / DELETEの5メソッドをDTO + Service層と組み合わせて実装する。

🔍 用語ノート: @RequestMapping

URLパスをControllerのクラス/メソッドに紐付けるアノテーション。クラスに付けると、そのControllerが担当する共通のベースパスを指定できる(例: @RequestMapping("/api/todos")を付けたクラス内の@GetMappingは実際にはGET /api/todosになる)。

@GetMapping、@PostMappingなどは@RequestMapping(method = RequestMethod.GET)等のショートカット(合成アノテーション)。メソッド単体に@RequestMappingを付けてパスとHTTPメソッドを指定することも技術的には可能だが、今は@GetMapping等を使うのが主流。「クラスに@RequestMapping、メソッドに@GetMapping等」という組み合わせが最も一般的。 

// 古い書き方(今はあまり使わない)
@RequestMapping(value = "/{id}", method = RequestMethod.GET)

// 今の主流(@GetMappingが上と同じ意味のショートカット)
@GetMapping("/{id}")

📌使用場面

  • リソース(例: TODO、ユーザー、商品)のCRUD APIを設計する時
  • Bean Validation(@Valid)でリクエストを検証したい時
  • Service層に処理を委譲し、Controllerをシンプルに保ちたい時

💻コード

基本形

@RestController
@RequestMapping("/api/todos")
public class TodoController {

  private final TodoService todoService;

  // コンストラクタインジェクション
  public TodoController(TodoService todoService) {
    this.todoService = todoService;
  }

  // GET /api/todos?status=ALL|ACTIVE|COMPLETED
  @GetMapping
  public ResponseEntity<List<TodoResponse>> getAll(
      @RequestParam(name = "status", defaultValue = "ALL") String status) {
    return ResponseEntity.ok(todoService.findAll(status));
  }

  // POST /api/todos → 201 Created
  @PostMapping
  public ResponseEntity<TodoResponse> create(
      @Valid @RequestBody TodoRequest request) {
    TodoResponse created = todoService.create(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(created);
  }

  // PUT /api/todos/{id} → 200 OK
  @PutMapping("/{id}")
  public ResponseEntity<TodoResponse> update(
      @PathVariable("id") Long id,
      @Valid @RequestBody TodoRequest request) {
    TodoResponse updated = todoService.update(id, request);
    return ResponseEntity.ok(updated);
  }

  // PATCH /api/todos/{id}/toggle → 200 OK(部分更新)
  @PatchMapping("/{id}/toggle")
  public ResponseEntity<TodoResponse> toggle(@PathVariable("id") Long id) {
    TodoResponse toggled = todoService.toggleComplete(id);
    return ResponseEntity.ok(toggled);
  }

  // DELETE /api/todos/{id} → 204 No Content
  @DeleteMapping("/{id}")
  public ResponseEntity<Void> delete(@PathVariable("id") Long id) {
    todoService.delete(id);
    return ResponseEntity.noContent().build();
  }
}

① リクエストを受け取る

@RequestParam のデフォルト値

@RequestParam(name = "status", defaultValue = "ALL") String status
  • クエリパラメータ未指定時に"ALL"が使われる
  • ?status=ACTIVEのように渡すと"ACTIVE"になる

@PathVariable の明示的な name 指定

@PathVariable("id") Long id
  • メソッド引数名とパス変数名が一致する場合は省略可能だが、明示すると可読性が上がる

@Valid でリクエストボディを検証

@PostMapping
public ResponseEntity<TodoResponse> create(@Valid @RequestBody TodoRequest request) {
  • @Validを付けるとTodoRequestのBean Validationアノテーション(@NotBlank、@Sizeなど)が実行される
  • バリデーション失敗時はMethodArgumentNotValidExceptionがスローされる
  • @RestControllerAdviceで一括ハンドリングするのが定石

🔍 なぜ create() に throws が書かれていないのに例外が飛ぶのか

throws が必要なのはチェック例外だけ

Javaの例外には「チェック例外」と「非チェック例外」の2種類がある。IOExceptionのようなチェック例外はthrowsを書かないとコンパイルエラーになるが、RuntimeExceptionを継承した非チェック例外はコンパイラが一切チェックしない。MethodArgumentNotValidExceptionはRuntimeException系(BindException経由)なので、throwsを書かなくてもコンパイルは通る。「throwsが書かれていない = 例外が起きない」わけではなく、単に「Javaがそのチェックを強制していない」だけ。

例外は create() の中身が実行される前に発生する

より重要なのは、この例外がcreate()メソッドの処理が始まる前に発生している点。@Valid @RequestBody TodoRequest requestという引数を見つけると、Springは実際にcreate()を呼び出す前に、引数を準備する段階(HandlerMethodArgumentResolverという内部の仕組み)でJSONの変換とバリデーションを済ませてしまう。ここで失敗すると、Spring自身がMethodArgumentNotValidExceptionを投げ、create()の中身は1行も実行されない。 

① リクエスト受信 (POST /api/todos, JSON body)
        ↓
② JSONを TodoRequest オブジェクトに変換 (デシリアライズ)
        ↓
③ @Valid が付いているのを見つける
        ↓
④ TodoRequest の中身をバリデーションルールと照合
        ↓
   ┌─ OK なら ──────────────→ ⑤ create(request) を実際に呼び出す
   └─ NG なら ──→ MethodArgumentNotValidException を投げて
                  ⑤には絶対に到達しない(即座に処理が中断される)

つまり「create()メソッドが例外を投げている」のではなく、「Springがcreate()を呼ぶ前にチェックして、ダメならSpring自身が例外を投げる」という流れ。だからコントローラー側にはthrowsはおろか、例外に関するコードが一切登場しない。捕まえたい場合は@RestControllerAdviceで一括ハンドリングする。

DTOパターン: なぜEntityを直接受け取らないか

Entityをそのまま受け取って返すのではなく、DTO(Data Transfer Object)に変換して受け渡しする。

Request JSON → TodoRequest (DTO) → todoService.create() → Entity → TodoResponse (DTO) → Response JSON

理由:

  • Entityのフィールド変更がレスポンス形式に影響しない
  • 不要なフィールド(パスワードなど)を返さずに済む
  • バリデーションロジックをDTOに閉じ込められる(@Validが機能するのもこのため)

🔍 「バリデーションロジックをDTOに閉じ込める」とは / Before・After比較

入力チェックのルールを1箇所(DTOクラス)にまとめて書き、使う側(Controller)は何も考えずに済むようにする、という意味。

DTOを使わない場合(悪い例)

@PostMapping
public ResponseEntity<Todo> create(@RequestBody Todo todo) {
    // Controllerの中でチェックを書く羽目になる
    if (todo.getTitle() == null || todo.getTitle().isBlank()) {
        return ResponseEntity.badRequest().build();
    }
    if (todo.getTitle().length() > 100) {
        return ResponseEntity.badRequest().build();
    }
    // ...他のフィールドのチェックも続く
    todoService.save(todo);
    return ResponseEntity.ok(todo);
}
  • チェックのロジックがControllerに散らばる
  • 同じEntityを使う別のControllerやメソッドがあれば、そこにも同じif文をコピペすることになる
  • 「タイトルのルールは何文字までだっけ?」を知りたい時、Controllerのコードを読まないと分からない

DTOパターンを使う場合(良い例)

public class TodoRequest {
    @NotBlank(message = "タイトルは必須です")
    @Size(max = 100, message = "タイトルは100文字以内で入力してください")
    private String title;
    // getter / setter
}
@PostMapping
public ResponseEntity<TodoResponse> create(@Valid @RequestBody TodoRequest request) {
    // if文が一切ない。ここに来た時点でルールは全て満たされている
    TodoResponse created = todoService.create(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(created);
}
  • ルール(@NotBlank、@Sizeなど)がTodoRequestクラスのフィールド定義そのものに書かれている
  • Controller側は@Validを付けるだけで、ルールの中身を一切知らなくていい
  • 別のControllerや別の場所で同じTodoRequestを受け取れば、自動的に同じチェックが効く(コピペ不要)
  • ルールを変更したい時(例: 最大文字数を200に変える)も、TodoRequestクラスの1箇所を直せば、使っている全箇所に反映される

つまり「ロジックをDTOに閉じ込める」= チェックのルールをDTOという1つの箱にしまい込んで、使う側はその箱を渡すだけで済むようにする、というイメージ。カプセル化と同じ発想。

② レスポンスを返す

🔍 用語ノート: ResponseEntity<List<TodoResponse>> の意味

ジェネリクスが入れ子になっているだけで、分解すると難しくない。 

ResponseEntity< List< TodoResponse > >
     ↑              ↑        ↑
  レスポンス全体   複数件の  TodoResponse
  (ステータス+     リスト    という具体的な型
   ボディ)

List<TodoResponse>
「TodoResponse型の要素だけを持つリスト」という意味。Listだけだと中身が何型か分からないが、<TodoResponse>と書くことで中身の型をコンパイラに教えている。

ResponseEntity<T>
ResponseEntity自体もジェネリクスを使ったクラスで、「レスポンスのボディに何を入れるか」を<T>の部分で指定する。ResponseEntity<TodoResponse>ならボディは1件、ResponseEntity<List<TodoResponse>>ならボディは複数件のリストになる。

getAll()は一覧取得(複数件)なのでListで包み、create()やupdate()は1件だけ返すのでResponseEntity<TodoResponse>(Listなし)になっている。

HTTPメソッドとResponseEntityの対応

HTTPメソッド用途正常時のステータスResponseEntity
@GetMapping一覧取得・単件取得200 OKResponseEntity.ok(body)
@PostMapping新規作成201 CreatedResponseEntity.status(HttpStatus.CREATED).body(body)
@PutMapping全体更新200 OKResponseEntity.ok(body)
@PatchMapping部分更新200 OKResponseEntity.ok(body)
@DeleteMapping削除204 No ContentResponseEntity.noContent().build()

POSTで新規作成した場合は「作成されたリソースが返る」ことを示すため201 Createdを使うのがRESTの慣習。DELETEは「成功したかどうか」だけが重要で返すデータがないため、200 OK + 空ボディより204 No Contentの方が「意図的にボディがない」ことを明確に伝えられる。

ResponseEntityの組み立て方

ResponseEntityは「ステータスコード + ボディ」をビルダー形式で組み立てるクラス。ok(body)やstatus(...).body(...)はすべて内部的に同じ考え方で作られている。

// ボディありのパターン(POST → 201 Created)
ResponseEntity.status(HttpStatus.CREATED)  // ① ステータスだけ決める
              .body(created);              // ② ボディを詰めて完成

// ボディなしのパターン(DELETE → 204 No Content)
ResponseEntity.noContent()  // ① ステータスを204に設定
              .build();      // ② ボディなしでレスポンスを完成させる

各メソッドの意味

  • status(HttpStatus.CREATED) / noContent()

    まずステータスコードだけを決める。

    ショートカットの関係
    status(任意のステータス)が本来の基本形で、何でも指定できる汎用メソッド。noContent()やok()は、その中でもよく使うステータスコードを固定して呼び出しを短く書けるようにした「省略形(ショートカット)」に過ぎない。

    つまり内部的には次のように実装されているイメージ: 

    // ResponseEntity クラスの中身(イメージ)
public static BodyBuilder noContent() {
    return status(HttpStatus.NO_CONTENT); // 結局これを呼んでいるだけ
}

public static BodyBuilder ok() {
    return status(HttpStatus.OK); // これも同じパターン
}

    そのため以下の2行は完全に同じ意味になる。 

    ResponseEntity.noContent().build();
ResponseEntity.status(HttpStatus.NO_CONTENT).build();  // ↑と全く同じ
  • .body(created)

    レスポンスに含めるオブジェクトをボディにセットして完成させる。

    使いどころ
    200以外(201, 202, 409など)のステータスでボディを返したい時に使う。

  • .build()

    ボディをセットせず完成させる専用メソッド。

    なぜ.body(null)ではないか
    204 No Contentは「ボディを含めない」ことに意味があるステータスなので、.body(null)ではなく.build()で「ボディが存在しない」ことを型として表現する。
